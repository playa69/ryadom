# Пост-деплойные проверки (боевой адрес)

Тестовый аккаунт с диалогами, посеянными **до** выката, и набор проверок, который после выката сверяет с ним данные и пробует приложение в деле.
Порядок выката и откат — в [`k8s/README.md`](../README.md) и [`k8s/agent/README.md`](../agent/README.md).

Что нужно: Python 3.11+ и `uv` (или `pip install -r requirements.txt`). Все команды из каталога `k8s/postdeploy`.

## 1. Посев (один раз, до выката)

```bash
uv run --no-project --with requests --with websocket-client python seed.py --out <путь к снимку>
```

Скрипт:

1. создаёт анонимный аккаунт по устройству (`POST /api/auth/device`), id устройства вида `loadtest-smoke-…`, принимает согласия первого экрана;
2. ведёт через публичный API и сокет три диалога, как приложение: два **завершённых** (итог диалога строится агентом) и один **открытый** (пять коротких реплик через Gemini Live);
3. читает всё обратно через API и пишет снимок: креды устройства, id диалогов, id, авторов, тексты и время сообщений, итоги.

Снимок содержит креды аккаунта и тексты тестовых реплик: **в репозиторий он не попадает** (`.gitignore`), хранить его нужно локально у администратора.
Второй посев поверх существующего файла запрещён: аккаунт один и живёт между выкатами. Если посев оборвётся, в файле остаётся неполный снимок
(`"complete": false`) с кредами: удалите его и посейте заново (прежний аккаунт останется в проде).

Аналитика: до api 0.6.1 отметки тестового трафика нет, поэтому события посева (`account_created`, `dialog_started`) попадут в продуктовую
аналитику как обычные. Пометить аккаунт тестовым (исключающий список) — отдельное решение владельца. После выката api 0.6.1 новые аккаунты
с префиксом `loadtest-` помечаются тестовыми сами.

## 2. Проверки

```bash
# до выката: проверить сами проверки на текущем проде (новые возможности пропускаются)
POSTDEPLOY_BASELINE=<снимок> uv run --no-project --with requests --with websocket-client --with pytest python -m pytest -q --expect pre

# после выката
POSTDEPLOY_BASELINE=<снимок> uv run --no-project --with requests --with websocket-client --with pytest python -m pytest -q --expect post
```

Переменные: `POSTDEPLOY_BASELINE` (путь к снимку, по умолчанию `baseline.json` в текущем каталоге), `PUBLIC_BASE_URL` (по умолчанию адрес из снимка),
`POSTDEPLOY_FULL=1` (добавить проверку μ-law: ещё одна реплика).
Флаг `--expect pre|post` (или `POSTDEPLOY_EXPECT`).

| Группа | Тест | Что доказывает |
|---|---|---|
| Сервисы | `test_api_health` | api и его БД живы |
| | `test_app_status_is_open` | открытый маршрут политики версий отвечает |
| | `test_private_routes_need_a_token` | закрытое закрыто (401 без токена) |
| | `test_front_ends_answer` | web (`/app`), PWA (`/pwa/`) и лендинг (`/`) отдают страницы |
| | `test_csp_lets_the_opus_decoder_run`* | в `script-src` web и PWA есть `'wasm-unsafe-eval'` (иначе WASM-декодер Opus не стартует) |
| Миграция | `test_test_account_is_the_same` | вход по устройству даёт тот же аккаунт (БД приложения цела) |
| | `test_dialogs_survived` | все диалоги на месте, завершённые завершены, открытый открыт, итоги те же |
| | `test_messages_survived` | начало истории каждого диалога совпадает со снимком: id, автор, текст, время (миграция файла агента ничего не потеряла и не исказила) |
| | `test_open_dialog_resumes` | старт диалога возвращает прежний открытый, а не новый |
| Работа | `test_text_turn_with_voice_for_a_legacy_client` | диалог идёт: ответ текстом и озвучка pcm16 для клиента без `codecs`, обе реплики сохранились |
| | `test_opus_is_negotiated_and_well_formed`* | клиент с `codecs` получает Opus: кодек в `tts_start`, пакеты разбираются, сжатие порядка 1/16 |
| | `test_mulaw_is_negotiated`* (`POSTDEPLOY_FULL=1`) | μ-law согласуется |
| | `test_memory_of_the_test_account_is_off_and_empty`* | поле `mode` ответа памяти равно `on` (оставлено для старых клиентов), у аккаунта память выключена, фактов нет |

\* только в режиме `post`.

Реплики идут в открытый тестовый диалог и остаются в нём; снимок сравнивается по **началу** истории, поэтому проверки можно гонять сколько угодно раз.
В вывод тексты реплик не попадают. Каждая реплика к Gemini стоит порядка тысяч токенов; полный прогон делает две.

## 3. Новые возможности выката (по просьбе)

`test_telegram.py` (с `--expect post`) проверяет Telegram Mini App снаружи, без аккаунтов: CSP PWA пускает во фрейм только Telegram Web, а вход через Telegram включён и отклоняет данные запуска, подписанные не нашим ботом (`NOT_CONFIGURED` значит, что ключ `TELEGRAM_BOT_TOKEN` в `app-secrets` не дошёл до api).

`test_features.py` проверяет память агента в бою от согласия до стирания. Запускается только по `POSTDEPLOY_FEATURES=1`: ходит в модель извлечения и в Gemini
и оставляет в проде тестовые данные (в конце стирает память и выключает её).

```bash
POSTDEPLOY_FEATURES=1 POSTDEPLOY_FEATURES_ACCOUNT=<файл> uv run --no-project --with requests --with websocket-client --with pytest python -m pytest test_features.py -v -s --expect post
```

Аккаунт отдельный от миграционного: id устройства `loadtest-features-…`. Префикс `loadtest-` (`ANALYTICS_TEST_DEVICE_PREFIX` сервера) заставляет api с 0.6.1 пометить
аккаунт тестовым **до первого события**: все его серверные события уходят в аналитику со свойством `traffic_type=test`, и продуктовые отчёты, настроенные на исключение
тестового трафика, не считают его людьми. Файл с кредами (`POSTDEPLOY_FEATURES_ACCOUNT`) хранится локально, в git не попадает; аккаунт создаётся один раз и переиспользуется.

Проверяется по шагам: сервер в режиме `on`; включение без согласия отказано (`CONSENT_REQUIRED`), с согласием записано; разговор из четырёх реплик (нужно не меньше четырёх или явное
«запомни…») и извлечение фактов после его конца; источники у фактов; экспорт и журнал изменений; закрепление факта; разговор «Без памяти» ничего не оставляет; новый разговор с непустой
памятью отвечает голосом; забыть один факт (повтор тоже успешен) и забыть всё; выключение.

Что проверки **не** покрывают: звук на слух и экран (проверяются вручную), голосовые реплики человека (нужен микрофон), реальные устройства
(iOS до 26, Android WebView, Firefox), нагрузку, метрики и журналы кластера (смотреть `kubectl`).
