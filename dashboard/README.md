# dashboard — метрики для Sber500

Один файл `app.py` (Python 3.12, стандартная библиотека и psycopg): страница `/dashboard` и JSON `/dashboard/api`
с шестью метриками по московским суткам за весь период конкурса — с 2026-11-05 по текущие сутки включительно.
Из всех метрик исключён трафик test/internal (`users.properties->>'traffic_type'` в базе app; отсутствие
метки = real). Плюс публичный endpoint для системы сбора Sber500 — `GET /api/v1/metrics/daily`
(Bearer-токен, контракт по ТЗ конкурса, см. раздел ниже).

## Метрики

- **dau** — уникальные аккаунты с хотя бы одним пользовательским сообщением за сутки.
- **daily_active_account** — внутренняя метрика: аккаунты со строго больше чем 10 сообщениями за сутки.
- **new_users** — аккаунты, чьё первое известное сообщение пришлось на эти сутки. Первый известный день —
  минимум из `user_reply_counts.first_reply_at` (база app), первого сохранённого сообщения в базе agent и
  первой live-turn трассы Langfuse; у legacy-аккаунтов `first_reply_at` остаётся NULL навсегда, поэтому
  одним источником обойтись нельзя. Каждый аккаунт считается новым ровно один день за всю историю.
- **total_users** — накопленный итог по снимкам: `total_users` предыдущего снимка + `new_users` дня;
  удалённые аккаунты не вычитаются.
- **llm_requests** — логические вызовы LLM, инициированные действиями пользователей: записи GENERATION
  Langfuse с именами `live_turn_voice`, `live_turn_text`, `mood_classify_sber`, `mood_classify_gemini`,
  `dialog_recap`, `memory_extract`, `memory_instruct`, у которых у трассы есть userId (не test/internal).
  Не считаются: `text_turn` (кризисный фиксированный текст, вызова модели нет), `live_turn_recovery`
  (технический ретрай уже посчитанного хода), `gemini_tts_phrase` (озвучка), `weekly_digest` (плановая
  сводка), записи без userId (прогревы). Глубина истории ограничена хранилищем Langfuse.
- **tool_requests** — успешно выполненные вызовы агента к серверу памяти: записи TOOL Langfuse
  `memory_search`, `memory_write`, `memory_delete_document`, `memory_forget_dataset` без `level=ERROR`,
  userId трассы не test/internal. Записи появляются со дня выката агента с TOOL-инструментацией, более
  ранние дни показывают 0. На странице метрика подписана «Tool calls — Память»; техническое поле JSON — `tool_requests`.

### Откуда берутся «сообщения»: база агента + трейсинг

Сохранённая история в базе agent неполна: дни 11–16.11.2026 в `messages` не записаны вовсе, провалы есть и
в другие дни. Поэтому «сообщения» для `dau` и `daily_active_account` считаются по двум источникам сразу:

1. база agent — разбивка «день × user_id → число сообщений» по `messages` (role='user');
2. Langfuse — записи GENERATION `live_turn_voice`/`live_turn_text` (подмножество `LLM_NAMES`): одна трасса
   (traceId) с такой записью — одно сообщение, связь с аккаунтом — по userId трассы. Дедупликация по
   (московский день, userId, traceId): повторная GENERATION той же трассы (ретрай клиента) сообщение не
   дублирует. `live_turn_recovery` (ретрай хода), `dialog_recap`, `mood_classify_*`, `memory_*` и записи
   TOOL сообщениями не считаются.

Для каждой пары «день, аккаунт» берётся **большее** из двух чисел (max), а не сумма: оба источника описывают
одни и те же ходы, и сумма посчитала бы сохранённые сообщения дважды. При полной базе верх даёт её count,
при потерянных записях — восстановленное из трейсинга число. Это приближение: ход, потерянный обоими
источниками по-разному, недосчитывается; завышения за счёт двойного счёта нет. Тот же объединённый расчёт
действует и для предварительных текущих суток, и для снимков, и для backfill. `new_users` дополнительно
использует первую live-turn трассу аккаунта как третий источник первого известного дня; при backfill/catch-up
первые дни накапливаются через границу окон выгрузки, чтобы аккаунт, известный только по трейсингу, не
посчитался новым в каждом окне заново. Для предварительных текущих суток окна в один день мало: первый
известный день считается по всей истории конкурса — `langfuse_first_turns` сворачивает её постранично
(observations с фильтром `name` на стороне API, страницы в памяти не накапливаются; полная выгрузка истории
в список убивала под по лимиту 128Mi), иначе аккаунт, говоривший раньше только в трейсинге, ошибочно стал
бы «новым» сегодня и раздул бы `total_users`.

Перечни имён зашиты константами `LLM_NAMES`/`MESSAGE_TURN_NAMES`/`TOOL_NAMES` в `app.py` с
комментариями-источниками (точки `start_turn`/`start_tool` агента). **При каждой правке трейсинга агента
(новые `start_turn`/`start_tool`) эти списки пересматриваются** — новое имя в метрику не попадёт, пока его
не добавят осознанно.

## Снимки и текущие сутки

Завершённые сутки закрываются в 00:15 МСК: метрики считаются из сырых источников один раз и пишутся в таблицу
`daily_metrics` собственной базы (`DASHBOARD_DATABASE_URL`, DDL — идемпотентный, при старте) запросом
`INSERT ... ON CONFLICT (day) DO NOTHING` — прошлое не пересчитывается и не перезаписывается. При старте
и после каждого снимка — catch-up: завершённые дни без снимка досчитываются из сырых источников.

Текущие сутки снимком не закрываются. При каждом обновлении часового кэша их шесть метрик считаются из тех же
сырых источников (базы agent и app, API Langfuse) по тем же определениям и добавляются в отчёт последним,
предварительным днём: числа реальные, но могут уточняться до закрытия суток (опоздавшие записи, удаления
в течение дня). `total_users` текущих суток — `total_users` вчерашнего снимка плюс `new_users` текущих суток:
цепочка итога остаётся аддитивной.

Прошлые дни страница и JSON читают только из снимков; к сырым источникам обращаются фоновое закрытие суток
и обновление часового кэша, но не сами запросы страницы. При недоступности своей базы или сырых источников
отдаётся последний удачный отчёт из памяти, при холодном старте без базы — 503. Наружу уходят только суммы:
ни текстов, ни идентификаторов людей.

## Backfill

История до выката восстанавливается разово и идемпотентно (пишутся только завершённые дни без снимка;
текущие сутки backfill не закрывает):

```bash
python app.py --backfill
```

Считается от первого сохранённого сообщения в базе agent до вчера: `dau`/`daily_active_account` — по
объединённым источникам сообщений (база agent + восстановленные из Langfuse ходы, max по паре «день,
аккаунт»), `new_users` — по первому известному дню из трёх источников (`first_reply_at`, первое сохранённое
сообщение, первая live-turn трасса; накапливается через границу окон), `llm_requests` — из записей
GENERATION Langfuse в пределах их доступной истории (дни старше — 0), `tool_requests` — из записей TOOL
Langfuse (дни до выката инструментации — 0).
История выгружается окнами не больше недели с инкрементальной записью снимков: вся выгрузка Langfuse одним
запросом в память не собирается, а цепочка `total_users` остаётся аддитивной. Трассы Langfuse выгружаются
с запасом 24 часа назад от окна observations: observation на границе суток может принадлежать трассе,
начавшейся раньше, и без запаса потеряла бы userId. Дни начала точного учёта показываются на странице
(переменные `LLM_REQUESTS_SINCE`, `TOOL_REQUESTS_SINCE`).
Честное ограничение: первые сообщения, физически удалённые до backfill, не восстанавливаются.

**Пересчёт снимков 05.11–16.11.2026.** Снимки, записанные версией 0.2.0, посчитаны по неполной базе (дни
11–16.11 в `messages` отсутствуют, провалы есть и раньше) и занижены. Backfill их не переписывает: снимки
неизменны по дизайну. Чтобы пересчитать объединённым расчётом, нужно отдельное разрешение владельца на
удаление строк `daily_metrics` за 05.11–16.11.2026 (скилл `db`, ручной `DELETE`), затем — повторный запуск
Job backfill из образа 0.2.1 (порядок — `k8s/dashboard/README.md`). Без разрешения строки не трогаем.

## Переменные

- `DASHBOARD_USER` (по умолчанию `sber500`), `DASHBOARD_PASSWORD` — вход на страницу; без пароля сервис не стартует.
- `DIALOG_DATABASE_URL` — база agent (только чтение; сессия `default_transaction_read_only=on`).
- `APP_DATABASE_URL` — база app (только чтение): метки `traffic_type` и `user_reply_counts.first_reply_at`.
- `DASHBOARD_DATABASE_URL` — собственная база дашборда: таблица снимков `daily_metrics`, единственная запись сервиса.
- `LANGFUSE_HOST`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` — чтение API Langfuse (observations + traces).
- `LLM_REQUESTS_SINCE`, `TOOL_REQUESTS_SINCE` — даты начала точного учёта (YYYY-MM-DD) для текста на странице.
- `PORT` (по умолчанию 8080).

Без `DASHBOARD_PASSWORD`, `DIALOG_DATABASE_URL`, `APP_DATABASE_URL`, `DASHBOARD_DATABASE_URL`,
`LANGFUSE_PUBLIC_KEY` или `LANGFUSE_SECRET_KEY` сервис не стартует с понятной ошибкой.

Выкат, Secret и сеть — `k8s/dashboard/README.md`.

## Восстановленные Tool calls Cognee

За 05.11–09.11.2026 Tool calls восстановлены из успешных операций `pipeline_runs`, за 10.11–17.11 — из HTTP access-логов Cognee. Считаются успешные `search`, пары `add+cognify` (один логический вызов записи) и успешные удаления; диагностические `postdeploy-synthetic-*` исключены. По решению владельца восстановление включает все фактические вызовы без сопоставления с аккаунтами и `traffic_type`.

Суточные суммы хранятся в `tool_call_recovery` отдельно от неизменяемых снимков. В отчёте для каждого дня берётся максимум из восстановленного числа и TOOL-наблюдений Langfuse, поэтому источники не складываются. Это нижняя граница: более ранние access-логи не сохранились, а `pipeline_runs` содержит не все типы поисков.

## Metrics API для системы сбора Sber500

Публичный endpoint по ТЗ конкурса: `GET /api/v1/metrics/daily?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`
с заголовком `Authorization: Bearer <METRICS_API_TOKEN>`. Отдельный бессрочный токен (≥32 символов, только
чтение, в Secret `dashboard-secrets`), лимит — 30 запросов в минуту на IP (429), тело всех ошибок —
`{"error": "…"}` (400 на невалидные даты и диапазон больше 90 дней, 401 без токена, 5xx при сбое расчёта).

Ответ — одна запись на каждый день диапазона, включительно, строго поля ТЗ:

```json
{"startup_id": "ryadom", "timezone": "Europe/Moscow", "generated_at": "…+03:00",
 "data": [{"date": "2026-11-17", "dau": 0, "llm_requests": 0, "tool_requests": 0,
           "total_users": 0, "new_users": 0, "is_final": true}]}
```

- Источники те же, что у страницы: закрытые сутки — неизменяемые снимки `daily_metrics` (внутренняя
  `daily_active_account` наружу не отдаётся), текущие сутки — тот же предварительный расчёт из сырых
  источников и `is_final=false`. Дни без активности и дни раньше начала истории снимков (2026-11-05) —
  нули, а не пропуск.
- `total_users` дня без снимка повторяет последний известный итог (накопленная кривая не проваливается
  к нулю); на первый день диапазона подкладывается итог последнего снимка строго раньше него.
- Ответ кэшируется на 15 минут по паре (from, to): закрытые дни неизменны, повторные запросы системы
  сбора (05:00–07:00 МСК, последние 7 дней) в базу и Langfuse не ходят.

Строка для организаторов при подключении (определения метрик — выше): «активный» = аккаунт с ≥1 сообщением
агенту за сутки; `total_users` — все когда-либо зарегистрировавшиеся (удалённые не вычитаются);
`llm_requests`/`tool_requests` — логические вызовы по наблюдениям Langfuse, test/internal трафик исключён;
восстановленные из журналов Cognee Tool calls за 05.11–17.11 учтены без сопоставления с аккаунтами.
