# agent-api

## Purpose
Общие правила внутреннего API агента для шлюза приложения (сервис `api`): адресация, внутренняя авторизация, идентификаторы, формат ошибок и общие коды, служебные эндпоинты, версия и совместимость, сквозная трассировка, а также проба самого шлюза. Агент недоступен извне кластера, и его единственный вызывающий — шлюз. Что делают доменные маршруты (разговор, журнал, итоги, память, стирание), описано в capability своих доменов: `dialog`, `dialog-voice`, `dialog-history`, `dialog-recaps`, `memory-notes`, `memory-search`, `mood-diary`, `account-deletion`; здесь они только перечислены.

## Requirements

### Requirement: Адресация и доступность агента
Агент SHALL быть доступен только внутри кластера: у его сервиса тип `ClusterIP`, порт 8001, внешнего маршрута (HTTPRoute) нет. Шлюз SHALL обращаться к агенту по адресу из `AGENT_API_URL`, с таймаутом `AGENT_TIMEOUT_MS` (по умолчанию 10 секунд) и внутренним токеном из `AGENT_API_TOKEN`. Адрес WebSocket шлюз получает из адреса REST заменой схемы. Пустой `AGENT_API_TOKEN` значит «заголовок Authorization к агенту не отправлять» (локальная заглушка); у агента внутренний токен (`AGENT_INTERNAL_TOKEN`) обязателен и непуст, без него он не стартует.

Поверхности: agent · api

#### Scenario: Запрос извне
- **WHEN** запрос к агенту приходит с публичного хоста продукта
- **THEN** ни один маршрут хоста его не обслуживает: `/api/*` — шлюз, остальные пути — клиенты и сайт

#### Scenario: Агент не стартует без токена
- **WHEN** агент запускается без `AGENT_INTERNAL_TOKEN`
- **THEN** процесс завершается с ошибкой настроек, а не принимает запросы без защиты

#### Scenario: Локальная заглушка
- **WHEN** `AGENT_API_TOKEN` у шлюза пуст
- **THEN** шлюз вызывает агента без заголовка Authorization

### Requirement: Внутренняя авторизация
Все маршруты `/v1/**`, включая рукопожатие WebSocket, SHALL требовать заголовок `Authorization: Bearer <токен>` с внутренним токеном; схема сравнивается без учёта регистра, значение — за постоянное время. Запросы без токена или с неверным токеном MUST отклоняться ответом `401` и кодом `AGENT_UNAUTHORIZED` («Нужен внутренний токен»), обработка не выполняется; для WebSocket отклонение — HTTP-ответ `401` на рукопожатии с тем же телом.

Поверхности: agent

#### Scenario: Запрос без токена
- **WHEN** запрос к `/v1/users/{userId}/dialogs` приходит без заголовка авторизации
- **THEN** ответ `401` с телом `{ "error": { "code": "AGENT_UNAUTHORIZED", … } }`

#### Scenario: Неверный токен
- **WHEN** запрос приходит с токеном, не совпадающим с внутренним
- **THEN** ответ `401`, обработка не выполняется

#### Scenario: Сокет без токена
- **WHEN** рукопожатие WebSocket приходит без заголовка авторизации
- **THEN** оно отклоняется ответом `401`

### Requirement: Идентификаторы и формат
Все маршруты агента SHALL быть вложены в человека: `/v1/users/{userId}/…`. `userId` — UUID человека на стороне шлюза (почта и имя агенту не передаются); агент приводит его к каноническому виду, а не-UUID MUST отклонять ответом `400` и кодом `AGENT_VALIDATION` («userId должен быть UUID»). `dialogId`, `messageId` и прочие идентификаторы — непрозрачные строки, выдаваемые агентом. Формат — JSON, UTF-8. Принадлежность диалога человеку проверяет только агент: чужой и несуществующий диалог MUST быть неразличимы — `404` и `AGENT_DIALOG_NOT_FOUND` на всех путях, включая рукопожатие WebSocket.

Поверхности: agent

#### Scenario: Не-UUID в пути
- **WHEN** шлюз вызывает `GET /v1/users/not-a-uuid/dialogs`
- **THEN** ответ `400` с кодом `AGENT_VALIDATION`

#### Scenario: Чужой диалог
- **WHEN** запрос содержит `dialogId`, принадлежащий другому человеку
- **THEN** ответ `404` `AGENT_DIALOG_NOT_FOUND`, как для несуществующего диалога

#### Scenario: Рукопожатие WebSocket
- **WHEN** открывается сокет для пары (`userId`, `dialogId`) без совпадения
- **THEN** рукопожатие отклоняется `404`

### Requirement: Формат ошибок и общие коды
Ошибки REST SHALL возвращаться в формате `{ "error": { "code", "message", "details" } }`. Общие коды: `AGENT_VALIDATION` (400: тело или параметр невалидны, `details` — список `{ loc, msg }`; также ошибки маршрутизации веб-фреймворка вроде неизвестного пути или метода — со своим HTTP-статусом; `409` — второе живое соединение к диалогу на рукопожатии), `AGENT_UNAUTHORIZED` (401), `AGENT_DIALOG_NOT_FOUND` (404), `AGENT_INTERNAL` (500 — необработанная ошибка, «Внутренняя ошибка»; 503 — не удалось стереть данные или удалить разговор, повторить позже). Доменные коды — память (`MEMORY_UNAVAILABLE`, `MEMORY_DISABLED`, `MEMORY_FULL`, `NOTE_REJECTED`, `NOTE_NOT_FOUND`), итоги (`RECAP_NOT_AVAILABLE`, `RECAP_UNAVAILABLE`, `DIALOG_NOT_ENDED`) и итоги недели (`DIGEST_UNAVAILABLE`) — описаны в capability своих доменов. Ошибка в сокете диалога MUST передаваться кадром `error` с кодом и сообщением (`AGENT_INTERNAL`; `VOICE_UNAVAILABLE` — модель не ответила или не озвучила ответ, разговор при этом не завершается; подробности — capability `dialog-voice`). Необработанная ошибка MUST NOT показывать внутренних деталей и текстов реплик в теле.

Поверхности: agent

#### Scenario: Ошибка валидации
- **WHEN** тело или параметр запроса невалидны
- **THEN** ответ `400` с кодом `AGENT_VALIDATION` и перечнем полей в `details`

#### Scenario: Неизвестный путь
- **WHEN** шлюз вызывает путь, которого у агента нет
- **THEN** ответ `404` в том же формате с кодом `AGENT_VALIDATION`

#### Scenario: Необработанная ошибка
- **WHEN** обработчик падает с непредвиденным исключением
- **THEN** ответ `500` с кодом `AGENT_INTERNAL` и сообщением «Внутренняя ошибка»

#### Scenario: Стирание не удалось
- **WHEN** стирание данных человека не завершилось (хранилище или память недоступны)
- **THEN** ответ `503` `AGENT_INTERNAL`, а не `204`: шлюз не должен считать данные стёртыми

### Requirement: Когда шлюз считает агента недоступным
Шлюз SHALL считать агента недоступным при сетевой ошибке, превышении таймаута, ответе `5xx` и ответе не в JSON там, где ждали JSON; такая ошибка MUST превращаться в ответ шлюза клиенту `503` с телом `{ "errorMessage": … }`, а клиент показывает линии помощи (см. `crisis-safety`). Ответы `4xx` MUST доходить до вызывающего кода с кодом ошибки агента: решение принимается по коду, потому что один статус может нести разные коды. Код, который шлюз обрабатывает сам несмотря на `5xx` (`MEMORY_UNAVAILABLE` означает «память выключена», а не «агент лежит»), перечисляется явно для каждого вызова.

Поверхности: api · agent

#### Scenario: Агент не ответил
- **WHEN** агент не отвечает дольше таймаута или соединение оборвалось
- **THEN** клиент получает от шлюза `503`

#### Scenario: Ответ не в JSON
- **WHEN** агент отвечает не JSON там, где шлюз ждёт JSON
- **THEN** это считается недоступностью агента, клиент получает `503`

#### Scenario: Память выключена
- **WHEN** агент отвечает `503 MEMORY_UNAVAILABLE` на вызов памяти
- **THEN** шлюз не считает агента недоступным и отвечает по правилам памяти

### Requirement: Служебные эндпоинты
Агент SHALL предоставлять `GET /health` (liveness: всегда `{ "status": "ok" }`, пока жив процесс), `GET /health/ready`, `GET /version` и `GET /metrics` (метрики Prometheus). `GET /health/ready` MUST отвечать `200` всегда и перечислять выбранные компоненты: `status` (`ok`), `pipeline` (имя соединителя Gemini Live или `none`), `voicePipeline` (путь разговоров, для которых API не передал путь: `sber` — если у агента настроен прокси, иначе `gemini`), `tts` (озвучка фраз или `none`), `llm` (фоновая модель итогов и заметок или `none`), `dialogs` (`postgres` — диалоги в PostgreSQL и переживают перезапуск, `memory` — только в памяти процесса: хранилище не задано или не открылось), `memory` (`on` — память настроена, `unavailable` — не настроена, `off` — пока не создана). Отказ модели или озвучки не делает агента неготовым: он отвечает текстом, а итоги и заметки откладываются. Служебные эндпоинты MUST NOT требовать внутренний токен, MUST NOT попадать в access-журнал и MUST NOT быть доступны извне кластера.

Поверхности: agent

#### Scenario: Liveness
- **WHEN** запрашивается `GET /health`
- **THEN** ответ `200` `{ "status": "ok" }` без токена

#### Scenario: Readiness показывает компоненты
- **WHEN** запрашивается `GET /health/ready` у исправного агента с базой диалогов
- **THEN** ответ `200` с полями `pipeline`, `voicePipeline`, `tts`, `llm`, `dialogs: "postgres"` и `memory`

#### Scenario: База диалогов не открылась
- **WHEN** хранилище диалогов не открылось при старте агента
- **THEN** агент отвечает на запросы, диалоги живут в памяти процесса, `GET /health/ready` содержит `"dialogs": "memory"`

#### Scenario: Журнал доступа
- **WHEN** оркестратор опрашивает `/health`, `/version` или `/metrics`
- **THEN** эти обращения не попадают в access-журнал агента

### Requirement: Версия и совместимость
`GET /version` SHALL отвечать `{ "version": <версия сборки> }` (значение `APP_VERSION`, по умолчанию `0.1.0`). Контракт между шлюзом и агентом MUST меняться только добавлением полей: поля и кадры, не названные в контракте, игнорируются в обе стороны, поэтому новое поле не меняет версию контракта, а шлюз и агент выкатываются независимо. Кадры WebSocket несут версию протокола (`v: 1`).

Поверхности: agent · api

#### Scenario: Версия сборки
- **WHEN** запрашивается `GET /version`
- **THEN** ответ содержит версию сборки агента

#### Scenario: Неизвестное поле в теле
- **WHEN** шлюз присылает в теле запроса поле, которого нет в контракте
- **THEN** агент игнорирует его и обрабатывает остальное как обычно

#### Scenario: Неизвестное поле в ответе
- **WHEN** агент добавляет в ответ новое поле
- **THEN** прежний шлюз продолжает работать, поле игнорируется

### Requirement: Сквозная трассировка
Шлюз SHALL передавать агенту на каждый вызов (REST и WebSocket) пять заголовков трассировки: `x-trace-id`, `x-request-time`, `x-client-id`, `x-session-id`, `x-user-id` с текущими значениями запроса клиента; отсутствующее значение уходит пустым заголовком, и принимающий считает его отсутствующим (см. `app-shell`). Агент сегодня заголовки не читает и в своих журналах номера запроса не пишет; `userId` и `dialogId` для связи берутся из пути. Трассы моделей в Langfuse включаются только при заданных ключах проекта, не влияют на разговор (сбой записи — предупреждение в журнал), группируются по идентификатору диалога, и тексты реплик в них MUST NOT попадать: вместо них число знаков и слов, токены и задержки.

Поверхности: api · agent

#### Scenario: Заголовки на вызове агента
- **WHEN** клиент прислал шлюзу запрос с `x-trace-id: abc-123`, и шлюз вызывает агента
- **THEN** вызов агента несёт `x-trace-id: abc-123` и остальные четыре заголовка

#### Scenario: Заголовка у клиента нет
- **WHEN** клиент не прислал `x-trace-id`
- **THEN** шлюз не придумывает значение, заголовок к агенту уходит пустым

#### Scenario: Трейс без текста
- **WHEN** агент записывает ход диалога в Langfuse
- **THEN** вместо текста реплик в трассе стоит «[скрыто: N симв., M сл.]»

### Requirement: Состав маршрутов агента
Агент SHALL предоставлять маршруты по доменам, все под `/v1/users/{userId}`: диалоги — `POST /dialogs` (начало и возобновление), `GET /dialogs` и `GET /dialogs/{dialogId}` (журнал и история), `POST /dialogs/{dialogId}/end` (завершение), `DELETE /dialogs/{dialogId}` (удаление разговора), WebSocket `/dialogs/{dialogId}/ws` (разговор текстом и голосом); итоги — `GET /recaps`, `POST /dialogs/{dialogId}/recap/draft`, `PUT /dialogs/{dialogId}/recap`, `GET` и `PUT /dialog-settings`; память — `/memory` и вложенные пути (настройки, заметки, изменения, экспорт, инструкция); итоги недели — `POST /digests`; стирание человека — `DELETE /v1/users/{userId}` (`204`, синхронно, повторный вызов безопасен). Содержимое каждого — в capability домена.

Поверхности: agent · api

#### Scenario: Стереть человека
- **WHEN** шлюз вызывает `DELETE /v1/users/{userId}`
- **THEN** агент стирает разговоры и память человека и отвечает `204`; повторный вызов безопасен

#### Scenario: Маршрут без токена
- **WHEN** любой из перечисленных маршрутов вызывается без внутреннего токена
- **THEN** ответ `401`

### Requirement: Проба шлюза
Шлюз SHALL отвечать на `GET /api/health` без конверта: `200` и `{ "status": "ok", "timestamp" }`, если база данных доступна; `503` и `{ "status": "error", "timestamp" }`, если нет. Проба не проверяет агента. Подом, получившим сигнал остановки, она MUST отвечать `503` и `{ "status": "draining" }` с первого мгновения, чтобы балансировщик вывел его из ротации до закрытия диалогов; затем открытые диалоги закрываются кодом `1012`, и клиенты переподключаются сами. Ворота версий пробу не проверяют.

Поверхности: api

#### Scenario: Исправный шлюз
- **WHEN** база доступна
- **THEN** `GET /api/health` отвечает `200` и `status: ok`

#### Scenario: База недоступна
- **WHEN** база данных недоступна
- **THEN** проба отвечает `503` и `status: error`

#### Scenario: Остановка пода
- **WHEN** под получил сигнал остановки
- **THEN** проба отвечает `503` и `status: draining`
