# admin-console

## Purpose
Внутренняя админка «Рядом» для сотрудников: вход по одноразовому коду на почту из списка администраторов, поиск пользователей и карточка пользователя, блокировка и разблокировка, завершение сессий, ручное подтверждение почты, удаление аккаунта вместе с данными у агента и журнал действий администраторов. Администратор — это адрес из `ADMIN_EMAILS`; ролей у пользователей приложения нет и выдать их нельзя. Админка рассчитана на экран рабочего места, светлая, русскоязычная, под телефон намеренно не адаптирована и содержимое разговоров не показывает. Что такое удаление аккаунта для самого человека — в `account-deletion`; что блокировка значит для клиента — в `account-auth`.

## Requirements

### Requirement: Доступ только по сессии
Все страницы и все действия админки, кроме `/login` и `/logout`, SHALL требовать действующей сессии администратора; без неё запрос MUST перенаправляться на `/login`. Каждое действие над пользователем MUST проверять сессию заново, а не полагаться на проверку при показе страницы. Корень `/` MUST вести на `/users`, а `/login` при действующей сессии — тоже на `/users`. Админка публикуется на общем хосте под путём `/admin`; все страницы MUST быть закрыты от индексации (`noindex, nofollow`).

Поверхности: admin

#### Scenario: Страница без сессии
- **WHEN** посетитель без сессии открывает `/admin/users`, `/admin/users/{id}` или `/admin/audit`
- **THEN** он перенаправляется на экран входа

#### Scenario: Действие с истёкшей сессией
- **WHEN** сессия истекла, а администратор нажимает кнопку действия на ранее открытой карточке
- **THEN** действие не выполняется и администратор перенаправляется на экран входа

#### Scenario: Вход при действующей сессии
- **WHEN** администратор с действующей сессией открывает `/login` или `/`
- **THEN** он попадает на `/users`

#### Scenario: Закрыто от индексации
- **WHEN** поисковый робот загружает страницу админки
- **THEN** в метаданных страницы указано `noindex, nofollow`

### Requirement: Запрос кода входа
Экран входа SHALL принимать адрес почты («Рабочая почта») и отправлять шестизначный одноразовый код только на адрес из `ADMIN_EMAILS`; сравнение MUST не зависеть от регистра и пробелов по краям. Ответ экрана MUST быть одинаковым для любого корректного адреса, чтобы по нему нельзя было узнать, кто входит в список. Адрес в неверном формате MUST отклоняться сообщением «Проверьте адрес почты.» без отправки. Код живёт 10 минут; новый запрос MUST заменять предыдущий код для этого адреса. Если `ADMIN_EMAILS` пуст, войти не может никто.

Поверхности: admin

#### Scenario: Адрес из списка
- **WHEN** администратор вводит свой адрес и нажимает «Прислать код»
- **THEN** на этот адрес уходит письмо с шестизначным кодом, экран переходит на шаг «Код из письма на <адрес>»

#### Scenario: Адрес не из списка
- **WHEN** посетитель вводит корректный адрес, которого нет в списке
- **THEN** экран переходит на тот же шаг ввода кода, письмо не отправляется и код не создаётся

#### Scenario: Неверный формат адреса
- **WHEN** посетитель отправляет строку, не являющуюся адресом почты
- **THEN** экран остаётся на шаге ввода адреса и показывает «Проверьте адрес почты.»

#### Scenario: Повторный запрос кода
- **WHEN** администратор на шаге ввода кода нажимает «Прислать код ещё раз»
- **THEN** отправляется новый код, а прежний перестаёт действовать

### Requirement: Лимиты запросов на экране входа
Экран входа SHALL ограничивать частоту попыток счётчиками в памяти процесса: запросы кода — не более 5 за 10 минут на адрес почты и не более 20 за час на IP; отправка кода — не более 30 за 10 минут на IP. Счётчики MUST быть раздельными у каждого экземпляра админки и обнуляться при перезапуске. IP определяется по записи, которую добавил доверенный прокси в `X-Forwarded-For` (число доверенных прокси задаёт окружение), а не по первой, которую пишет клиент; без заголовков все посетители делят один счётчик. При превышении администратор видит «Слишком много попыток. Подождите немного и попробуйте снова.».

Поверхности: admin

#### Scenario: Много запросов кода для одной почты
- **WHEN** за 10 минут для одного адреса сделано шестое обращение за кодом
- **THEN** код не отправляется, экран возвращается на шаг ввода адреса с сообщением о слишком большом числе попыток

#### Scenario: Много запросов кода с одного IP
- **WHEN** с одного IP за час сделан двадцать первый запрос кода, даже на разные адреса
- **THEN** запрос отклоняется с тем же сообщением

#### Scenario: Много попыток ввода кода
- **WHEN** с одного IP за 10 минут отправлено тридцать первое значение кода
- **THEN** проверка не выполняется, экран остаётся на шаге ввода кода и показывает то же сообщение

### Requirement: Подтверждение кода и сессия администратора
Шаг ввода кода SHALL принимать ровно шесть цифр; иначе MUST показываться «Код состоит из шести цифр.» без обращения к проверке. Верный код MUST гаситься сразу: повторно им войти нельзя. Неверный или истёкший код MUST давать «Код неверный или истёк. Запросите новый.» с сохранением введённого адреса; после пятой неверной попытки код сгорает, и экран MUST вернуть на шаг ввода адреса с сообщением «Слишком много неверных попыток. Запросите новый код.». Если адрес убран из `ADMIN_EMAILS` после выдачи кода, вход MUST отклоняться сообщением «Доступ закрыт.» даже при верном коде. После успешного входа админка MUST выдать подписанную сессию в cookie `admin_session` на 24 часа (`httpOnly`, `SameSite=Lax`, `secure` в рабочем окружении, путь — префикс админки, чтобы cookie не уходила на сайт, в API и в веб-клиент) и перенаправить на `/users`. Список администраторов MUST сверяться на каждом запросе: убранный адрес теряет доступ после перезапуска сервиса, даже при неистёкшей cookie.

Поверхности: admin

#### Scenario: Верный код
- **WHEN** администратор вводит верный код в течение 10 минут
- **THEN** выдаётся cookie `admin_session` на 24 часа и открывается `/users`

#### Scenario: Неверный код
- **WHEN** администратор вводит неверный шестизначный код
- **THEN** экран остаётся на шаге ввода кода с тем же адресом и сообщением «Код неверный или истёк. Запросите новый.»

#### Scenario: Пять неверных попыток
- **WHEN** подряд введено пять неверных кодов к одному коду
- **THEN** код больше не принимается даже верный, экран возвращается на шаг ввода адреса и просит запросить новый код

#### Scenario: Код истёк или уже использован
- **WHEN** администратор вводит код старше 10 минут или тот, которым уже входил
- **THEN** вход отклоняется сообщением «Код неверный или истёк. Запросите новый.»

#### Scenario: Адрес убран из списка после выдачи кода
- **WHEN** адрес удалён из `ADMIN_EMAILS` между выдачей кода и его вводом
- **THEN** вход отклоняется сообщением «Доступ закрыт.» и экран возвращается на шаг ввода адреса с пустым полем

#### Scenario: Сессия сверяется со списком
- **WHEN** адрес убран из `ADMIN_EMAILS`, сервис перезапущен, а у администратора остаётся неистёкшая cookie
- **THEN** cookie перестаёт давать доступ, и следующий запрос перенаправляется на вход

### Requirement: Выход
Выход SHALL выполняться только запросом `POST /logout` из кнопки «Выйти» в шапке: он MUST очищать cookie `admin_session` и перенаправлять на экран входа. `GET /logout` MUST NOT выходить из системы, чтобы чужая страница не могла разлогинить администратора.

Поверхности: admin

#### Scenario: Выход
- **WHEN** администратор нажимает «Выйти»
- **THEN** cookie сбрасывается и открывается экран входа, а возврат на закрытую страницу ведёт на вход

#### Scenario: Выход запросом GET
- **WHEN** на `/logout` приходит запрос методом GET
- **THEN** сессия не сбрасывается

### Requirement: Каркас админки
Разделы админки SHALL открываться в общем каркасе: боковое меню фиксированной ширины с пунктами «Пользователи» (`/users`) и «Журнал действий» (`/audit`), шапка с адресом вошедшего администратора, подписью «Администратор» и кнопкой «Выйти», внизу меню — ссылка «Перейти на сайт» на публичный сайт в новой вкладке (см. `landing-site`). Админка MUST быть рассчитана на экран рабочего места; раскладки для телефона (сворачиваемое меню, карточки вместо таблиц) в ней нет, и это не дефект. Аналитики продукта в админке нет. Проба `GET /admin/api/health` SHALL проверять базу данных: 200 и `{"status":"ok"}` при исправной базе, иначе 503 и `{"status":"error"}`.

Поверхности: admin

#### Scenario: Навигация
- **WHEN** администратор находится на карточке пользователя
- **THEN** в меню подсвечен пункт «Пользователи», а переход в «Журнал действий» открывает `/audit`

#### Scenario: Переход на сайт
- **WHEN** администратор нажимает «Перейти на сайт»
- **THEN** сайт открывается в новой вкладке

#### Scenario: Проба при недоступной базе
- **WHEN** база данных недоступна
- **THEN** `/admin/api/health` отвечает 503 и `{"status":"error"}`

### Requirement: Список пользователей
Страница `/users` SHALL показывать пользователей таблицей по 25 на странице: «Почта» (ссылка на карточку; у аккаунта без почты — «Без почты · первые 8 знаков идентификатора»), «Имя», «Статус» («Активен», «Заблокирован», «Удалён»; «Удалён» сильнее «Заблокирован»), «Почта подтверждена» («да», «нет», «—» у аккаунта без почты), «Регистрация» (всегда по московскому времени). Под таблицей — «Найдено: N», переход между страницами «Назад»/«Вперёд» и «Страница X из Y». Когда никого не нашлось, показывается «Никого не нашлось. Попробуйте изменить условия поиска.». Содержимое разговоров в списке и в карточке MUST NOT показываться.

Поверхности: admin

#### Scenario: Список по умолчанию
- **WHEN** администратор открывает `/users`
- **THEN** пользователи идут от новых к старым, по 25 на странице, показано общее число

#### Scenario: Аккаунт без почты в списке
- **WHEN** в списке есть аккаунт без почты
- **THEN** вместо почты стоит «Без почты · …» с началом идентификатора, ссылка ведёт на его карточку

#### Scenario: Пустой результат
- **WHEN** условия поиска ничего не находят
- **THEN** вместо таблицы пояснение «Никого не нашлось…», счётчик «Найдено: 0»

### Requirement: Поиск, фильтры и сортировка списка
Поле «Почта, имя или id» SHALL искать по вхождению в почту и имя без учёта регистра (служебные символы шаблонов экранируются) и по точному идентификатору, если введён UUID; ввод применяется с задержкой 300 мс. Фильтры: статус («Любой», «Активен», «Заблокирован»), почта («Любая», «Подтверждена», «Не подтверждена»), удалённые («Показывать», «Скрыть», «Только удалённые»); сортировка «По дате» (от новых к старым) и «По почте», «По имени» (по возрастанию); порядок можно задать и в адресе (`order=asc` или `desc`). Пока включён хоть один фильтр, показывается кнопка «Сбросить». Состояние MUST храниться в адресе страницы, поэтому его можно сохранить в закладку. Непонятное значение в адресе MUST заменяться значением по умолчанию без ошибки; поисковая строка обрезается до 120 знаков.

Поверхности: admin

#### Scenario: Поиск по части почты
- **WHEN** администратор вводит часть почты в любом регистре
- **THEN** список сужается до подходящих аккаунтов

#### Scenario: Поиск по идентификатору
- **WHEN** администратор вставляет UUID аккаунта
- **THEN** находится этот аккаунт

#### Scenario: Состояние в адресе
- **WHEN** администратор выбрал фильтр «Заблокирован» и сортировку «По почте»
- **THEN** адрес страницы содержит эти условия, и после перезагрузки список прежний

#### Scenario: Мусор в адресе
- **WHEN** в адресе указан несуществующий порядок сортировки или номер страницы меньше 1
- **THEN** применяются значения по умолчанию, ошибки нет

### Requirement: Карточка пользователя
Страница `/users/{id}` SHALL показывать: почту (или «Аккаунт без почты»), значки статуса и подтверждения почты («Анонимный аккаунт», «Почта подтверждена», «Почта не подтверждена»), профиль (идентификатор, имя, подтверждение, дату регистрации, дату последнего изменения, дату удаления, время по Москве), открытые сессии (устройство так, как оно о себе сообщило, время входа, последняя активность, идентификатор клиента), ссылку «Что администраторы делали с этим аккаунтом» на журнал, отфильтрованный по этому аккаунту, и пояснение, что содержание разговоров в админке не показывается. Идентификатор, не являющийся UUID, или несуществующий пользователь MUST давать страницу «Страница не найдена» внутри каркаса со ссылкой «К пользователям». У удалённого аккаунта сессий нет, действия недоступны.

Поверхности: admin

#### Scenario: Открытие карточки
- **WHEN** администратор открывает карточку существующего аккаунта
- **THEN** видны профиль, сессии и блок «Действия»

#### Scenario: Нет сессий
- **WHEN** у аккаунта нет открытых сессий
- **THEN** показано «Открытых сессий нет.»

#### Scenario: Несуществующий пользователь
- **WHEN** открыт `/users/not-a-uuid` или идентификатор, которого нет
- **THEN** показана страница «Страница не найдена» с каркасом админки

#### Scenario: Удалённый аккаунт
- **WHEN** открыта карточка удалённого аккаунта
- **THEN** вместо кнопок написано, что действия недоступны, персональные данные стёрты и восстановить их нельзя, блока «Опасная зона» нет

### Requirement: Блокировка, завершение сессий и подтверждение почты
Карточка SHALL давать три действия, каждое из которых записывается в журнал действий. «Заблокировать»/«Разблокировать» переключает доступ: заблокированный аккаунт не может продлить сессию и начать разговор (см. `account-auth`), а при блокировке все его токены продления MUST отзываться, чтобы разблокировка не возвращала старую сессию, — человек входит заново; сообщения «Доступ закрыт.» и «Доступ восстановлен.». «Завершить все сессии» отзывает токены продления на всех устройствах, не блокируя аккаунт: войти заново можно сразу («Все сессии завершены. Войти заново можно сразу.»); кнопка отключена, когда сессий нет. «Подтвердить почту вручную» отмечает почту подтверждённой («Почта отмечена подтверждённой.») и показывается только аккаунту с неподтверждённой почтой. К удалённому аккаунту блокировка и завершение сессий неприменимы («Аккаунт удалён: …»), к аккаунту без почты подтверждение почты неприменимо. Заблокированный человек теряет доступ к разговорам, памяти, дневнику, ссылкам и списку сессий на ближайшем запросе, а остальные запросы с уже выданным токеном доступа проходят, пока он не истечёт (15 минут); подробности — в `account-auth`.

Поверхности: admin · api

#### Scenario: Блокировка
- **WHEN** администратор нажимает «Заблокировать» на активном аккаунте
- **THEN** аккаунт получает статус «Заблокирован», все его сессии завершаются, в журнале появляется запись «Заблокирован»

#### Scenario: Разблокировка
- **WHEN** администратор нажимает «Разблокировать»
- **THEN** статус снова «Активен», прежние сессии не возвращаются, человек входит заново

#### Scenario: Завершение сессий
- **WHEN** администратор нажимает «Завершить все сессии»
- **THEN** все сессии завершаются, аккаунт остаётся активным, в журнале запись «Сессии завершены»

#### Scenario: Ручное подтверждение почты
- **WHEN** администратор нажимает «Подтвердить почту вручную» на аккаунте с неподтверждённой почтой
- **THEN** почта отмечается подтверждённой, кнопка исчезает, в журнале запись «Почта подтверждена вручную»

#### Scenario: Аккаунт без почты в карточке
- **WHEN** открыта карточка аккаунта без почты
- **THEN** кнопки подтверждения почты нет

### Requirement: Удаление аккаунта администратором
Блок «Опасная зона» SHALL давать кнопку «Удалить аккаунт», открывающую окно «Удалить аккаунт?» с предупреждением, что аккаунт и все разговоры стираются без возможности восстановления, включая данные у сервиса диалогов. Кнопка «Удалить навсегда» MUST быть доступна только после того, как в поле введена почта пользователя (для аккаунта без почты — его идентификатор) с точностью до регистра и пробелов по краям; совпадение MUST проверяться заново на сервере, несовпадение даёт «Почта не совпала. Удаление отменено.». Что именно стирается (то же, что при удалении самим человеком, включая профиль в аналитике и отзыв согласий) и в каком порядке (сначала агент, затем аккаунт) — в capability `account-deletion` («Удаление администратором»). Если агент не ответил, ничего не удаляется и показывается «Сервис диалогов недоступен, данные не тронуты. Повторите позже.». При успехе показывается «Аккаунт удалён, разговоры стёрты.», статус в списке становится «Удалён», а в журнал действий пишется запись «Аккаунт удалён» с почтой на момент удаления; повторное удаление даёт «Аккаунт уже удалён.».

Поверхности: admin · api · agent

#### Scenario: Подтверждение вводом почты
- **WHEN** администратор открыл окно удаления и ввёл почту пользователя
- **THEN** кнопка «Удалить навсегда» становится доступной, а пока ввод не совпадает — отключена

#### Scenario: Несовпадение на сервере
- **WHEN** действие удаления отправлено с не совпавшей почтой
- **THEN** ничего не удаляется, показано «Почта не совпала. Удаление отменено.»

#### Scenario: Успешное удаление
- **WHEN** администратор подтверждает удаление, агент отвечает
- **THEN** у агента стёрты данные пользователя, аккаунт анонимизирован и помечен удалённым, в журнале запись «Аккаунт удалён», статус в списке — «Удалён»

#### Scenario: Агент недоступен
- **WHEN** агент не отвечает на стирание
- **THEN** аккаунт остаётся нетронутым, показано «Сервис диалогов недоступен, данные не тронуты. Повторите позже.»

#### Scenario: Состав стирания как у человека
- **WHEN** администратор удаляет аккаунт, у которого есть ссылки на разговоры, отметки настроения, результаты тестов и согласие на память
- **THEN** их не остаётся, согласие отмечено отозванным, стирание профиля в аналитике поставлено в очередь, а в журнале действий одна запись «Аккаунт удалён»

#### Scenario: Аккаунт уже удалён
- **WHEN** администратор повторно удаляет уже удалённый аккаунт
- **THEN** показано «Аккаунт уже удалён.»

#### Scenario: Аккаунт без почты
- **WHEN** удаляется гостевой аккаунт
- **THEN** окно просит ввести идентификатор пользователя

### Requirement: Журнал действий
Страница `/audit` SHALL показывать журнал действий администраторов над аккаунтами, от новых к старым, по 50 записей на странице: время по Москве и адрес администратора, действие («Заблокирован», «Разблокирован», «Почта подтверждена вручную», «Аккаунт удалён», «Сессии завершены»), почта аккаунта на момент действия со ссылкой на его карточку, подробности (пустые — «—»). Параметр `user` сужает журнал до одного аккаунта (ссылка «Показать все» возвращает полный). Записи MUST NOT редактироваться и удаляться через интерфейс; журнал пишется внутри той же операции, что и действие. Пустой журнал показывает «Пока ничего не происходило.».

Поверхности: admin

#### Scenario: Журнал после действий
- **WHEN** администратор заблокировал аккаунт
- **THEN** вверху журнала запись с его адресом, действием «Заблокирован» и почтой аккаунта

#### Scenario: Один аккаунт
- **WHEN** администратор переходит по ссылке «Что администраторы делали с этим аккаунтом»
- **THEN** журнал показывает только записи об этом аккаунте и ссылку «Показать все»

#### Scenario: Журнал без записей
- **WHEN** действий администраторов ещё не было
- **THEN** показано «Пока ничего не происходило.»

### Requirement: Ошибки админки
Необработанная ошибка отрисовки MUST показывать страницу «Что-то сломалось» с кнопкой «Повторить» и кодом ошибки для поиска в журналах сервиса; ошибка запроса записывается в журнал сервиса с этим кодом, а одноразовые коды, пароли, токены и cookie из журналов вычёркиваются. Несуществующий адрес вне каркаса MUST давать страницу «Страница не найдена» со ссылкой «К пользователям».

Поверхности: admin

#### Scenario: Сбой отрисовки
- **WHEN** страница админки падает при отрисовке
- **THEN** показана страница «Что-то сломалось» с кодом и кнопкой «Повторить»

#### Scenario: Несуществующий адрес
- **WHEN** открыт адрес вне разделов админки
- **THEN** показана страница «Страница не найдена» со ссылкой «К пользователям»
