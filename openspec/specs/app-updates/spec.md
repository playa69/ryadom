# app-updates

## Purpose
Нативные приложения узнают об обновлениях, спрашивая API: по номеру сборки решается, нужно ли обновить приложение через магазин (блокирующий экран или мягкое предложение), а по версии JS — можно ли без магазина подтянуть новый пакет интерфейса (OTA). Веб-клиент и PWA в этом не участвуют: у них ворот версий нет, а оболочка PWA обновляется в браузере по кнопке (см. `pwa-delivery`). Спека описывает ответ `GET /api/app-status`, ворота версий (426), раздачу `GET /api/ota/<file>`, политику релизов и то, что видит человек; сами нативные сборки описаны в `native-app-build`.

## Requirements

### Requirement: Запрос статуса версий
`GET /api/app-status` SHALL быть открыт для клиента любой версии и без авторизации. Параметры: `platform` (`android` или `ios`), `version_code` (десятичное целое от 1 до 10 цифр) и необязательный `js_version` (версия из одного–четырёх числовых сегментов по 1–6 цифр, например `1.2.3`). Отсутствующие или непригодные параметры MUST давать 400 с телом `{ "errorMessage": … }`. Успешный ответ — конверт `{ "status": true, "result": … }`, где `result` содержит `runtimeUpdate`, `latestVersionCode`, `storeUrl`, `downloadUrl`, `jsUpdate`, `jsVersion`, `jsBundleUrl` и `jsBundleChecksum`. Значения `runtimeUpdate` и `jsUpdate` — `not_available`, `available` или `required`.

Поверхности: api

#### Scenario: Статус для Android
- **WHEN** клиент запрашивает `GET /api/app-status?platform=android&version_code=12&js_version=1.2.0`
- **THEN** ответ 200 с конвертом и всеми перечисленными полями

#### Scenario: Непригодные параметры
- **WHEN** запрос содержит `platform=web`, или `version_code=abc`, или не содержит параметров вовсе
- **THEN** ответ 400 с телом `{ "errorMessage": … }`

#### Scenario: Версия ниже минимальной
- **WHEN** `version_code` ниже минимума платформы
- **THEN** маршрут всё равно отвечает 200, ворота версий его не блокируют

### Requirement: Нативная ось — минимум и последняя сборка
Поле `runtimeUpdate` SHALL принимать значение `required`, если `version_code` ниже минимального номера сборки платформы; `available`, если он не ниже минимума, но ниже последнего номера сборки платформы; иначе `not_available`. `latestVersionCode` — последний номер сборки платформы, `storeUrl` — адрес магазина платформы (или `null`), `downloadUrl` — прямая ссылка на APK только для Android (для iOS и при незаданной ссылке — `null`). Нулевой минимум MUST отключать блокировку, нулевая последняя сборка — предложение; по умолчанию оба значения равны 0.

Поверхности: api

#### Scenario: Ниже минимума
- **WHEN** для Android минимум 10, последняя 12, а клиент сообщает `version_code=9`
- **THEN** `runtimeUpdate` равен `required`

#### Scenario: Между минимумом и последней
- **WHEN** для Android минимум 10, последняя 12, а клиент сообщает `version_code=11`
- **THEN** `runtimeUpdate` равен `available`

#### Scenario: Последняя сборка
- **WHEN** для Android последняя 12, а клиент сообщает `version_code=12`
- **THEN** `runtimeUpdate` равен `not_available`

#### Scenario: Платформы независимы
- **WHEN** для iOS минимум 5, последняя 7, а клиент сообщает `platform=ios&version_code=6`
- **THEN** `runtimeUpdate` равен `available`, `latestVersionCode` равен 7, `downloadUrl` равен `null`

#### Scenario: Политика не задана
- **WHEN** минимум и последняя сборка платформы равны 0
- **THEN** любой `version_code` получает `runtimeUpdate` `not_available`

### Requirement: Откуда берётся политика релизов
Нативная ось SHALL читаться из переменных окружения процесса API: `MOBILE_ANDROID_MIN_VERSION_CODE`, `MOBILE_ANDROID_LATEST_VERSION_CODE`, `MOBILE_ANDROID_STORE_URL`, `MOBILE_ANDROID_DOWNLOAD_URL`, `MOBILE_IOS_MIN_VERSION_CODE`, `MOBILE_IOS_LATEST_VERSION_CODE`, `MOBILE_IOS_STORE_URL`; пустая строка означает «не задано», номера — неотрицательные целые, адреса — корректные URL. Ось JS SHALL браться из манифеста OTA-пакетов, запечённого в образ API: при `APP_ENV=prod` действует пакет варианта `prod`, при `APP_ENV=local` пакета нет (окружения staging нет). Минимальная версия JS SHALL читаться из переменной `MOBILE_JS_MIN_VERSION` (версия того же вида, что `js_version`; пустая строка — минимума нет). Политика MUST вычисляться один раз при старте процесса, поэтому изменение значений вступает в силу только после перезапуска; некорректное значение MUST останавливать запуск API с перечнем ошибок окружения, а отсутствующий или повреждённый манифест — только отключать ось JS, не мешая запуску.

Поверхности: api

#### Scenario: Правка номеров после релиза в магазине
- **WHEN** после публикации в магазине повышен `MOBILE_ANDROID_LATEST_VERSION_CODE` и API перезапущен
- **THEN** сборки Android ниже нового номера получают `runtimeUpdate` `available`

#### Scenario: Некорректное значение
- **WHEN** `MOBILE_ANDROID_MIN_VERSION_CODE` не целое число, `MOBILE_ANDROID_STORE_URL` не URL или `MOBILE_JS_MIN_VERSION` не версия (например, `latest`)
- **THEN** API при запуске завершается с перечнем ошибок окружения

#### Scenario: Окружение без пакета
- **WHEN** `APP_ENV=local` или манифеста пакетов в образе нет
- **THEN** ось JS отключена: `jsUpdate` равен `not_available`, `jsVersion` равен `null`, запуск не нарушен

#### Scenario: Пакет по окружению
- **WHEN** `APP_ENV=prod`
- **THEN** статус указывает на пакет варианта `prod`

#### Scenario: Минимум JS поднят после выката
- **WHEN** после выката образа с пакетом `0.1.0.42` задан `MOBILE_JS_MIN_VERSION=0.1.0.42` и API перезапущен
- **THEN** клиенты с версией JS ниже `0.1.0.42` получают `jsUpdate` `required`

### Requirement: Ворота версий отвечают 426
HTTP-запрос с допустимым `X-Platform` (`android` или `ios`) и заголовком `X-App-Version` SHALL получать ответ 426 с телом `{ "errorMessage": … }`, если номер сборки ниже минимума платформы; нечисловой номер считается нулём. Запросы без этих заголовков (веб, PWA, мониторинг), запросы с неизвестной платформой и запросы `OPTIONS` MUST NOT проверяться. `/api/app-status`, `/api/health` и `/api/ota/*` MUST оставаться открытыми для любой версии. Ответ 426 SHALL нести заголовки CORS. Устаревший JS сам по себе клиента не отрезает: отрезает только нативный минимум. Подключение WebSocket `/api/dialogs/ws` воротами не проверяется.

Поверхности: api · android · ios

#### Scenario: Сборка ниже минимума
- **WHEN** сборка Android с `X-App-Version: 9` при минимуме 10 обращается к `GET /api/auth/me`
- **THEN** ответ 426, в нём есть заголовок `Access-Control-Allow-Origin`

#### Scenario: Нет заголовков версии
- **WHEN** браузер обращается к `GET /api/auth/me` без `X-Platform` и `X-App-Version`
- **THEN** ворота пропускают запрос, дальше отвечает сам маршрут (например, 401 без токена)

#### Scenario: Открытые адреса
- **WHEN** сборка ниже минимума обращается к `/api/app-status`, `/api/health` или `/api/ota/<файл>`
- **THEN** запрос доходит до маршрута, а не получает 426

#### Scenario: Нечисловой номер
- **WHEN** заголовок `X-App-Version` не число, а минимум платформы больше нуля
- **THEN** ответ 426

#### Scenario: Минимум не задан
- **WHEN** минимум платформы равен 0
- **THEN** ни одна сборка этой платформы не получает 426

### Requirement: Решение сервера по версии JS
Поле `jsUpdate` SHALL вычисляться только если клиент передал `js_version`, для окружения есть пакет, а нативная сборка клиента способна его выполнить (минимальная нативная сборка для пакета задаётся в коде по платформе; по умолчанию ограничений нет). Версии MUST сравниваться по сегментам как числа (недостающий сегмент равен нулю, `1.0.10` новее `1.0.9`, `1.2` равна `1.2.0`): версия клиента ниже серверной даёт `required`, если задан минимум JS и версия клиента ниже него, иначе `available`; выше серверной — `required` (откат: образ с прежней версией остаётся источником правды); равная — `not_available`. `jsBundleUrl` и `jsBundleChecksum` SHALL заполняться только при `available` и `required`, иначе быть `null`; `jsVersion` — версия пакета окружения (или `null`, если пакета нет). `jsBundleUrl` MUST строиться как `PUBLIC_APP_URL` + `/api/ota/` + имя файла, закодированное для URL. Заголовок `X-Js-Version` с мусорным значением считается версией `0`. Устаревший JS сам по себе MUST NOT давать ответ 426.

Поверхности: api

#### Scenario: Клиент отстал
- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0`
- **THEN** `jsUpdate` равен `available`, а `jsBundleUrl` и `jsBundleChecksum` заполнены

#### Scenario: Клиент ниже минимума JS
- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0` и минимуме JS `1.2.0`
- **THEN** `jsUpdate` равен `required`, а `jsBundleUrl` и `jsBundleChecksum` заполнены

#### Scenario: Клиент между минимумом и пакетом
- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0` и минимуме JS `1.1.0`
- **THEN** `jsUpdate` равен `available`

#### Scenario: Минимум выше пакета
- **WHEN** минимум JS `2.0.0` выше версии пакета `1.2.0`
- **THEN** клиент с `js_version=1.1.5` получает `required`, а клиент с `js_version=1.2.0` — `not_available`

#### Scenario: Клиент новее сервера
- **WHEN** клиент с `js_version=1.3.0` запрашивает статус при версии пакета `1.2.0`
- **THEN** `jsUpdate` равен `required`

#### Scenario: Версии совпадают
- **WHEN** `js_version` равна версии пакета
- **THEN** `jsUpdate` равен `not_available`, `jsBundleUrl` и `jsBundleChecksum` равны `null`

#### Scenario: Клиент без OTA
- **WHEN** запрос не содержит `js_version`
- **THEN** `jsUpdate` равен `not_available`

#### Scenario: Сравнение сегментов числами
- **WHEN** сравниваются `1.0.10` и `1.0.9`
- **THEN** `1.0.10` считается новее

#### Scenario: Нативная сборка слишком старая для пакета
- **WHEN** для платформы задана минимальная нативная сборка для пакетов, а клиент старше этой сборки
- **THEN** `jsUpdate` равен `not_available`, `jsBundleUrl` равен `null`

#### Scenario: Устаревший JS не отрезан
- **WHEN** сборка не ниже нативного минимума с версией JS ниже минимума JS обращается к `GET /api/auth/me`
- **THEN** ворота версий пропускают запрос, ответа 426 нет

### Requirement: Раздача пакета OTA
`GET /api/ota/<file>` SHALL отдавать zip-архив только под тем именем файла, которое пакет окружения указал в статусе; для любого другого имени, а также когда пакета нет, ответ MUST быть 404 с телом `{ "errorMessage": … }`. Успешный ответ SHALL иметь `Content-Type: application/zip` и `Cache-Control: public, max-age=31536000, immutable` (имя файла содержит версию). Маршрут MUST быть открыт без авторизации и для любой версии клиента.

Поверхности: api

#### Scenario: Имя из статуса
- **WHEN** клиент запрашивает `GET /api/ota/<file>` с именем, полученным из `jsBundleUrl`
- **THEN** ответ 200 с архивом и заголовками `application/zip` и `immutable`

#### Scenario: Чужое или старое имя
- **WHEN** запрашивается имя файла прежней версии
- **THEN** ответ 404

#### Scenario: Пакета нет
- **WHEN** окружение без пакета (`APP_ENV=local` или нет манифеста) получает запрос к `/api/ota/<file>`
- **THEN** ответ 404, и даже сборка ниже минимума получает 404, а не 426

### Requirement: Сборка OTA-пакета и манифест
Сборка образа API SHALL выполнять сборку OTA-пакета: собрать JS варианта `prod`, упаковать содержимое `dist/client` в zip так, чтобы `index.html` лежал в корне архива, с прямыми слэшами в путях, назвать его `ryadom-prod-<версия>.zip`, посчитать SHA-256 архива и записать `ota/manifest.json` вида `{ "prod": { "version", "file", "checksum" } }`. Версия пакета SHALL быть `<номер версии мобильного клиента>.<OTA_BUILD_NUMBER>` (без номера — `0`), и JS внутри пакета MUST сообщать серверу ровно эту версию. `OTA_BUILD_NUMBER` MUST быть целым числом из 1–6 цифр, иначе сборка прерывается. Адреса `VITE_PROD_API_URL` и `VITE_PROD_WEB_URL` передаются в сборку образа аргументами и вшиваются в пакет; каталог `ota` MUST копироваться в образ API рядом с серверным бандлом. Пакет уезжает тем же деплоем, что и сервер, отдельного шага публикации нет. Пакет варианта `dev` не собирается и не раздаётся.

Поверхности: api · android · ios

#### Scenario: Сборка с номером
- **WHEN** образ собирается при версии `0.1.0` и `OTA_BUILD_NUMBER=42`
- **THEN** создаётся `ryadom-prod-0.1.0.42.zip`, а в манифесте его `version` равна `0.1.0.42`

#### Scenario: Сборка без номера
- **WHEN** `OTA_BUILD_NUMBER` не задан
- **THEN** версия пакета равна `0.1.0.0`

#### Scenario: Пакет сообщает свою версию
- **WHEN** устройство применило пакет `0.1.0.42` и запрашивает статус
- **THEN** запрос содержит `js_version=0.1.0.42`, и сервер с тем же пакетом отвечает `jsUpdate` `not_available`

#### Scenario: Неверный номер сборки
- **WHEN** `OTA_BUILD_NUMBER` равен `abc` или содержит больше шести цифр
- **THEN** сборка прерывается, манифест не записывается

#### Scenario: Состав архива
- **WHEN** архив распакован
- **THEN** `index.html` лежит в его корне

#### Scenario: Ошибка шага сборки
- **WHEN** сборка JS или упаковка завершается ошибкой
- **THEN** сборка образа прерывается, манифест не записывается

### Requirement: Нативное приложение сообщает версии в заголовках
Нативное приложение SHALL добавлять к каждому запросу к API (включая обновление токена и выход) заголовки `X-Platform` (`android` или `ios`), `X-App-Version` (номер сборки) и, только если сборка на канале OTA, `X-Js-Version` — версию работающего JS: `<номер версии мобильного клиента>.<OTA_BUILD_NUMBER на момент сборки JS>` (без номера — `0`); у применённого пакета OTA это его версия из манифеста, у JS, встроенного в нативную сборку, — номер, с которым собирался её JS. Если номер сборки прочитать не удалось, заголовки MUST NOT добавляться. Браузер (веб-клиент, PWA, Telegram Mini App) MUST NOT отправлять эти заголовки.

Нативная сборка участвует в OTA (отправляет `X-Js-Version` и параметр `js_version`) только если это вариант `prod`: пакет собирается только для него. Вариант `dev`, направленный на `prod` или `local`, MUST NOT отправлять версию JS и получать чужой пакет, иначе чужой минимум мог бы его заблокировать.

Поверхности: android · ios

#### Scenario: Запрос из боевой сборки
- **WHEN** (Android) боевая сборка обращается к API
- **THEN** запрос содержит `X-Platform: android`, `X-App-Version` и `X-Js-Version`

#### Scenario: Версия применённого пакета
- **WHEN** (Android) на устройстве работает пакет `0.1.0.42`
- **THEN** запросы к API несут `X-Js-Version: 0.1.0.42`, а запрос статуса — `js_version=0.1.0.42`

#### Scenario: Встроенный JS без номера сборки
- **WHEN** (Android) JS нативной сборки собран при версии `0.1.0` без `OTA_BUILD_NUMBER`
- **THEN** сборка сообщает `X-Js-Version: 0.1.0.0` и получает любой пакет `0.1.0.N` с N больше нуля

#### Scenario: Dev-сборка на prod
- **WHEN** (Android) сборка варианта `dev` переключена на среду `prod`
- **THEN** запросы статуса и API идут без версии JS, и пакет не предлагается

#### Scenario: Номер сборки недоступен
- **WHEN** нативное приложение не смогло прочитать номер сборки
- **THEN** запросы уходят без заголовков версий

### Requirement: Когда клиент проверяет статус версий
Нативное приложение SHALL запрашивать `GET /api/app-status` (без авторизации и без заголовков версий; платформа и номер сборки — в параметрах, `js_version` — если сборка на канале OTA) при запуске, при возврате на передний план, при появлении сети после потери и при ответе 426 на запрос клиента (кроме запроса выхода: его ответ клиент не разбирает, выход всё равно завершается на устройстве). Проверки при возврате и при появлении сети MUST выполняться не чаще раза в минуту (60 с от последней успешной проверки), запуск и ответ 426 — всегда; одновременные проверки MUST объединяться в одну. Сбой запроса (нет сети, ответ не 2xx, неожиданный формат тела) MUST оставлять экран без изменений: при ответе не 2xx и неожиданном формате ошибка пишется в консоль, повтор — по следующему поводу. Если номер сборки прочитать не удалось, проверка MUST NOT выполняться. Веб-клиент, PWA и Mini App статус не запрашивают.

Поверхности: android · ios

#### Scenario: Запуск
- **WHEN** нативное приложение запускается
- **THEN** выполняется проверка статуса, независимо от времени последней проверки

#### Scenario: Частое возвращение в приложение
- **WHEN** человек возвращается в приложение чаще раза в минуту после успешной проверки
- **THEN** повторного запроса статуса нет

#### Scenario: Ответ 426 на любой запрос
- **WHEN** запрос клиента к API (кроме запроса выхода) вернул 426
- **THEN** выполняется проверка статуса, даже если с прошлой прошло меньше минуты

#### Scenario: Сеть вернулась
- **WHEN** после потери сети она появилась и с последней успешной проверки прошло больше минуты
- **THEN** выполняется проверка статуса

#### Scenario: Сбой проверки
- **WHEN** запрос статуса вернул 500 или тело неожиданного формата
- **THEN** человек ничего не видит, в консоль пишется ошибка, следующая проверка пройдёт по следующему поводу

#### Scenario: Неизвестное значение
- **WHEN** `runtimeUpdate` или `jsUpdate` в ответе имеет значение вне допустимых
- **THEN** клиент не показывает ни блокировку, ни баннер, в консоль пишется ошибка

### Requirement: Блокирующий экран обновления приложения
Если статус содержит `runtimeUpdate` `required`, нативное приложение SHALL показать поверх всего экран с заголовком «Пора обновить «Рядом»» и пояснением «Вышла новая версия «Рядом», и эта больше не подойдёт. Установи её — это займёт минуту. Входить заново не придётся: всё останется на месте.», который нельзя закрыть; кнопка «Назад» на Android MUST сворачивать приложение. Экран SHALL предлагать «Обновить в магазине», если есть `storeUrl`, и «Скачать напрямую», если есть `downloadUrl`; если нет ни одного адреса, он MUST предлагать «Открыть страницу загрузки» (адрес сайта + `/download`). Обновление JS в этом случае MUST NOT применяться. Сессия человека MUST сохраняться: ответ 426 не завершает вход, поэтому после обновления входить заново не нужно.

Поверхности: android · ios

#### Scenario: Понятный текст
- **WHEN** статус содержит `required`
- **THEN** на экране заголовок «Пора обновить «Рядом»» и пояснение без слов «сервер» и «версия API», с обещанием, что входить заново не придётся

#### Scenario: Есть магазин и прямая ссылка
- **WHEN** статус содержит `required`, `storeUrl` и `downloadUrl`
- **THEN** на экране две кнопки: «Обновить в магазине» и «Скачать напрямую»

#### Scenario: Адресов нет
- **WHEN** статус содержит `required`, а `storeUrl` и `downloadUrl` равны `null`
- **THEN** на экране одна кнопка «Открыть страницу загрузки», ведущая на `/download` сайта

#### Scenario: Кнопка «Назад»
- **WHEN** (Android) человек нажимает «Назад» на этом экране
- **THEN** приложение сворачивается, экран остаётся

#### Scenario: Сессия после 426
- **WHEN** обновление токена вернуло 426
- **THEN** токены не стираются, и после установки новой сборки человек остаётся в аккаунте

#### Scenario: Проверка статуса не удалась
- **WHEN** запрос статуса после ответа 426 завершился ошибкой
- **THEN** экран не показывается, запросы к API продолжают получать 426, а проверка повторится по следующему поводу

### Requirement: Мягкое предложение обновить приложение
Если статус содержит `runtimeUpdate` `available`, нативное приложение SHALL показать закрываемый баннер «Вышла новая версия» с кнопкой «Обновить», которая открывает `storeUrl`, а если его нет — `downloadUrl`, а если нет и его — адрес сайта + `/download`. Кнопка закрытия (доступное имя «Скрыть») MUST запоминать `latestVersionCode` в локальном хранилище (`ryadom.update.dismissedVersionCode`): для того же номера баннер больше не показывается, для более нового — показывается снова. Если хранилище недоступно, баннер MAY показываться снова. Статус `not_available` MUST убирать баннер. Показ, закрытие и применение обновлений учитываются в аналитике без текстов (см. `product-analytics`).

Поверхности: android · ios

#### Scenario: Вышла новая версия
- **WHEN** статус содержит `available` и `storeUrl`
- **THEN** показывается баннер, «Обновить» открывает магазин

#### Scenario: Закрыли баннер
- **WHEN** человек закрывает баннер при `latestVersionCode` 12 и приложение перезапускается
- **THEN** при том же `latestVersionCode` баннера нет

#### Scenario: Вышла ещё более новая версия
- **WHEN** после закрытия баннера последняя сборка платформы выросла с 12 до 13
- **THEN** баннер показывается снова

#### Scenario: Старая сборка выше минимума
- **WHEN** сборка старше последней, но не ниже минимума, обращается к API
- **THEN** она получает ответы без 426, а предложение обновиться для неё мягкое (баннер)

### Requirement: Применение пакета OTA на устройстве
Если `jsUpdate` равен `required` и есть `jsBundleUrl`, нативное приложение SHALL показать экран «Обновляемся — это пара секунд», скачать пакет (если пакет этой версии уже скачан, использовать его), передав плагину контрольную сумму, и применить его перезапуском WebView; при ошибке экран MUST убираться, человека не блокировать, повтор — по следующему поводу проверки. Если `jsUpdate` равен `available` и есть `jsBundleUrl`, приложение SHALL тихо скачать пакет и назначить его на следующий запуск, не повторяя загрузку для уже назначенной версии (`ryadom.update.nextJsVersion`); при ошибке загрузка повторяется при следующей проверке. При первом запуске после установки новой нативной сборки (в хранилище уже есть номер прежней сборки, и он отличается от текущего; при чистой установке номера нет) `available` MUST обрабатываться как `required`. `required` без `jsBundleUrl` MUST игнорироваться. Блокирующее обновление нативной сборки приоритетнее обновления JS.

Поверхности: android · ios

#### Scenario: Обязательное применение
- **WHEN** статус содержит `jsUpdate` `required` и `jsBundleUrl`
- **THEN** показывается экран обновления, пакет скачивается и применяется, WebView перезапускается

#### Scenario: Скачивание не удалось
- **WHEN** при `required` загрузка пакета завершилась ошибкой
- **THEN** экран обновления исчезает, человек продолжает работу, повтор будет при следующей проверке

#### Scenario: Тихая загрузка
- **WHEN** статус содержит `jsUpdate` `available`
- **THEN** пакет скачивается в фоне без экранов и применяется при следующем запуске приложения

#### Scenario: Версия уже скачана
- **WHEN** пакет этой версии уже назначен на следующий запуск
- **THEN** новая загрузка не начинается

#### Scenario: Первый запуск после обновления из магазина
- **WHEN** приложение впервые запускается после установки новой нативной сборки и статус содержит `available`
- **THEN** пакет применяется немедленно, как при `required`

#### Scenario: Обязательное обновление без адреса
- **WHEN** статус содержит `jsUpdate` `required`, а `jsBundleUrl` равен `null`
- **THEN** обновление JS не выполняется

### Requirement: Целостность и откат пакета на устройстве
Нативное приложение SHALL передавать плагину обновлений SHA-256 архива из `jsBundleChecksum`: архив, не совпавший с суммой, плагин отвергает, и загрузка считается неудачной. При каждом запуске нативной сборки приложение MUST вызывать `notifyAppReady`, подтверждая, что интерфейс стартовал; если подтверждения нет, плагин возвращает предыдущий пакет. Сбой этого вызова MUST фиксироваться в консоли.

Поверхности: android · ios

#### Scenario: Подменённый архив
- **WHEN** скачанный архив не совпадает с `jsBundleChecksum`
- **THEN** загрузка считается неудачной, пакет не применяется

#### Scenario: Пакет не запустился
- **WHEN** после применения пакета интерфейс не дошёл до старта и `notifyAppReady` не вызван
- **THEN** плагин возвращает предыдущий пакет

#### Scenario: Откат образа на сервере
- **WHEN** на сервере задеплоен образ с более старой версией пакета, чем версия JS, которую сообщает устройство
- **THEN** сервер отвечает `jsUpdate` `required`

### Requirement: Ворота версий и OTA не действуют в вебе, PWA и Mini App
Веб-клиент (`/app`), PWA и Telegram Mini App SHALL работать без ворот версий: они не отправляют `X-Platform` и `X-App-Version`, поэтому не получают 426, не запрашивают `/api/app-status` и не получают OTA-пакеты. Оболочка PWA обновляется только service worker по кнопке (см. `pwa-delivery`). PWA и веб-клиент выкатываются отдельными образами, независимо от API, поэтому API MUST оставаться совместимым с их предыдущими сборками: контракт меняется добавлением полей, неизвестные поля клиенты игнорируют. Нативные сборки живут месяцами, поэтому сервер MUST отрезать старую сборку только по нативному минимуму.

Поверхности: web · pwa · tg · api

#### Scenario: PWA при высоком минимуме
- **WHEN** (PWA) минимум нативной платформы поднят, а человек работает в PWA
- **THEN** запросы PWA не получают 426 и экран обновления не показывается

#### Scenario: Запуск PWA
- **WHEN** (PWA) PWA запускается в браузере
- **THEN** запрос `/api/app-status` не отправляется, регистрируется только service worker

#### Scenario: Веб-клиент
- **WHEN** (Web) человек работает в веб-клиенте
- **THEN** экрана «Пора обновить «Рядом»» и баннера новой версии нет

#### Scenario: Новое поле в ответе
- **WHEN** сервер добавляет в ответ `app-status` новое поле
- **THEN** сборки, не знающие о нём, продолжают работать, поле игнорируется
