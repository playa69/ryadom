# native-app-build

## Purpose
Мобильный клиент выпускается и как нативные приложения Android и iOS на Capacitor: тот же JS-код работает в WebView, собирается отдельно под вариант `dev` или `prod`. Спека фиксирует идентификаторы, конфигурацию оболочки, источники адресов API и номеров версий, нативные возможности и разрешения, артефакты и подпись — для тех, кто выпускает версии и обслуживает магазины. Как нативные сборки узнают об обновлениях — в `app-updates`; экраны и навигация — в `app-shell`. Конвейер релизов (теги, секреты подписи, нумерация запусков) в этом репозитории не хранится и здесь не описывается.

## Requirements

### Requirement: Идентификатор и имя приложения
Приложение SHALL иметь идентификатор `ru.ryadom.app`: он же `appId` Capacitor, `applicationId` и Java-пакет (`namespace`) Android и `PRODUCT_BUNDLE_IDENTIFIER` iOS. Отображаемое имя — «Рядом» (Android: `app_name` варианта `prod`; iOS: `CFBundleDisplayName`). Вариант `dev` на Android SHALL иметь `applicationId` `ru.ryadom.app.dev`, суффикс версии `-dev` и имя «Рядом dev», чтобы ставиться рядом с боевым; на iOS отдельного идентификатора для `dev` нет. Идентификатор MUST NOT меняться после первой публикации в магазине.

Поверхности: android · ios

#### Scenario: Боевая сборка Android
- **WHEN** (Android) собирается вариант `prod`
- **THEN** `applicationId` равен `ru.ryadom.app`, имя под иконкой — «Рядом»

#### Scenario: Dev-сборка рядом с боевой
- **WHEN** (Android) на телефон, где стоит боевое приложение, ставится вариант `dev`
- **THEN** он устанавливается как отдельное приложение `ru.ryadom.app.dev` с именем «Рядом dev»

#### Scenario: iOS
- **WHEN** (iOS) собирается приложение
- **THEN** `PRODUCT_BUNDLE_IDENTIFIER` равен `ru.ryadom.app`, имя на домашнем экране — «Рядом»

### Requirement: Порядок нативной сборки
Нативная сборка SHALL состоять из трёх шагов: сборка JS клиента для нужного варианта (режим `dev` или `prod`, результат в `dist/client`), `cap sync <android|ios>`, который копирует `dist/client` в нативный проект, и компиляция нативной части. JS MUST собираться под синтаксис не новее ES2020, чтобы работать и в старых версиях системного WebView. Для разработки `pnpm android:dev` SHALL выполнять эти шаги с вариантом `dev`, собирать отладочный APK `app-dev-debug.apk`, ставить его по `adb` и запускать `ru.ryadom.app.dev/ru.ryadom.app.MainActivity`.

Поверхности: android · ios

#### Scenario: Локальная dev-сборка Android
- **WHEN** (Android) выполняется `pnpm android:dev`
- **THEN** собирается JS в режиме `dev`, затем `cap sync android`, затем `assembleDevDebug`, установка по `adb` и запуск

#### Scenario: Целевой синтаксис
- **WHEN** собирается JS для нативной сборки
- **THEN** результат не использует синтаксис новее ES2020

### Requirement: Вариант сборки обязателен и определяет среду
Для нативной сборки JS переменная `VITE_FLAVOR` SHALL быть равна `dev` или `prod`; иначе сборка MUST завершаться ошибкой с указанием режима `dev` или `prod`. Вариант `prod` MUST всегда указывать на адреса `prod`, а код переключателя сред MUST отсутствовать в его бандле. Вариант `dev` по умолчанию SHALL указывать на среду `local` (на нативном клиенте — `http://10.0.2.2:3002`, адрес хост-машины из эмулятора Android; сайт — `http://10.0.2.2:3000`). Варианты Gradle `dev` и `prod` (измерение `environment`) соответствуют этим двум вариантам JS. Адреса `prod` SHALL фиксироваться при сборке JS из `VITE_PROD_API_URL` и `VITE_PROD_WEB_URL` (значение из окружения процесса приоритетнее файла `.env.<режим>`, завершающие `/` отбрасываются); если одна из них пуста, сборка продолжается с предупреждением, что среда `prod` в ней не работает. Нативное приложение MUST NOT получать эти адреса во время работы (кроме выбора среды в `dev`-сборке).

Поверхности: android · ios

#### Scenario: Вариант не задан
- **WHEN** нативный JS собирается без `VITE_FLAVOR` или с другим значением
- **THEN** сборка завершается ошибкой «VITE_FLAVOR must be "dev" or "prod"»

#### Scenario: Боевой вариант
- **WHEN** запущено приложение, собранное в варианте `prod`
- **THEN** оно работает только с адресами `prod`, выбрать другую среду нельзя

#### Scenario: Dev-вариант
- **WHEN** собран вариант `dev` и человек ещё не менял среду
- **THEN** приложение стартует в среде `local`

#### Scenario: Адреса не заданы
- **WHEN** нативный JS собирается без `VITE_PROD_API_URL` или `VITE_PROD_WEB_URL`
- **THEN** сборка не падает, выводится предупреждение, что среда `prod` в этой сборке не работает

#### Scenario: Переменная процесса и файл
- **WHEN** `VITE_PROD_API_URL` задана и в окружении процесса, и в `.env.<режим>`
- **THEN** используется значение из окружения процесса

### Requirement: Переключатель сред только в dev-сборке
В варианте `dev` семь быстрых нажатий подряд (пауза между нажатиями не больше 1,5 с) на знак «Рядом» экрана входа или первого экрана либо на номер версии в профиле SHALL открывать выбор среды: пункты «Local — <адрес>» и «Prod — <адрес>», текущая выделена, пункт, адрес которого не вшит в сборку, MUST быть недоступен. Для `Local` запрашивается адрес сервера (пусто — адрес по умолчанию). Выбор SHALL сохраняться между запусками (неизвестное сохранённое значение читается как `local`); переключение MUST выводить человека из аккаунта (токены выданы другим сервером) и перезагружать WebView. В профиле dev-сборки есть строка «Среда» с названием текущей. В публичных сборках (PWA, магазинные `prod`) переключателя MUST NOT быть, нажатия ничего не делают, строки «Среда» нет.

Поверхности: android · ios

#### Scenario: Переключение на prod
- **WHEN** (Android) в `dev`-сборке человек семь раз быстро нажимает на знак и выбирает «Prod»
- **THEN** он выходит из аккаунта, WebView перезагружается и приложение работает с `prod`, а после перезапуска выбор сохранён

#### Scenario: Медленные нажатия
- **WHEN** паузы между нажатиями больше 1,5 с
- **THEN** счёт начинается заново и выбор среды не открывается

#### Scenario: Среда без вшитого адреса
- **WHEN** в `dev`-сборке не вшит адрес `prod`
- **THEN** пункт «Prod» недоступен, подпись «адрес не задан в сборке»

#### Scenario: Боевая сборка
- **WHEN** в варианте `prod` человек семь раз нажимает на знак или номер версии
- **THEN** ничего не происходит

### Requirement: Конфигурация нативной оболочки Capacitor
Оболочка SHALL быть настроена так: `webDir` — `dist/client`; схема Android — `https` (страница открывается с origin `https://localhost`); фон оболочки и заставки — `#00051a`; заставка показывается 500 мс, скрывается автоматически и без индикатора; значки системных панелей светлые (`DARK`) независимо от системной темы; отступы системных панелей передаются в CSS, а WebView выходит под них; клавиатура меняет размер окна нативно (`resize: native`). Плагин обновлений `CapacitorUpdater` SHALL работать с `autoUpdate: false` и пустым `statsUrl`: обновлениями управляет собственный механизм приложения (см. `app-updates`), а события и ошибки в облако плагина не отправляются. `server.url` и `cleartext` SHALL добавляться в генерируемую конфигурацию только когда при `cap sync` задана переменная `CAP_LIVE_RELOAD_URL`: HTTP-адрес в релизе означал бы отказ магазина и возможность подмены приложения в открытой сети. `pnpm android:dev` MUST удалять эту переменную из окружения, а `pnpm android:live` SHALL задавать её (по умолчанию `http://10.0.2.2:5174`).

Поверхности: android · ios

#### Scenario: Релизная синхронизация
- **WHEN** выполняется `cap sync` без `CAP_LIVE_RELOAD_URL`
- **THEN** сгенерированная конфигурация содержит `androidScheme: 'https'`, `webDir: 'dist/client'` и настройки плагинов, но не `server.url` и `cleartext`

#### Scenario: Облако плагина обновлений
- **WHEN** приложение запущено с плагином `CapacitorUpdater`
- **THEN** он не скачивает обновления сам и не шлёт статистику

#### Scenario: Работа с dev-сервером
- **WHEN** (Android) выполняется `pnpm android:live`
- **THEN** WebView загружает адрес из `CAP_LIVE_RELOAD_URL`, и правки видны без пересборки

#### Scenario: Dev-сборка после live-запуска
- **WHEN** после `pnpm android:live` выполняется `pnpm android:dev`
- **THEN** переменная удалена из окружения, APK не наследует адрес dev-сервера

### Requirement: Нативные возможности клиента
Нативная сборка SHALL использовать плагины Capacitor: защищённое хранилище платформы (Android Keystore, iOS Keychain) для токена продления сессии и ключа устройства для входа без регистрации; хранилище настроек для записи о человеке (чтобы экран не был пустым без сети); приложение (номер сборки, состояние, аппаратная кнопка «назад»); браузер (внешние ссылки открываются в Custom Tabs); панели статуса и заставку; клавиатуру; обновления пакетов интерфейса. Токен продления и ключ устройства MUST NOT храниться в открытых настройках. Приложение сообщает API номер сборки (Android `versionCode`, iOS номер сборки) целым числом; если прочитать его не удалось, проверки версий не выполняются (см. `app-updates`).

Поверхности: android · ios

#### Scenario: Токены
- **WHEN** человек входит в аккаунт в нативной сборке
- **THEN** токен продления лежит в защищённом хранилище платформы, а в настройках — только запись о человеке

#### Scenario: Внешняя ссылка
- **WHEN** человек открывает «Условия использования» из профиля
- **THEN** документ открывается в Custom Tabs, а не внутри WebView приложения

### Requirement: Разрешения и платформенные параметры
Android-приложение SHALL запрашивать только разрешения `INTERNET`, `RECORD_AUDIO` и `ACCESS_NETWORK_STATE`; наличие микрофона MUST NOT быть обязательным для установки (`required="false"`: разговор можно вести текстом); `CALL_PHONE` MUST NOT запрашиваться, потому что кнопка SOS и номера линий помощи только набирают номер, звонок начинает человек. Минимальная версия Android — API 24, целевая и компилируемая — API 36. iOS-приложение SHALL содержать пояснение для микрофона («Микрофон нужен, чтобы вы могли говорить вслух. Запись не сохраняется: речь распознаётся в момент разговора.»), поддерживать iOS 15.0 и новее, всегда использовать тёмный стиль интерфейса, объявлять `ITSAppUsesNonExemptEncryption` равным `false` и поддерживать на iPhone только портретную ориентацию (на iPad — портретную и перевёрнутую портретную). Android-приложение MUST NOT попадать в резервные копии и переносы на новый телефон: `allowBackup` равен `false`, а правила извлечения данных исключают из облачного бэкапа и из переноса все домены (`root`, `file`, `database`, `sharedpref`, `external`), потому что в хранилище лежат токены сессии и ключ устройства.

Поверхности: android · ios

#### Scenario: Телефон без микрофона
- **WHEN** (Android) приложение ставится на устройство без микрофона
- **THEN** установка не блокируется

#### Scenario: SOS
- **WHEN** (Android) человек нажимает на номер линии помощи
- **THEN** набирается номер без разрешения `CALL_PHONE`, звонок начинает человек

#### Scenario: Первый запрос микрофона на iOS
- **WHEN** (iOS) система впервые запрашивает доступ к микрофону
- **THEN** показывается пояснение из `NSMicrophoneUsageDescription`

#### Scenario: Перенос на новый телефон
- **WHEN** (Android) человек переносит данные со старого телефона на новый
- **THEN** данные приложения не переносятся, на новом телефоне нужно войти заново

### Requirement: Версии нативной сборки
Android SHALL брать `versionCode` из переменной `RYADOM_VERSION_CODE` (без неё — `1`) и `versionName` из `RYADOM_VERSION_NAME` (без неё — `0.1.0`); вариант `dev` добавляет к `versionName` суффикс `-dev`. iOS SHALL брать версию из `MARKETING_VERSION` (в проекте `1.0`, `CFBundleShortVersionString`) и номер сборки из `CURRENT_PROJECT_VERSION` (в проекте `1`, `CFBundleVersion`). Номер сборки MUST расти с каждым выпуском, потому что ворота версий сравнивают его как число (см. `app-updates`).

Поверхности: android · ios

#### Scenario: Локальная сборка без переменных
- **WHEN** (Android) собирается без `RYADOM_VERSION_CODE` и `RYADOM_VERSION_NAME`
- **THEN** `versionCode` равен `1`, `versionName` — `0.1.0` (для `dev` — `0.1.0-dev`)

#### Scenario: Сборка с переменными
- **WHEN** (Android) заданы `RYADOM_VERSION_CODE=57` и `RYADOM_VERSION_NAME=0.1.0`
- **THEN** вариант `prod` получает `versionCode` 57 и `versionName` `0.1.0`

#### Scenario: Номер iOS
- **WHEN** (iOS) архив собирается с `CURRENT_PROJECT_VERSION=57`
- **THEN** `CFBundleVersion` равен `57`, и приложение сообщает API номер сборки 57

### Requirement: Артефакты и подпись
Android-сборка SHALL производить для каждого варианта релизный APK (`assemble<Вариант>Release`) или AAB (`bundle<Вариант>Release`) без минификации кода; AAB предназначен для магазинов, APK — для установки напрямую. Android SHALL подписывать релиз, когда задан `RYADOM_KEYSTORE_PATH`, с входными данными `RYADOM_KEYSTORE_PASSWORD`, `RYADOM_KEY_ALIAS` и `RYADOM_KEY_PASSWORD`; без пути к хранилищу ключей релиз MUST собираться неподписанным, а не падать. Файлы ключей (`*.keystore`, `*.jks`, `keystore.properties` в каталоге Android-проекта) MUST NOT попадать в систему контроля версий. iOS-сборка SHALL архивировать схему `App` в конфигурации Release и экспортировать IPA для App Store Connect (`method` — `app-store-connect`, `uploadSymbols` — `true`) с ручной подписью (`signingStyle` — `manual`), для которой нужны идентификатор команды разработчика (`DEVELOPMENT_TEAM`), сертификат распространения и provisioning profile.

Поверхности: android · ios

#### Scenario: AAB для магазина
- **WHEN** (Android) выпускается вариант `prod` в формате AAB
- **THEN** выполняется `bundleProdRelease`, результат — AAB

#### Scenario: APK для установки напрямую
- **WHEN** (Android) выпускается вариант `dev` в формате APK
- **THEN** выполняется `assembleDevRelease`, результат — APK

#### Scenario: Релиз с ключом
- **WHEN** (Android) релиз собирается с `RYADOM_KEYSTORE_PATH` и остальными входными данными
- **THEN** артефакт подписан этим ключом

#### Scenario: Релиз без ключа
- **WHEN** (Android) релиз собирается без `RYADOM_KEYSTORE_PATH`
- **THEN** сборка завершается успешно, артефакт не подписан

#### Scenario: IPA
- **WHEN** (iOS) выпускается сборка
- **THEN** результат — IPA, экспортированный для App Store Connect

### Requirement: Каналы выпуска
Android-сборка SHALL распространяться через магазины (RuStore, Google Play) и/или по прямой ссылке на APK, iOS — через App Store; каждый канал MUST быть необязательным и задаваться адресом. Для окна обновления API отдаёт адрес магазина платформы (`MOBILE_ANDROID_STORE_URL`, `MOBILE_IOS_STORE_URL`) и прямую ссылку на APK только для Android (`MOBILE_ANDROID_DOWNLOAD_URL`); страница загрузки сайта показывает кнопки по адресам `PUBLIC_RUSTORE_URL`, `PUBLIC_GOOGLE_PLAY_URL`, `PUBLIC_ANDROID_APK_URL`, `PUBLIC_APP_STORE_URL`, а незаданный адрес скрывает кнопку (см. `app-updates` и `landing-site`).

Поверхности: android · ios · api · landing

#### Scenario: Задан только магазин
- **WHEN** (Android) `MOBILE_ANDROID_DOWNLOAD_URL` пуст, а `MOBILE_ANDROID_STORE_URL` задан
- **THEN** API отдаёт `downloadUrl: null`, и окно обновления предлагает только магазин

#### Scenario: iOS
- **WHEN** (iOS) приложение запрашивает статус версий как iOS
- **THEN** `downloadUrl` равен `null`: прямой ссылки для iOS нет

#### Scenario: Канал не настроен
- **WHEN** адрес канала не задан
- **THEN** соответствующая кнопка на странице загрузки не показывается
