# pwa-delivery

## Purpose
Мобильный клиент открывается в браузере как PWA: оболочку, манифест и service worker раздаёт отдельный контейнер `app-pwa` (nginx) на том же хосте, что и API, под путём `/pwa/`; клиент предлагает поставить приложение на домашний экран, открывается без сети и обновляется по кнопке. Спека описывает, что раздаётся, под каким адресом, как кэшируется и обновляется и как предлагается установка. Индикатор офлайна и экраны — в `app-shell`, нативные обновления — в `app-updates`, запуск внутри Telegram — в `telegram-mini-app`, карточка установки на сайте — в `landing-site`.

## Requirements

### Requirement: Раздача PWA отдельным контейнером
PWA (браузерная сборка мобильного клиента) SHALL раздаваться отдельным контейнером `app-pwa`: статические файлы сборки отдаёт nginx. Процесс API MUST NOT раздавать клиент (ни файлы, ни оболочку): он отвечает только за `/api/*`, а его образ содержит лишь OTA-пакеты нативных сборок (см. `app-updates`). На общем хосте продукта пути распределяются так: `/` — сайт, `/api` — API (REST, WebSocket, OTA), `/app` — веб-клиент, `/pwa` — PWA, `/admin` — админка; запросы `/api/*` с PWA MUST доходить до API, а не до контейнера PWA.

Поверхности: pwa

#### Scenario: Контейнер с PWA
- **WHEN** контейнер `app-pwa` запущен с верными настройками
- **THEN** nginx отдаёт файлы веб-сборки мобильного клиента, процесс API для этого не нужен

#### Scenario: API не раздаёт клиент
- **WHEN** к процессу API приходит `GET /` или `GET /pwa/`
- **THEN** оболочка не отдаётся: ответ 404 с телом `{ "errorMessage": … }`, как для любого адреса без маршрута

#### Scenario: Запрос данных из PWA
- **WHEN** PWA, открытая по `https://<хост>/pwa/`, выполняет fetch к `/api/dialogs`
- **THEN** запрос уходит на `https://<хост>/api/dialogs` — тот же origin, без CORS — и его обслуживает API

#### Scenario: Разговор по WebSocket
- **WHEN** PWA открывает разговор на странице `https://<хост>/pwa/`
- **THEN** WebSocket подключается к `wss://<хост>/api/dialogs/ws`: схема и хост берутся из адреса страницы

### Requirement: Префикс адреса задаётся при сборке образа
Путь, под которым PWA опубликована на хосте (префикс), SHALL задаваться при сборке образа аргументом `PWA_BASE_PATH` и MUST NOT меняться при запуске контейнера: он записывается в адреса всех файлов сборки, область service worker и манифеста и в конфигурацию nginx. Значение — пустое (PWA владеет всем хостом) или вида `/pwa`: косая черта в начале, без завершающей, сегменты из латинских букв, цифр, `_` и `-`; любое другое значение MUST прерывать сборку образа. В продукте префикс — `/pwa`.

Поверхности: pwa

#### Scenario: Образ для общего хоста
- **WHEN** образ собран с `PWA_BASE_PATH=/pwa`
- **THEN** файлы открываются под `/pwa/`, адреса файлов в `index.html` начинаются с `/pwa/`, область service worker и манифеста — `/pwa/`

#### Scenario: Образ для собственного хоста
- **WHEN** образ собран без `PWA_BASE_PATH`
- **THEN** PWA открывается с корня хоста `/`, перенаправлений на префикс нет, область service worker и манифеста — `/`

#### Scenario: Некорректный префикс
- **WHEN** образ собирается с `PWA_BASE_PATH=/pwa/` или `pwa`
- **THEN** сборка завершается ошибкой с пояснением, а не откладывается до запуска контейнера

#### Scenario: Смена префикса
- **WHEN** PWA нужно опубликовать под другим путём
- **THEN** собирается новый образ: переменной окружения запуска, меняющей префикс, нет

### Requirement: Перенаправления и пути вне префикса
При непустом префиксе контейнер SHALL отвечать: `GET /pwa` — 301 на `/pwa/`; `GET /` — 302 на `/pwa/`; любой другой путь вне префикса, кроме проверки живости, — 404 обычной страницей nginx (не JSON формата API). Строка запроса при перенаправлениях MUST сохраняться, а заголовок `Location` MUST быть относительным (без схемы и хоста): за шлюзом, завершающим TLS, абсолютный адрес содержал бы внутренние схему и порт. При пустом префиксе этих правил нет: все пути принадлежат PWA.

Поверхности: pwa

#### Scenario: Адрес без завершающей косой черты
- **WHEN** приходит `GET /pwa?from=landing`
- **THEN** ответ 301 с `Location: /pwa/?from=landing`

#### Scenario: Корень хоста
- **WHEN** к контейнеру приходит `GET /` (при префиксе `/pwa`)
- **THEN** ответ 302 с `Location: /pwa/`

#### Scenario: Чужой путь
- **WHEN** к контейнеру приходит `GET /journal/` или `GET /other.js` (при префиксе `/pwa`)
- **THEN** ответ 404 обычной страницей nginx, оболочка не отдаётся

#### Scenario: Пустой префикс
- **WHEN** образ собран без префикса и приходит `GET /journal/`
- **THEN** отдаётся оболочка со статусом 200, а не 404

### Requirement: Оболочка для маршрутов приложения
Под префиксом на запрос контейнер SHALL отдавать файл сборки, если он есть, а иначе оболочку (`index.html` с метатегом адреса сайта) со статусом 200, `Content-Type: text/html; charset=utf-8` и `Cache-Control: no-cache`; дальше маршрут разбирает клиент. Исключение: отсутствующий файл под `<префикс>/assets/` MUST давать настоящий 404, а не оболочку, чтобы устаревшая оболочка не получала HTML вместо скрипта или стиля. Перенаправлений на адрес с косой чертой в конце контейнер не делает.

Поверхности: pwa

#### Scenario: Корень приложения
- **WHEN** браузер запрашивает `GET /pwa/`
- **THEN** приходит оболочка, статус 200, `Cache-Control: no-cache`

#### Scenario: Глубокая ссылка на экран приложения
- **WHEN** браузер запрашивает `GET /pwa/dialog/d-1/`, а такого файла в сборке нет
- **THEN** приходит та же оболочка со статусом 200, и клиент сам открывает нужный экран

#### Scenario: Неизвестный путь под префиксом
- **WHEN** браузер запрашивает `GET /pwa/no-such-file.js`, которого нет в сборке и который лежит не в `assets/`
- **THEN** приходит оболочка со статусом 200

#### Scenario: Файл сборки
- **WHEN** браузер запрашивает файл, который есть в сборке (например, `/pwa/manifest.webmanifest`)
- **THEN** приходит сам файл, а не оболочка

#### Scenario: Отсутствующий файл в assets
- **WHEN** браузер запрашивает `GET /pwa/assets/index-старый-хэш.js`, которого в этой сборке нет
- **THEN** ответ 404, а не оболочка

### Requirement: Контейнер вписывает адрес сайта в оболочку при запуске
При каждом запуске контейнер SHALL вставить перед `</head>` оболочки метатег `ryadom-web-url` со значением `PUBLIC_WEB_URL` без завершающих косых черт; значение MUST экранироваться как HTML-атрибут (`&`, `"`, `<`, `>`). Один образ обслуживает локальный стенд и прод, поэтому адрес в сборку не вшивается. И `/pwa/`, и `/pwa/index.html` (и любой путь, получивший оболочку) SHALL отдавать один и тот же файл с метатегом; исходный `index.html` без метатега MUST NOT отдаваться никогда. Метатега окружения (`APP_ENV`) в оболочке нет. PWA SHALL брать адрес сайта (юридические документы, страница загрузки) из `ryadom-web-url`, а адрес API — свой же origin. Смена значения требует перезапуска контейнера; до уже установленных копий она доходит только со следующей сборкой образа, потому что service worker кэширует оболочку.

Поверхности: pwa

#### Scenario: Метатег в ответе
- **WHEN** контейнер запущен с `PUBLIC_WEB_URL=https://site.example/`, и приходит `GET /pwa/`
- **THEN** в `<head>` ответа есть `<meta name="ryadom-web-url" content="https://site.example">`

#### Scenario: Спецсимволы в значении
- **WHEN** значение `PUBLIC_WEB_URL` содержит `"`, `<`, `>` или `&`
- **THEN** в метатеге они заменены на `&quot;`, `&lt;`, `&gt;`, `&amp;`

#### Scenario: Одинаковая оболочка по двум адресам
- **WHEN** браузер запрашивает `GET /pwa/` и `GET /pwa/index.html`
- **THEN** оба ответа содержат один и тот же `index.html` с метатегом, а исходного файла без метатега контейнер не отдаёт

#### Scenario: Ссылки на документы в PWA
- **WHEN** человек открывает из PWA условия использования или политику
- **THEN** адрес строится от значения метатега `ryadom-web-url`

### Requirement: Контейнер не запускается с неверными настройками
Контейнер SHALL проверять настройки при старте и MUST завершаться с ненулевым кодом и сообщением в stderr, не запуская nginx, если `PUBLIC_WEB_URL` не задан, не начинается с `http://` или `https://` либо содержит пробельные символы, а также если в собранном `index.html` нет `</head>`. Оболочку без метатега или с неверным значением клиентам MUST NOT отдавать.

Поверхности: pwa

#### Scenario: Нет адреса сайта
- **WHEN** контейнер запускается без `PUBLIC_WEB_URL`
- **THEN** он завершается с ненулевым кодом и сообщением, что `PUBLIC_WEB_URL` обязателен

#### Scenario: Адрес без схемы или с пробелом
- **WHEN** `PUBLIC_WEB_URL` равен `site.example` либо `https://site .example`
- **THEN** контейнер завершается с ненулевым кодом и сообщением о неверном адресе

#### Scenario: Верные настройки
- **WHEN** задан `PUBLIC_WEB_URL=https://site.example`
- **THEN** контейнер стартует и отдаёт оболочку с метатегом

### Requirement: Кэш-заголовки и сжатие
`Cache-Control` SHALL выбираться по виду файла: только файлы под `<префикс>/assets/` (JS, CSS, шрифты с хэшем содержимого в имени) получают `public, max-age=31536000, immutable`; иконки (`png`, `svg`, `ico`) — `public, max-age=86400`; всё остальное — оболочка, `sw.js`, `manifest.webmanifest`, `voice-worklet.js` — `no-cache`. Заголовок MUST выставляться только успешным ответам и перенаправлениям: ответ с ошибкой не получает `Cache-Control`, чтобы 404 не стал `immutable`. Манифест отдаётся с типом `application/manifest+json`. Текстовые ответы (HTML, CSS, JS, JSON, манифест, SVG, шрифты TTF) от 1024 байт SHALL сжиматься gzip для клиентов, которые принимают сжатие, с `Vary: Accept-Encoding`.

Поверхности: pwa

#### Scenario: Service worker не кэшируется
- **WHEN** браузер запрашивает `/pwa/sw.js`
- **THEN** ответ содержит `Cache-Control: no-cache`

#### Scenario: Ресурс с хэшем в имени
- **WHEN** браузер запрашивает файл вида `/pwa/assets/index-<хэш>.js`
- **THEN** ответ содержит `Cache-Control: public, max-age=31536000, immutable`

#### Scenario: Иконка
- **WHEN** браузер запрашивает `/pwa/pwa-192x192.png`
- **THEN** ответ содержит `Cache-Control: public, max-age=86400`

#### Scenario: Файл из public без хэша
- **WHEN** браузер запрашивает `/pwa/voice-worklet.js`
- **THEN** ответ содержит `Cache-Control: no-cache`, а не `immutable`

#### Scenario: Манифест
- **WHEN** браузер запрашивает `/pwa/manifest.webmanifest`
- **THEN** ответ содержит `Cache-Control: no-cache` и `Content-Type: application/manifest+json`

#### Scenario: Ошибка не кэшируется навсегда
- **WHEN** браузер запрашивает отсутствующий файл под `/pwa/assets/`
- **THEN** ответ 404 не содержит `Cache-Control: public, max-age=31536000, immutable`

#### Scenario: Запрос со сжатием
- **WHEN** браузер запрашивает JS-файл сборки с `Accept-Encoding: gzip`
- **THEN** ответ приходит с `Content-Encoding: gzip`

### Requirement: Заголовки безопасности ответов PWA
Каждый ответ контейнера (файл, оболочка, перенаправление, 404, проверка живости) SHALL нести `X-Robots-Tag: noindex`, `X-Content-Type-Options: nosniff` и `Content-Security-Policy` с директивами `default-src 'self'`, `script-src 'self' 'wasm-unsafe-eval'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: blob:`, `font-src 'self' data:`, `media-src 'self' blob:`, `connect-src 'self' ws: wss:`, `worker-src 'self' blob:`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors https://web.telegram.org`. Разговор идёт по WebSocket на тот же origin, поэтому `connect-src` MUST разрешать `ws:` и `wss:`. Встраивание приложения во фрейм MUST быть разрешено только Telegram Web (`https://web.telegram.org`), который показывает Mini App во фрейме; приложения Telegram для телефона и компьютера открывают его в собственном WebView без фрейма (см. `telegram-mini-app`). `'wasm-unsafe-eval'` разрешает лишь компиляцию WebAssembly для декодера озвучки там, где у браузера нет своего декодера Opus.

Поверхности: pwa · tg

#### Scenario: Политика на оболочке
- **WHEN** браузер запрашивает `GET /pwa/`
- **THEN** в ответе есть `Content-Security-Policy`, содержащая `connect-src` и `frame-ancestors https://web.telegram.org`

#### Scenario: Чужой сайт во фрейме
- **WHEN** сайт, отличный от `https://web.telegram.org`, встраивает `/pwa/` во фрейм
- **THEN** браузер не показывает приложение во фрейме

#### Scenario: Заголовки на 404
- **WHEN** контейнер отвечает 404 (путь вне префикса или отсутствующий файл в `assets/`)
- **THEN** в ответе тоже есть `Content-Security-Policy`, `X-Robots-Tag` и `X-Content-Type-Options`

### Requirement: Проверка живости контейнера
Контейнер SHALL отвечать на `GET /healthz` статусом 200 и телом `ok` (`text/plain`). Адрес лежит вне префикса и предназначен только для проб оркестратора и проверки образа: шлюз его не публикует. Обращения к нему MUST NOT попадать в журнал доступа.

Поверхности: pwa

#### Scenario: Проба
- **WHEN** оркестратор запрашивает `GET /healthz` у работающего контейнера
- **THEN** ответ 200 с телом `ok`, даже при непустом префиксе

### Requirement: API и PWA выкатываются независимо
API и PWA SHALL выпускаться отдельными образами с собственными тегами, поэтому версии клиента и сервера на хосте могут расходиться. API MUST оставаться совместимым с предыдущей сборкой PWA: установленная копия обновляется только по кнопке человека, и PWA может подолгу работать на оболочке старой сборки; контракт `/api/*` для неё меняется только добавлением полей. Ворота версий PWA не касаются: она не шлёт `X-Platform` и `X-App-Version`, и выкат нового API этого MUST NOT менять (см. `app-updates`).

Поверхности: pwa · api

#### Scenario: Новый API, старая оболочка
- **WHEN** выкачен новый образ API, а у человека установлена оболочка предыдущей сборки PWA
- **THEN** старая оболочка продолжает работать с новым API, ответа 426 она не получает

#### Scenario: Выкат только PWA
- **WHEN** выкачен новый образ PWA, а образ API не менялся
- **THEN** у установленных копий после проверки обновления появляется баннер новой версии, API не затронут

### Requirement: Web app manifest
Манифест `manifest.webmanifest` (под префиксом — `GET /pwa/manifest.webmanifest`) SHALL содержать: `name` и `short_name` «Рядом», описание, `lang` `ru`, `start_url` и `scope` `./` (каталог манифеста), `display` `standalone`, `background_color` и `theme_color` `#00051a`, `categories` `health` и `lifestyle`, ярлык «Отметить настроение» (короткое имя «Настроение», адрес `./diary/?checkin=1`) и иконки `pwa-192x192.png` (192×192), `pwa-512x512.png` (512×512) и `maskable-icon-512x512.png` (512×512, `purpose: maskable`). В `<head>` веб-сборки SHALL быть ссылка на манифест, `apple-touch-icon` (`apple-touch-icon-180x180.png`), `mobile-web-app-capable`, `apple-mobile-web-app-capable`, стиль строки состояния `black-translucent` и название «Рядом» для iOS; адреса манифеста и значка MUST строиться от префикса сборки. В нативные сборки эти теги MUST NOT попадать.

Поверхности: pwa

#### Scenario: Манифест отдаётся
- **WHEN** браузер запрашивает `/pwa/manifest.webmanifest`
- **THEN** статус 200, JSON с `name` «Рядом», `display` `standalone`, областью `/pwa/` и непустым списком `icons`

#### Scenario: Теги веб-сборки
- **WHEN** контейнер отдаёт оболочку с префиксом `/pwa`
- **THEN** в ней есть `<link rel="manifest" href="/pwa/manifest.webmanifest">`, `apple-touch-icon` с адресом `/pwa/apple-touch-icon-180x180.png` и перечисленные теги для iOS

#### Scenario: Ярлык настроения
- **WHEN** человек запускает PWA ярлыком «Отметить настроение»
- **THEN** открывается `/pwa/diary/?checkin=1`, и клиент показывает вкладку «Дневник» (см. `app-shell`)

#### Scenario: Нативная сборка
- **WHEN** (Android, iOS) собран JS для нативной сборки
- **THEN** в его `index.html` нет ссылки на манифест и тегов `apple-*`

### Requirement: Регистрация service worker
В веб-сборке клиент SHALL при старте регистрировать `sw.js`, лежащий рядом с `index.html`, с областью, равной префиксу сборки: `/pwa/sw.js` с областью `/pwa/` (без префикса — `/sw.js` с областью `/`). Воркер MUST NOT управлять страницами вне префикса (сайт, веб-клиент, `/api/`). Если браузер не поддерживает service worker или регистрация не удалась, приложение MUST продолжать работать без офлайн-режима и без сообщения о новой версии, не показывая ошибку. В нативных сборках service worker MUST NOT регистрироваться.

Поверхности: pwa · tg

#### Scenario: Воркер зарегистрирован
- **WHEN** человек открывает PWA по `/pwa/` в браузере с поддержкой service worker
- **THEN** у страницы появляется регистрация service worker с областью `/pwa/`

#### Scenario: Другие приложения хоста
- **WHEN** на том же хосте человек открывает сайт, веб-клиент или адрес `/api/…`
- **THEN** service worker PWA их запросы не перехватывает

#### Scenario: Регистрация не удалась
- **WHEN** регистрация `/pwa/sw.js` отклонена браузером
- **THEN** приложение работает как обычная страница, человек ошибки не видит

#### Scenario: Нативная сборка
- **WHEN** (Android, iOS) приложение запущено как нативное
- **THEN** service worker не регистрируется

### Requirement: Что кэширует service worker
Service worker SHALL при установке предкэшировать оболочку `index.html`, JS и CSS сборки (предел одного файла — 4 МиБ) и удалять устаревшие предкэши прежних версий. SDK продуктовой аналитики и WASM-декодер Opus MUST NOT входить в предкэш: они загружаются по требованию, и только когда нужны. На навигационные запросы воркер SHALL отвечать закэшированным `index.html` — и онлайн, и без сети, — кроме адресов, начинающихся с `/api/`. Он MUST NOT кэшировать ответы `/api/*` и MUST NOT перехватывать остальные запросы (fetch, WebSocket): они идут в сеть.

Поверхности: pwa

#### Scenario: Переход на внутренний маршрут
- **WHEN** воркер установлен и браузер переходит на `/pwa/diary/journal/`
- **THEN** страница отвечается закэшированным `index.html`

#### Scenario: Навигация на адрес API
- **WHEN** браузер переходит по адресу, начинающемуся с `/api/`
- **THEN** воркер не подставляет `index.html`, запрос уходит в сеть

#### Scenario: Запрос данных
- **WHEN** клиент выполняет fetch к `/api/dialogs`
- **THEN** ответ не берётся из кэша воркера и не сохраняется в нём

#### Scenario: Аналитика не в предкэше
- **WHEN** воркер устанавливается
- **THEN** SDK аналитики и декодер Opus не скачиваются вместе с оболочкой

#### Scenario: Новая версия сборки
- **WHEN** воркер новой версии установлен и активирован
- **THEN** предкэш прежней версии удаляется

### Requirement: Обновление service worker только по кнопке
Новая версия service worker SHALL ждать действия человека и MUST NOT активироваться сама: смена версии посреди разговора перезагрузила бы экран. Когда есть ожидающий воркер и страница уже управляется воркером, клиент SHALL показать баннер «Вышла новая версия» с кнопками «Обновить» и «Скрыть»; «Обновить» отправляет воркеру `SKIP_WAITING` и один раз перезагружает страницу, когда новый воркер возьмёт управление; «Скрыть» скрывает баннер до перезагрузки страницы. Пока страница открыта, клиент SHALL проверять наличие новой версии раз в час. Каждое появление, применение и скрытие баннера SHALL учитываться в аналитике (см. `product-analytics`).

Поверхности: pwa · tg

#### Scenario: Вышла новая версия
- **WHEN** новый воркер установился, а старый ещё управляет страницей
- **THEN** появляется баннер «Вышла новая версия» с кнопкой «Обновить», страница не перезагружается

#### Scenario: Человек нажал «Обновить»
- **WHEN** человек нажимает «Обновить»
- **THEN** ожидающий воркер получает `SKIP_WAITING`, и страница один раз перезагружается уже под новой версией

#### Scenario: Человек скрыл баннер
- **WHEN** человек нажимает «Скрыть»
- **THEN** баннер исчезает до перезагрузки страницы, а после неё, пока воркер всё ещё ждёт, появляется снова

#### Scenario: Первая установка
- **WHEN** воркер устанавливается впервые и страница ещё не управляется воркером
- **THEN** баннер о новой версии не показывается

#### Scenario: Долго открытая PWA
- **WHEN** установленная PWA остаётся открытой больше часа
- **THEN** клиент по таймеру запрашивает обновление воркера, не дожидаясь перезагрузки

### Requirement: Работа без сети
Когда service worker установлен, открытие приложения без сети (в том числе переход по любому маршруту оболочки) SHALL показывать оболочку из кэша; запросы к API без сети MUST завершаться сетевой ошибкой, обрабатываемой клиентом (индикатор офлайна — в `app-shell`). Без установленного воркера (первое открытие, браузер без поддержки, неудачная регистрация) оболочка без сети MUST NOT быть доступна.

Поверхности: pwa

#### Scenario: Повторное открытие без сети
- **WHEN** PWA уже открывалась с установленным воркером, а сети нет, и человек открывает приложение
- **THEN** оболочка загружается из кэша

#### Scenario: Первое открытие без сети
- **WHEN** сети нет, а воркер ещё ни разу не устанавливался
- **THEN** оболочка не открывается: показывать нечего, кроме страницы ошибки браузера

#### Scenario: Запрос к API без сети
- **WHEN** оболочка открыта без сети и клиент обращается к `/api/*`
- **THEN** запрос завершается сетевой ошибкой, ответ из кэша не подставляется

### Requirement: Условия показа баннера установки
В веб-сборке клиент SHALL показывать баннер установки внизу экрана поверх интерфейса, если приложение открыто не как установленное (ни `display-mode: standalone`, ни признака `standalone` в iOS), этот браузер не знает об установленном приложении и баннер не закрывали в последние 14 дней. Установка запоминается в `localStorage` под ключом `ryadom.install.installedAt` (общему для вкладки и окна приложения): метка записывается по событию `appinstalled` и при каждом запуске в режиме `standalone`, а при новом `beforeinstallprompt` снимается — браузер предлагает установку, только пока приложения нет. Пока метка есть, баннер MUST NOT показываться, в том числе в открытой вкладке. В нативных сборках, в установленном PWA и в Telegram Mini App баннер MUST NOT показываться. Первое появление баннера на странице учитывается в аналитике (`shown` либо `ios_instructions`).

Поверхности: pwa

#### Scenario: Вкладка браузера
- **WHEN** человек открывает PWA во вкладке браузера, приложение не установлено и баннер не закрывали
- **THEN** внизу экрана появляется баннер установки

#### Scenario: Установленное приложение
- **WHEN** PWA открыта с домашнего экрана в режиме `standalone`
- **THEN** баннер не показывается

#### Scenario: Вкладка при установленном приложении
- **WHEN** приложение установлено, а человек открывает тот же адрес во вкладке браузера
- **THEN** баннер не показывается, даже если `beforeinstallprompt` не приходит

#### Scenario: Установка из баннера
- **WHEN** человек нажимает «Установить» и принимает системный диалог
- **THEN** баннер в этой вкладке исчезает, а не меняется на подсказку про меню браузера

#### Scenario: Приложение удалили
- **WHEN** приложение удалено, метка осталась, и браузер снова присылает `beforeinstallprompt`
- **THEN** метка снимается, баннер появляется с кнопкой «Установить»

#### Scenario: Нативная сборка и Telegram
- **WHEN** (Android, iOS, Telegram) приложение запущено как нативное либо как Mini App
- **THEN** баннер установки не показывается

### Requirement: Текст подсказки и кнопка «Установить»
Содержимое баннера SHALL зависеть от среды. Если браузер выдал системное предложение установки (`beforeinstallprompt`), баннер говорит «Установи «Рядом» на телефон — открывается сразу, без браузера» и показывает кнопку «Установить», которая вызывает системный диалог. Иначе, если страница открыта во встроенном браузере мессенджера или соцсети (Telegram, VK, Facebook, Instagram, Line), баннер просит открыть её в Safari (iOS) или в браузере. Иначе, на iOS (включая iPadOS, представляющийся Mac с сенсорным экраном), баннер подсказывает «Нажми «Поделиться» и выбери «На экран «Домой»»». Иначе баннер подсказывает «Открой меню браузера и выбери «Установить приложение»». Кнопка «Установить» MUST показываться только в первом случае; системное предложение используется один раз — после ответа человека или события `appinstalled` кнопка исчезает.

Поверхности: pwa

#### Scenario: Браузер предлагает установку
- **WHEN** браузер сообщил `beforeinstallprompt`
- **THEN** баннер предлагает установку и показывает «Установить», по нажатию открывается системный диалог

#### Scenario: Safari на iPhone
- **WHEN** событие недоступно и страница открыта в Safari на iPhone
- **THEN** баннер без кнопки подсказывает «Поделиться» → «На экран «Домой»»

#### Scenario: Встроенный браузер мессенджера
- **WHEN** страница открыта во встроенном браузере мессенджера
- **THEN** баннер без кнопки просит открыть страницу в системном браузере

#### Scenario: Браузер без события
- **WHEN** событие не приходило, страница открыта не на iOS и не во встроенном браузере
- **THEN** баннер без кнопки подсказывает пункт меню «Установить приложение»

#### Scenario: Диалог использован
- **WHEN** человек ответил на системный диалог установки (принял или отклонил)
- **THEN** кнопка «Установить» больше не показывается

### Requirement: Закрытие баннера установки и память о нём
Кнопка закрытия баннера (доступное имя «Скрыть») SHALL сразу скрывать баннер и записывать текущее время в `localStorage` под ключом `ryadom.install.dismissedAt`; следующие 14 дней баннер MUST NOT показываться при любых загрузках, после — SHALL появиться снова. Закрытие учитывается в аналитике (`dismissed`). Если хранилище недоступно, баннер скрывается только на текущей странице и MAY вернуться при следующей загрузке.

Поверхности: pwa

#### Scenario: Закрыли и перезагрузили
- **WHEN** человек нажимает «Скрыть» и затем перезагружает страницу
- **THEN** баннер не показывается

#### Scenario: Прошло больше 14 дней
- **WHEN** с момента закрытия прошло больше 14 дней и человек открывает PWA в браузере
- **THEN** баннер показывается снова

#### Scenario: Хранилище недоступно
- **WHEN** `localStorage` недоступен, человек закрывает баннер и перезагружает страницу
- **THEN** баннер после закрытия исчезает, а после перезагрузки показывается снова

### Requirement: Веб-клиент не поставляется как PWA
Веб-клиент (`/app`) SHALL NOT поставляться как PWA: у него нет манифеста, service worker и баннера установки. Он и PWA живут на одном origin, поэтому хранилище браузера не пересекается: веб-клиент пишет только в пространство `ryadom.web.`, а PWA и нативные сборки сохраняют прежние имена (`ryadom_…`, `ryadom.user`, `ryadom.update.…`, `ryadom.install.…`) и не читают пространство веб-клиента; так сессии двух клиентов не затирают друг друга.

Поверхности: web · pwa

#### Scenario: Открытие веб-клиента
- **WHEN** (Web) человек открывает веб-клиент в браузере
- **THEN** страница не регистрирует service worker, не ссылается на манифест и не показывает баннер установки

#### Scenario: Две сессии на одном хосте
- **WHEN** человек вошёл в веб-клиент и в PWA в одном браузере под разными аккаунтами
- **THEN** вход в одном не выводит из другого: ключи хранилища разные
