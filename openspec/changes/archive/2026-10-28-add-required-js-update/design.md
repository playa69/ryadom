## Context

Политика версий — две оси. Нативная (минимум и последняя сборка по платформе) живёт в переменных окружения API, то
есть в ConfigMap, и меняется вручную после публикации в магазине. Ось JS запечена в образ API: сборка образа
собирает пакет варианта `prod`, и каждый выкат API автоматически предлагает его устройствам (`available`). Клиент
сравнивает себя с сервером по версии, которую сам сообщает в `js_version` и `X-Js-Version`.

До этого change'а эта версия бралась из `package.json` (`0.1.0`), а пакет назывался `0.1.0.<OTA_BUILD_NUMBER>`.

## Goals / Non-Goals

**Goals:**

- Четыре рычага оператора: мягкое и жёсткое обновление нативной сборки, мягкое и жёсткое обновление JS.
- Откат образа API немедленно возвращает устройства на прежний пакет.

**Non-Goals:**

- 426 за устаревший JS, проверка статуса по таймеру, CI для нативных релизов.

## Decisions

### Одна функция версии для пакета и для JS внутри него

Версию `<package.json>.<OTA_BUILD_NUMBER>` считает один модуль, его используют и конфигурация Vite (константа,
которую JS сообщает серверу), и скрипт сборки пакета (имя файла и манифест). Разойтись им больше негде. Номер
сборки проверяется там же: 1–6 цифр (столько допускает формат версии на сервере), иначе сборка падает — образ с
пакетом, версию которого сервер отвергнет, хуже упавшей сборки.

Отвергнуто: брать версию из `package.json` и в пакете (без номера сборки) — тогда два выката подряд дают пакеты одной
версии, и второй никогда не доходит до устройств.

### Минимум JS — в окружении, как нативный минимум

`MOBILE_JS_MIN_VERSION` в ConfigMap: оператор решает «этот пакет обязателен» после выката, не пересобирая образ,
ровно так же, как поднимает нативный минимум. Клиент ниже минимума получает `required` — существующий путь клиента
(экран «Обновляемся», загрузка, перезапуск WebView), уже проверенный откатом. Минимум выше пакета не ломает
ничего: требовать можно только то, что есть, поэтому клиент на версии пакета получает `not_available`.

Отвергнуто:

- флаг «обязательный» при сборке образа — его нельзя включить после выката, а пропущенный обязательный пакет
  забывается при следующем мягком выкате (минимум помнит его, пока его не опустят);
- 426 для JS ниже минимума — клиент, у которого не скачался пакет или натив слишком стар для пакета, остался бы без
  API и без экрана, который объяснил бы почему.

### Встроенный JS нативной сборки

Нативной релизной сборке стоит собирать JS с тем же `OTA_BUILD_NUMBER`, что и образ API из того же коммита
(`git rev-list --count HEAD`): тогда свежая сборка из магазина не скачивает пакет, который у неё уже есть. Без номера
встроенный JS сообщает `<версия>.0` и сразу получает пакет сервера — так же, как все сборки до этого change'а.
Сборка из коммита новее выкаченного API получит `required` (откат) и перейдёт на пакет сервера: сервер — источник
правды, и это безопаснее, чем JS, который зовёт ещё не выкаченные маршруты.

## Risks / Trade-offs

- **Жёсткое обновление не мгновенно.** Пакет применяется при ближайшей проверке статуса: запуск, возврат на передний
  план (не чаще раза в минуту), появление сети, ответ 426. Приложение, открытое без перерыва, получит его при
  следующем возврате.
- **Мягкое применение — при уходе в фон.** Плагин применяет назначенный пакет, когда приложение уходит в фон, а не
  только при холодном запуске; разговор в этот момент оборвётся. Так было и раньше.
- **Уже установленные сборки** сообщают `0.1.0`, это ниже любого пакета, поэтому они догоняют сервер как раньше и
  после первого применения сообщают версию пакета.
