# Design: add-dialog-share-link

## Модель угроз (коротко)

| Угроза | Мера |
|---|---|
| Угадывание ссылки | Токен — 32 случайных байта (CSPRNG), base64url (43 символа); перебор невозможен. В БД только `sha256(token)` |
| Утечка БД | Токена в БД нет, только хеш; текстов разговоров в `dialog_shares` нет |
| Перебор и сканирование | Лимит запросов на IP к `/api/shared/*` (как у неавторизованных маршрутов, `limits.ts`), одинаковый ответ `404` для «нет», «истекла», «отозвана» |
| Попадание в поиск и превью мессенджеров | `X-Robots-Tag: noindex, nofollow`, `<meta name="robots">`; страница рендерится на клиенте, превью без текста («Разговор в Рядом») |
| Утечка токена через `Referer` | `Referrer-Policy: no-referrer` на странице и в ответе API |
| Кэширование | `Cache-Control: no-store` |
| Поделился лишнего | Граница разговора фиксируется при создании (`upToMessageId`): новые реплики после создания не видны; видно только выбранный разговор |
| Автор не понимает, что делится | Лист подтверждения с предупреждением, явный выбор срока, предпросмотр что увидит получатель |
| Ссылка живёт дольше разговора | Удаление разговора, «забыть всё», аккаунта, удаление по сроку хранения и блокировка аккаунта делают ссылку `404` (проверка при каждом чтении, а не только при создании) |

## Решения

**D1. Что видит получатель.** Реплики человека и агента в порядке диалога, время начала и «Поделились N часов назад / до такого-то». Не видит: аудио, `summary`, напряжение, темы, `safety`, имя и почту автора, `userId`, `dialogId`. Причина: сводка и напряжение — выводы о человеке (`REQ-PRD-03`: ярлыков не показываем), а идентификаторы дали бы получателю опору для атак на API.

**D2. Моментальный срез через границу, а не копия.** Тексты хранит только агент (`REQ-MEM-01`). Ссылка хранит `upToMessageId`; API читает сообщения у агента и режет по границе. Копировать тексты в `app/` нельзя: стирание (`REQ-DATA-02`) пришлось бы делать в двух местах. Следствие: пока разговор не удалён, ссылка читает живые данные агента — агент недоступен → получатель видит «Не получилось открыть, попробуйте позже» (`503`, не `404`).

**D3. Одна активная ссылка на разговор, видна всегда.** Токен не хранится: он вычисляется как `base64url(HMAC-SHA256(DIALOG_SHARE_SECRET, shareId))`, в БД только `shareId` и `token_hash = sha256(token)` для поиска при чтении. Повторное «Поделиться» показывает ту же ссылку (`GET …/share` пересчитывает токен). Сменить срок — отозвать и создать новую. Утечка БД без секрета ссылок не раскрывает; ротация секрета обрывает все ссылки. (Альтернативы: одноразовый показ с хешем — неудобно; шифрование токена в строке — больше поверхность; несколько ссылок на разговор — лишняя сложность для личного разговора.)

**D4. Срок.** `ttlHours` ∈ {24, 72, 168}; любое другое значение — `400`. Ссылка не продлевается, только создаётся новая. Срок ссылки ограничивается моментом удаления разговора по сроку хранения, если он раньше.

**D5. Открытый (не завершённый) разговор.** Делиться можно: срез фиксируется на момент создания. Получатель видит пометку «Разговор ещё идёт — вы видите его на {время}». Кризисные разговоры делиться не запрещаем (человек вправе показать близким), но лист подтверждения для них добавляет строку «Если вам плохо прямо сейчас — линии помощи» со ссылкой на «Люди рядом».

**D6. Лимиты.** Не более 5 активных ссылок на аккаунт; на разговор — одна; создание — не чаще 10 в час. Превышение — `429`/`409` с понятным текстом.

**D7. Только чтение и без следов получателя.** У получателя нет входа, нет действий, нет кнопок записи. Сервер хранит только `view_count` и `last_viewed_at` (для владельца), IP и User-Agent получателей не пишутся (`REQ-DATA-01`). В логах токен маскируется (`/s/<redacted>`).

**D10. Ссылка всегда ведёт на веб-клиент.** Страница получателя живёт в `apps/web` (`/s/<token>` веб-клиента (в проде `/app/s/<token>`), без логина), а не в PWA: получателю не нужна установка, а ссылка из мессенджера открывается в браузере и не попадает в область PWA (`/pwa/`). Создают и отзывают ссылку из обоих клиентов (веб и PWA/мобильный) одним и тем же API; адрес в ответе всегда веб-адрес.

**D8. Системный «Поделиться».** Нативные клиенты и PWA, где есть `navigator.share`, вызывают системный лист с готовым текстом «Поделился(-ась) разговором с тобой в Рядом: <ссылка>. Ссылка действует до …»; иначе — кнопка «Скопировать ссылку».

**D9. Без PII-маскирования получателю.** Текст показывается как есть: человек сам выбирает делиться. Это явно сказано в листе подтверждения.

## API (все под `/api`, JSON, заголовки трассировки как везде)

| Маршрут | Доступ | Описание |
|---|---|---|
| `POST /dialogs/{dialogId}/share` `{ttlHours}` | JWT владельца | `201 {shareId, url, expiresAt, viewCount}`. Ошибки: `404` чужой/несуществующий разговор, отказ `SHARE_EXISTS` (уже есть активная — вернуть её через GET), `SHARE_LIMIT`, `429`, `400` |
| `GET /dialogs/{dialogId}/share` | JWT владельца | `200 {shareId, url, createdAt, expiresAt, viewCount, lastViewedAt}` или `404`, если активной нет |
| `DELETE /dialogs/{dialogId}/share` | JWT владельца | `204`, идемпотентно |
| `GET /shared/{token}` | без авторизации (`no-store`, `no-referrer`, `noindex`) | `200 {startedAt, sharedAt, expiresAt, isOpen, messages:[{role, text, createdAt}]}` либо единообразный `404`; `503` если агент недоступен |

## Данные: `dialog_shares`

`id uuid pk`, `user_id uuid fk users on delete cascade`, `dialog_id text`, `token_hash bytea unique` (сам токен не хранится, см. D3), `up_to_message_id text`, `expires_at timestamptz`, `revoked_at timestamptz null`, `created_at`, `view_count int default 0`, `last_viewed_at timestamptz null`. Индексы: `(user_id)`, `(dialog_id)`, `(expires_at)`. Просроченные строки чистятся фоновой задачей раз в сутки (ссылка недействительна и без неё: срок проверяется при чтении).

## Экраны (см. `mockups/share-mockups.html`)

1. Веб: кнопка «Поделиться» в заголовке `/journal/<id>` → модальное окно: срок (сегменты 24 ч / 3 дня / 7 дней), предупреждение, «Создать ссылку».
2. Веб: окно активной ссылки (после создания и при каждом повторном открытии).
3. Веб: повторное «Поделиться» открывает карточку активной ссылки: ссылка, срок, просмотры, «Скопировать», «Отправить…», «Отозвать ссылку».
4. PWA/мобильный: те же состояния листом снизу (action sheet), «Отправить…» вызывает системный лист.
5. Получатель (всегда веб-клиент, в любом браузере): страница `/s/<token>` веб-клиента (в проде `/app/s/<token>`): шапка «Рядом», плашка «Вам поделились разговором. Он доступен до …», сообщения в пузырях, внизу пояснение «Вы видите только этот разговор» и приглашение «Попробовать Рядом» (без трекинга).
6. Получатель: ссылка недействительна — «Ссылка больше не действует» (одинаково для всех причин).

## Открытые вопросы

1. Нужна ли возможность защитить ссылку кодом/паролем? (v1 — нет; усложняет передачу близким.)
2. Подтверждать ли у владельца каждый просмотр (уведомление «ссылку открыли»)? Предлагаем счётчик, без пушей.
3. Хранить ли срез навсегда после удаления аккаунта автора? Нет: ссылка умирает вместе с данными.
4. Можно ли выключить фичу целиком? Да: переключатель `DIALOG_SHARE_DISABLED` отключает создание и открытие ссылок (по умолчанию фича включена).
5. Есть ли у агента ручка чтения сообщений по `dialogId` с границей — уточнить при реализации (`REQ-DLG-08`).

## Как реализовано

- Адрес ссылки: `PUBLIC_WEBAPP_URL` (в проде `https://<хост>/app/`), а без него `PUBLIC_APP_URL` + `/app`. Токен — `HMAC-SHA256(AUTH_SECRET, "dialog-share:v1:" + shareId)`, base64url; смена `AUTH_SECRET` отзывает все ссылки.
- Отказы создания (`SHARE_EXISTS`, `SHARE_LIMIT`, `SHARE_DISABLED`) приходят как отказ маршрута (`200` с кодом), как у остальных маршрутов приложения; недопустимый срок — `422`.
- Граница среза — id последнего сообщения: ссылка читает диалог у агента (`GET /v1/users/{userId}/dialogs/{id}`, он уже отдаёт сообщения с id) и режет по границе. Нет границы среди сообщений — получатель видит единый отказ.
- Путь запроса в журнале запросов API записывается как `/api/shared/:token`.
- Открытые вопросы 1–2 решены как в v1 (без пароля, счётчик без пушей); вопрос 5 закрыт — ручка у агента есть.
