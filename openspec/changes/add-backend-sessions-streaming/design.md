# Design: add-backend-sessions-streaming

## Context

Строится поверх change add-backend-foundation-auth (каркас, auth, rate-limit, аудит). Контракт — specs/sessions и specs/streaming этого change'а + docs/openapi.yaml (тег `sessions`, операции createSession/listSessions/getSession/deleteSession/finishSession/postSessionMessage). Стек из openspec/config.yaml: FastAPI + WebSocket, PostgreSQL + pgvector, Redis + Sentinel, Celery + beat, GigaChat, SaluteSpeech, Langfuse. Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Один процесс FastAPI обслуживает REST и WS (меньше движущихся частей на MVP).
- Конвейер реплики как единый отменяемый async-pipeline с трейсингом каждого шага.
- Деградация голоса в текст без разрыва сессии.
- Кризисный протокол — структурно неотключаемый шаг конвейера, а не опция.

**Non-Goals:**

- Консолидация памяти L2/L3 (фоновая, еженедельная) — отдельный change; здесь только retrieval и запись L0/L1.
- Горизонтальное масштабирование WS на несколько подов (sticky sessions) — поступательная задача инфры при росте; контракт это не меняет.
- ClickHouse для component_calls — пока собственный лог/метрики; ClickHouse задеплоим позже.
- Режим `warmth` — зарезервирован под v1.

## Decisions

### D1. WS-менеджер в процессе FastAPI

`app/api/ws/`: реестр соединений (user_id → активное соединение) в памяти процесса + маркер активного соединения в Redis (для вытеснения кодом 4003 и проверки «1 соединение на пользователя»). Буфер событий — Redis list per session, последние 200 событий, TTL = TTL сессии.

**Почему:** один под на MVP, реестр в памяти прост и быстр; Redis-маркер оставляет путь к мультиподовой схеме без смены контракта.

**Альтернативы:** отдельный WS-сервис — отвергнуто (лишний хоп к конвейеру); pub/sub Redis для событий — отвергнуто на MVP (нет второго пода).

### D2. session_token — отдельный короткоживущий JWT назначения `ws`

Выдаётся в `POST /sessions`, TTL 300 сек, claim `session_id` + `sub`. Проверяется при upgrade без обращения в БД. Обновление токена для reconnect после истечения — открытый вопрос v0.1 (в v0 — пересоздание сессии после `finished`/`expired`).

**Почему:** не таскать access-токен в query-параметре WS (утечки в логах прокси) и не привязывать жизнь соединения к 15-минутному access.

### D3. Конвейер реплики — отменяемый async-pipeline

`dialog_orchestrator` исполняет шаги ASR → safety → эмоции → retrieval → LLM → TTS как asyncio-задачу с cancellation: новая реплика пользователя (barge-in) отменяет генерацию текущего ответа. Каждый шаг — отдельный спан Langfuse + счётчик component call. Состояние конвейера не персистится (переживает только транскрипт/события).

**Почему:** голосовой диалог требует прерываемости; отмена через asyncio.shield/cancel прозрачнее, чем флаги.

### D4. Клиенты GigaChat/SaluteSpeech — httpx/ws с retry, backoff и circuit breaker

`app/services/llm/`: клиент GigaChat (chat completions стрим, embeddings), клиенты SaluteSpeech ASR (стриминговый) и TTS (стриминговый + кэш аудио ритуалов/типовых фраз в Redis по хэшу текста+голоса). Retry — только идемпотентные вызовы (embeddings, TTS), 3 попытки с экспоненциальным backoff; circuit breaker (открытие после N подряд ошибок, half-open probe) на каждую интеграцию. При открытом breaker'е голосовой цепочки — деградация в текст (событие клиенту).

**Почему:** голос — основной драйвер стоимости и главная точка отказа; кэш TTS ритуалов — прямой рычаг юнит-экономики из спеки.

### D5. Safety-классификатор как обязательный шаг до LLM

Двухступенчатый: правила + лёгкая модель (класс ruBERT в контуре) → LLM-проверка неоднозначных. Шаг выполняется до retrieval/LLM и не может быть пропущен конфигурацией режима. Порог — на высокий recall (лучше лишний бережный вопрос). Валидационный набор собирается с консультантами до релиза.

**Почему:** «кризис важнее продукта» — сквозной принцип спеки; структурная неотключаемость исключает регрессию режимов.

### D6. PII-фильтрация (NER) на входе внешних вызовов

`pii_filter_service` маскирует ФИО/телефоны/email в тексте реплики перед отправкой в GigaChat/SaluteSpeech; маппинг масок восстанавливается в ответе для естественности (в пределах запроса, не персистится).

### D7. Суммаризация — Celery-задача после finish

`finish` ставит задачу `summarize_session` (Celery worker из стека config.yaml): L1-саммари (темы, эмоции, tension до/после, key_facts) лёгкой моделью GigaChat → `session_summaries`. Идемпотентность по session_id (повтор задачи не создаёт дубль).

**Почему Celery, а не Arq:** решение пользователя; Celery + beat зафиксирован в openspec/config.yaml и закрывает и разовые задачи, и расписания (ритуалы — следующий change).

### D8. Транскрипты — шифрование text_enc, аудио не хранится

Реплики пишутся в `messages` с полевым шифрованием (Fernet/AES-GCM, ключ из k8s-secret) только при `store_transcripts=true` и не-инкогнито. Аудио не персистится нигде (буфер чанков живёт в памяти соединения до финала ASR). Эмбеддинги — по финальному транскрипту (pgvector).

### D9. Лимиты канала — в конфиг, проверка на WS-менеджере и rate-limit сервисе

60 сообщений/мин — через anti_spam (action `message_send`, sliding window); heartbeat/idle/max-duration — таймеры WS-менеджера; размеры фреймов — валидация на входе. Все пороги — env-конфиг с дефолтами из specs/streaming.

## Risks / Trade-offs

- [Пропуск кризиса классификатором — критичный по последствиям] → порог на высокий recall, постоянная кнопка SOS на клиенте, линии всегда в один тап, валидация с консультантами до релиза, логирование всех red-срабатываний для ревью.
- [Стоимость голоса] → кэш TTS, лёгкие модели для классификации/суммаризации, текстовая деградация, лимит voice_minutes_per_day (настройка из change user-profile).
- [Один под = единая точка отказа WS] → приемлемо для MVP; reconnect/resume по last_event_id сглаживает рестарты; мультипод — отдельная инфра-задача (sticky sessions на gateway).
- [Гонки при вытеснении соединения (4003) во время генерации] → отмена конвейера старого соединения через cancellation, буфер событий в Redis — новое соединение дочитывает по last_event_id.
- [LLM-вызовы в уточняющем safety-шаге увеличивают латентность] → уточнение только для неоднозначных; целевое время до показа помощи < 1 сек контролируется метрикой.
- [Новая реплика во время TTS-стрима] → barge-in отменяет TTS-стрим; недошедшие tts.chunk клиент отбрасывает по event_id.

## Migration Plan

1. Миграция Alembic `0002_sessions` (sessions, messages с vector-колонкой, session_summaries) — новые таблицы, без риска для существующих.
2. Деплой Celery worker (новый контейнер того же образа) + задача summarize_session.
3. Rollout приложения; проверка: создание сессии → WS-подключение → текстовая реплика полного цикла → finish → саммари.
4. Откат: откат Deployment, `alembic downgrade` (данных ещё нет).

## Open Questions

- Таймауты долгоживущих WS на istio-gateway/Envoy (idle timeout HTTPRoute должен быть ≥ 60 мин) — значение подбирается при деплое, на контракт не влияет.
- Обновление session_token для reconnect после истечения 300 сек — v0.1, в v0 пересоздание сессии.
- Хостинг лёгких классификаторов (ruBERT safety/эмоции): sidecar vs отдельный сервис — решение при интеграции моделей, шаг конвейера от этого не меняется.
