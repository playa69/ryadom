# Дельта-спецификация: streaming

## Purpose

Дуплексный протокол реального времени для голосовых и текстовых сессий: WebSocket-фреймы, авторизация и жизненный цикл соединения, reconnect/resume, кризисный протокол в потоке, SSE-fallback и конвейер обработки реплики.

## ADDED Requirements

### Requirement: WebSocket-канал и типы фреймов

Сервис SHALL предоставлять WebSocket-эндпоинт `/api/v1/ws/sessions/{session_id}` с JSON-фреймами (аудио — base64 внутри JSON). Клиентские типы: `audio.chunk` (`seq`, `codec` opus/pcm16, `data` ≤ 64 КБ), `text.message` (`text` ≤ 4000, `client_msg_id`), `ping`, `session.pause`, `session.resume`. Серверные типы: `transcript.partial`, `transcript.final`, `safety.status` (green/yellow/red), `llm.token`, `llm.done`, `tts.chunk`, `session.state` (active/paused/finishing/finished), `crisis.intervention`, `error`, `pong`. Каждый серверный фрейм MUST нести монотонный `event_id` в пределах сессии. Фрейм MUST NOT превышать 256 КБ.

#### Scenario: Голосовая реплика полного цикла

- **WHEN** клиент шлёт поток `audio.chunk` и завершает реплику
- **THEN** сервер последовательно шлёт `transcript.partial`/`transcript.final`, `safety.status`, поток `llm.token` + `llm.done`, поток `tts.chunk` — каждый с монотонным `event_id`

#### Scenario: Текстовая реплика

- **WHEN** клиент шлёт `text.message` с `client_msg_id`
- **THEN** сервер обрабатывает реплику и отвечает тем же набором серверных фреймов (без транскрибации аудио)

#### Scenario: Пауза и возобновление

- **WHEN** клиент шлёт `session.pause`, затем `session.resume`
- **THEN** сервер отвечает `session.state` со значениями `paused`, затем `active`

### Requirement: Авторизация соединения

WS-соединение SHALL устанавливаться только по валидному `session_token` (query-параметр `token`, TTL 300 секунд), выданному при создании сессии. Недействительный или истёкший токен MUST закрывать соединение кодом 4401.

#### Scenario: Подключение с валидным токеном

- **WHEN** клиент подключается с актуальным `session_token` своей сессии
- **THEN** соединение установлено, сервер шлёт `session.state` = `active`

#### Scenario: Истёкший токен

- **WHEN** клиент подключается с истёкшим `session_token`
- **THEN** соединение закрывается кодом 4401

### Requirement: Одно активное соединение

На пользователя MUST быть не более одного активного WS-соединения. Новое подключение MUST закрывать предыдущее кодом 4003.

#### Scenario: Вытеснение старого соединения

- **WHEN** пользователь подключается повторно при живом соединении
- **THEN** старое соединение закрывается кодом 4003, новое становится активным

### Requirement: Heartbeat и таймауты

Клиент SHALL слать `ping` каждые 30 секунд; сервер MUST отвечать `pong` и закрывать соединение при 60 секундах тишины. При 10 минутах без сообщений сервер MUST перевести сессию в `finishing` и закрыть соединение кодом 4002. По достижении 60 минут длительности сервер MUST перевести сессию в `finishing` и закрыть соединение кодом 4001. Нормальное завершение — код 4000.

#### Scenario: Потеря heartbeat

- **WHEN** клиент не шлёт `ping` более 60 секунд
- **THEN** сервер закрывает соединение

#### Scenario: Idle-таймаут

- **WHEN** в сессии 10 минут нет сообщений
- **THEN** сервер шлёт `session.state` = `finishing` и закрывает соединение кодом 4002

#### Scenario: Максимальная длительность

- **WHEN** сессия длится 60 минут
- **THEN** сервер шлёт `session.state` = `finishing` и закрывает соединение кодом 4001

### Requirement: Reconnect и resume

При переподключении клиент MAY передать `last_event_id`; сервер MUST дослать пропущенные серверные события из буфера (последние 200 событий сессии в Redis). Аудио-фреймы MUST NOT реплеиться. Повторная текстовая реплика с тем же `client_msg_id` MUST дедуплицироваться (не порождать вторую обработку).

#### Scenario: Переподключение после обрыва

- **WHEN** клиент переподключается с `last_event_id` после обрыва
- **THEN** сервер досылает события новее указанного из буфера и продолжает сессию

#### Scenario: Повторная отправка реплики

- **WHEN** клиент повторно шлёт `text.message` с уже обработанным `client_msg_id`
- **THEN** повторная обработка не выполняется

### Requirement: Кризисный протокол в потоке

Каждая реплика пользователя MUST проходить двухступенчатый safety-классификатор (быстрый: правила + лёгкая модель; уточняющий: LLM-проверка неоднозначных случаев), настроенный на высокий recall. Результат MUST доставляться фреймом `safety.status`. При уровне red сервер MUST: мягко остановить сценарий режима, отправить `crisis.intervention` со скриптом деэскалации и ресурсами помощи (горячие линии, близкие из памяти), не удерживать пользователя в диалоге. Кризисный протокол MUST перекрывать любой режим и любую метрику.

#### Scenario: Безопасная реплика

- **WHEN** реплика не содержит кризисных маркеров
- **THEN** сервер шлёт `safety.status` = `green` и продолжает обычный конвейер

#### Scenario: Кризисная реплика

- **WHEN** классификатор определяет высокий риск (суицидальные мысли, самоповреждение, срыв, насилие)
- **THEN** сервер шлёт `safety.status` = `red` и `crisis.intervention` со скриптом деэскалации и ресурсами помощи вместо обычного ответа режима

#### Scenario: Неоднозначная реплика

- **WHEN** быстрый классификатор сомневается
- **THEN** реплика проходит уточняющую LLM-проверку до выставления уровня

### Requirement: SSE-fallback

Сервис SHALL предоставлять `POST /sessions/{id}/messages` с ответом `text/event-stream` для текстовой деградации (без голоса). Типы SSE-событий MUST соответствовать серверным WS-фреймам (`transcript.final`, `safety.status`, `llm.token`, `llm.done`, `crisis.intervention`, `error`) без аудио-типов. Запрос MUST содержать `text` и `client_msg_id`.

#### Scenario: Текстовое сообщение через SSE

- **WHEN** клиент отправляет сообщение на `POST /sessions/{id}/messages`
- **THEN** сервер отвечает потоком SSE с `safety.status`, `llm.token`, `llm.done` без TTS-событий

#### Scenario: Кризис через SSE

- **WHEN** сообщение через SSE определяется как кризисное
- **THEN** в потоке приходит `crisis.intervention` с ресурсами помощи

### Requirement: Конвейер обработки реплики

Каждая реплика MUST проходить конвейер: ASR-стрим (для голоса) → safety-классификатор → классификатор эмоций → retrieval памяти (гибрид: векторный + вес давности; в контекст всегда включаются «время с последней сессии» и активные темы) → LLM-ядро по режиму (стрим) → TTS-стрим (для голоса; кэш ритуалов и типовых фраз). Перед внешними вызовами моделей MUST выполняться PII-фильтрация (NER). При недоступности голосовой цепочки (ASR/TTS) сервис MUST деградировать в текстовый режим с уведомлением клиента. Все вызовы компонентов MUST трейситься.

#### Scenario: Контекст памяти в ходе диалога

- **WHEN** пользователь возвращается после паузы в три недели
- **THEN** LLM-контекст содержит «с последней сессии прошло N дней» и активные темы, ответ это учитывает

#### Scenario: Деградация голоса

- **WHEN** ASR или TTS недоступны
- **THEN** сессия продолжается в текстовом режиме, клиент получает `session.state`/событие о деградации

#### Scenario: PII не покидает контур

- **WHEN** реплика содержит ФИО, телефон или email
- **THEN** во внешние вызовы моделей уходят маскированные значения
