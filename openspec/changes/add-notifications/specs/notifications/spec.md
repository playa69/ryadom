# Дельта-спецификация: notifications

## Purpose

Уведомления «Рядом» устроены одинаково для всех видов: каналы по платформам, согласие перед системным разрешением, настройки и подписки устройств, планировщик с ровно одной доставкой, окно и пауза при неоткрытых, ничего личного на экране блокировки. Первый вид — напоминание о настроении (capability `mood-reminders`). В приложении сейчас нет ни одного уведомления: ни push, ни локальных, ни сообщений бота.

## ADDED Requirements

### Requirement: Каналы доставки

Каждое устройство SHALL подключать один канал: нативные Android и iOS — локальные уведомления на устройстве по расписанию из настроек; PWA и веб в браузере с Web Push — подписку service worker (VAPID); Telegram Mini App — сообщение бота с кнопкой, открывающей Mini App на нужном экране (боту нужно право писать человеку). На iPhone вне установленной PWA настройка SHALL показывать «Напоминания работают, если добавить Рядом на экран „Домой“».

Поверхности: api · web · pwa · android · ios · tg

#### Scenario: (Telegram) Сообщение бота
- **WHEN** человек в Mini App разрешил боту писать, и пришло время напоминания
- **THEN** бот присылает одно сообщение с текстом и кнопкой, открывающей Mini App на нужном экране

#### Scenario: (PWA) Web Push
- **WHEN** человек подписал установленную PWA на напоминания, и пришло время
- **THEN** приходит одно push-уведомление

#### Scenario: (Android) Локальное уведомление
- **WHEN** человек включил напоминание в нативном приложении
- **THEN** в заданное время уведомление ставит само устройство, сервер по этому каналу ничего не отправляет

#### Scenario: (iOS) iPhone без установленной PWA
- **WHEN** человек открывает настройку напоминания в Safari вне установленной PWA
- **THEN** строка говорит «Напоминания работают, если добавить Рядом на экран „Домой“», системный запрос не показывается

### Requirement: Разрешение не на первом экране

Клиент MUST NOT запрашивать системное разрешение на уведомления при запуске, в онбординге и в разговоре. Системный запрос (или запрос права писать в Telegram) показывается только после того, как человек ответил «Да» на вопрос вида уведомления в приложении. Отказ в системном разрешении MUST NOT менять настройку на сервере.

Поверхности: web · pwa · android · ios · tg

#### Scenario: Первый запуск
- **WHEN** человек впервые открыл приложение и прошёл онбординг
- **THEN** системного запроса на уведомления не было

#### Scenario: Отказ в системе
- **WHEN** человек ответил «Да», но запретил уведомления в системном запросе
- **THEN** строка показывает «Уведомления запрещены в настройках» и как их включить, а другие его устройства продолжают получать уведомления

### Requirement: Настройки по видам уведомлений

Настройки SHALL храниться на сервере по видам (первый вид — напоминание о настроении) и действовать на всех устройствах человека: `GET /api/notifications/settings` отдаёт для каждого вида, включён ли он, время, на паузе ли он и отвечал ли человек на вопрос, и публичный ключ Web Push; если строки нет, отдаются значения по умолчанию. `PUT /api/notifications/settings/{kind}` меняет включённость, время и ответ на вопрос; время вне допустимого окна — `422`, включение вида снимает паузу. Пока уведомления выключены на сервере, маршруты уведомлений отвечают `404`, и клиент не показывает строк про уведомления.

Поверхности: api · web · pwa · android · ios · tg

#### Scenario: (API) Значения по умолчанию
- **WHEN** человек ещё ничего не настраивал
- **THEN** `GET /api/notifications/settings` отдаёт напоминание о настроении включённым на 20:00, не на паузе

#### Scenario: (API) Время вне окна
- **WHEN** клиент присылает время напоминания 23:30
- **THEN** ответ `422`, настройка не изменена

#### Scenario: (API) Включение снимает паузу
- **WHEN** вид стоит на паузе, а человек включает его заново
- **THEN** пауза снята

#### Scenario: Уведомления выключены на сервере
- **WHEN** уведомления выключены на сервере
- **THEN** маршруты отвечают `404`, а в клиентах нет ни вопроса, ни строки про напоминание

### Requirement: Подписка устройства

Устройство SHALL сообщать серверу свой канал через `POST /api/notifications/subscriptions` и снимать подписку через `DELETE /api/notifications/subscriptions/{id}`. Повторная подписка того же адреса не создаёт дубль. Подписку, на которую push-сервис ответил `404` или `410`, а бот Telegram — `403`, сервер MUST удалять. Чужие подписки недоступны.

Поверхности: api · web · pwa · android · ios · tg

#### Scenario: (API) Подписка идемпотентна
- **WHEN** устройство подписывается дважды на один и тот же адрес
- **THEN** подписка одна

#### Scenario: (API) Подписка истекла
- **WHEN** push-сервис отвечает на отправку `410`
- **THEN** подписка удалена, следующая отправка по ней не выполняется

#### Scenario: (API) Бот заблокирован
- **WHEN** бот Telegram получает `403` от человека, заблокировавшего его
- **THEN** подписка `telegram` удалена

### Requirement: Ровно одна доставка

Планировщик шлюза SHALL работать на каждой реплике и MUST гарантировать не больше одной доставки вида в местные сутки на человека. Перед отправкой вставляется запись доставки с уникальным ключом (человек, вид, местная дата). Отправляет только реплика, чья вставка удалась. Канал «локальные уведомления» сервер не отправляет.

Поверхности: api

#### Scenario: (API) Две реплики
- **WHEN** работают две реплики шлюза, и у человека наступило время напоминания
- **THEN** человек получает одно уведомление

### Requirement: Окно доставки

Уведомление MUST NOT отправляться позже 23:00 и раньше 08:00 по местному времени человека (`mood-diary`, «Местное время человека»). Если плановое время пропущено больше чем на 2 часа, уведомление за этот день не отправляется.

Поверхности: api

#### Scenario: (API) Сервер лежал
- **WHEN** шлюз был недоступен с 19:30 до 22:15, а напоминание стоит на 20:00
- **THEN** напоминание за этот день не отправляется

#### Scenario: (API) Ночное время
- **WHEN** у человека по местному времени 02:00
- **THEN** никакое уведомление ему не отправляется

### Requirement: Открытие уведомления

Касание уведомления на любом канале MUST открывать экран, к которому оно относится; ссылка из уведомления на дневник (`/diary/…`) открывает вкладку «Дневник» (`app-shell`, «Вкладки мобильного клиента»). Для серверных каналов (Web Push, бот Telegram) клиент SHALL сообщать серверу об открытии доставки (`POST /api/notifications/opened`). У локального уведомления нативной сборки записи доставки нет, его открытие на сервере не учитывается.

Поверхности: api · web · pwa · android · ios · tg

#### Scenario: (PWA) Касание пуша
- **WHEN** человек касается напоминания Web Push
- **THEN** открывается (или выходит на передний план) PWA на `/diary/` с карточкой отметки, а у доставки появляется время открытия

#### Scenario: (Telegram) Кнопка бота
- **WHEN** человек касается кнопки в сообщении бота
- **THEN** Mini App открывается на дневнике, а у доставки появляется время открытия

#### Scenario: (Android) Локальное уведомление
- **WHEN** человек касается локального напоминания в нативном приложении
- **THEN** открывается вкладка «Дневник» на карточке отметки, на сервер ничего не отправляется

### Requirement: Пауза при неоткрытых

После семи неоткрытых доставок вида подряд этот вид SHALL вставать на паузу. Считаются доставки серверных каналов (Web Push, бот Telegram): у локальных уведомлений нативной сборки записей доставки и открытий нет, и в счёт они не входят. Экран вида показывает «Напоминания на паузе — вернуть?». Тексты MUST NOT становиться настойчивее при пропусках.

Поверхности: api · web · pwa · tg

#### Scenario: (API) Неделя без открытий
- **WHEN** человек не открыл семь напоминаний подряд
- **THEN** восьмого не будет, пока он не нажмёт «Вернуть» или не включит напоминание заново

### Requirement: Ничего личного на экране блокировки

Текст уведомления MUST NOT содержать имя человека, его настроение, темы разговоров, заметки памяти и результаты тестов. В тексте только нейтральная фраза из согласованного набора.

Поверхности: api · android · ios

#### Scenario: Текст напоминания
- **WHEN** приходит напоминание о настроении
- **THEN** в тексте нет ни имени, ни прошлых отметок, ни тем разговоров

### Requirement: Выход и удаление аккаунта

Выход на устройстве SHALL удалять подписку этого устройства и снимать его локальные уведомления. Удаление аккаунта MUST стирать настройки уведомлений, подписки и записи доставок до того, как удаление объявлено; то же при автоматическом стирании анонимных аккаунтов.

Поверхности: api · web · pwa · android · ios · tg

#### Scenario: Выход
- **WHEN** человек вышел из аккаунта на телефоне
- **THEN** на этот телефон уведомления больше не приходят

#### Scenario: (API) Удаление аккаунта
- **WHEN** человек удалил аккаунт
- **THEN** в таблицах уведомлений нет его настроек, подписок и доставок

### Requirement: Старая нативная сборка

Если в нативной сборке нет плагина уведомлений (новый пакет интерфейса на старом APK), клиент MUST NOT предлагать локальные напоминания и MUST NOT показывать ошибок.

Поверхности: android · ios

#### Scenario: Старый APK
- **WHEN** приложение из текущего APK получило пакет интерфейса с уведомлениями
- **THEN** строки напоминания в нативном приложении нет, остальное работает

### Requirement: Аналитика уведомлений без содержимого

События аналитики уведомлений SHALL нести только вид, канал и результат действия: ответ на вопрос, результат системного запроса, смена настройки, отправка, открытие, пауза. Тексты уведомлений, значения настроения и другие личные данные MUST NOT попадать в события.

Поверхности: api · web · pwa · android · ios · tg

#### Scenario: Отправка
- **WHEN** сервер отправил напоминание
- **THEN** событие `notification_sent` содержит только `kind` и `channel`
