# Design: add-backend-content

## Context

Строится поверх add-backend-foundation-auth (каркас, идемпотентность через Redis, rate-limit по IP, trusted-proxy XFF). Контракт — specs/content/spec.md + docs/openapi.yaml (теги `news`, `support`, `sos`). Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Полностью публичный читающий контур (без auth) с кэшированием — дёшево по нагрузке.
- Справочник — данные, а не код: обновление без релиза (маграция/сид), ETag-инвалидация автоматически.
- SOS — максимально доступный: ничто (auth, валидация лишних полей) не должно мешать фиксации.

**Non-Goals:**

- Админ-CRUD новостей и справочника — TODO v2, отдельный контур с отдельной auth.
- Маркетплейс специалистов (бронирование, комиссия) — после конкурса.
- Push/email-уведомления при SOS — осознанно нет (анонимность, нет контактов).

## Decisions

### D1. Справочник и новости — сидирование миграциями

`support_resources` (kind: hotline/group/specialist, topic, payload jsonb) и `news` наполняются Alembic data-миграциями (SQL INSERT). Обновление справочника = новая data-миграция, а не релиз кода.

**Почему:** на MVP нет админки; контент меняется редко и ревьюится в git (консультанты утверждают тексты линий/групп).

**Альтернативы:** статичный JSON в коде — отвергнуто (нет истории изменений, нельзя расширить без релиза); админка сейчас — вне scope (лишний контур auth).

### D2. ETag из версии справочника

ETag = хэш (kind, max(updated_at), count) по соответствующей выборке; middleware/роутер сравнивает с `If-None-Match` и отдаёт 304. Любая data-миграция, меняющая справочник, автоматически меняет ETag — отдельной инвалидации не нужно.

### D3. SOS — запись всегда, ответ независим от auth

`sos_events` (user_id nullable, session_id nullable, trigger, created_at) пишется без обязательной auth: если Bearer валиден — привязываем user_id, если нет/истёк — пишем анонимно (auth-ошибка НЕ возвращается). Ответ — ресурсы из справочника (hotlines), собирается из того же `support_resources` (single source). Rate-limit 10/час по IP через anti_spam (action `sos_event`).

**Почему:** «SOS доступен всегда» — требование спеки; блокировка по auth в кризис недопустима.

### D4. Публичные GET — без обязательной auth, но с опциональным контекстом

Роутеры не требуют Bearer; при наличии валидного токена контекст пользователя доступен (для будущей персонализации), отсутствие/истёкший токен — не ошибка, а анонимный доступ.

## Risks / Trade-offs

- [Устаревший номер горячей линии — критичный контент] → источник истины ревьюят консультанты; data-миграции в git с ревью; ETag гарантирует обновление кэша клиентов.
- [Анонимные sos_events — мусор/флуд] → лимит 10/час по IP + идемпотентность; события — только агрегатные метрики, без контента.
- [ETag по max(updated_at) — ложные 304 при параллельных вставках] → приемлемо для редко меняющегося справочника; новости ETag не кэшируются (лента cursor-based).
- [payload jsonb справочника дрейфует по структуре между kind] → Pydantic-схемы ответа по kind на уровне сервиса (валидация при чтении, битая строка — ошибка деплоя, не клиента).

## Migration Plan

1. Миграция Alembic `0005_content` (news, support_resources, sos_events) + data-миграция сидирования (горячие линии РФ, стартовые группы/специалисты, 1–2 новости).
2. Rollout; проверка: лента новостей, hotlines без auth, ETag 304, SOS анонимно + с auth.
3. Откат: откат Deployment, downgrade (таблицы новые).

## Open Questions

- Точные тексты и контакты горячих линий/групп/специалистов — утверждаются консультантами, сидируются отдельно от кода (data-миграция).
- Метрика «конверсия в контакт» (звонок линии, переход к специалисту) — клиентские события, backend-учёт — отдельная задача аналитики после MVP.
