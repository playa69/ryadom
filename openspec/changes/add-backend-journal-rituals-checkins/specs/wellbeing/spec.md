# Дельта-спецификация: wellbeing

## Purpose

Инструменты регулярной самоподдержки: журнал (гештальт-письма и записи) с экспортом, ежедневные ритуалы с сериями, которые «отдыхают, а не сгорают», чекины состояния (HALT/WHO-5/tension) с динамикой благополучия и счётчиком чистого времени.

## ADDED Requirements

### Requirement: Журнал записей

Сервис SHALL предоставлять журнал: `POST /journal/entries` (kind: `gestalt_letter` или `note`; title ≤ 200, text ≤ 50000 символов), `GET /journal/entries` (cursor-пагинация, фильтры `kind`, `from`/`to`, поиск подстрокой `q`), `GET /journal/entries/{id}`, `DELETE /journal/entries/{id}` (204). Тексты записей MUST храниться зашифрованными. Доступ — только владельцу (чужая запись → 404 `ENTRY_NOT_FOUND`).

#### Scenario: Создание записи

- **WHEN** пользователь создаёт запись с `kind="gestalt_letter"`, title и text
- **THEN** возвращается 201 с созданной записью (id, временные метки)

#### Scenario: Лента с фильтрами и поиском

- **WHEN** пользователь запрашивает `GET /journal/entries?kind=note&q=мама`
- **THEN** возвращаются только заметки, содержащие подстроку, с cursor-пагинацией

#### Scenario: Чужая запись

- **WHEN** пользователь запрашивает запись другого пользователя
- **THEN** возвращается 404 `ENTRY_NOT_FOUND`

#### Scenario: Удаление записи

- **WHEN** владелец удаляет запись
- **THEN** возвращается 204, запись недоступна при повторном запросе

### Requirement: Экспорт журнала

Сервис SHALL возвращать все записи журнала одним Markdown-документом через `GET /journal/export` (format: markdown, filename, content) для передачи в системный share sheet на клиенте.

#### Scenario: Экспорт всех записей

- **WHEN** пользователь вызывает `GET /journal/export`
- **THEN** возвращается Markdown-документ со всеми записями пользователя в хронологическом порядке

### Requirement: Ритуалы дня и серии

Сервис SHALL возвращать ритуалы на сегодня через `GET /rituals/today` (утренний и вечерний, адаптированные под пользователя из памяти, со статусом выполнения и серией). Серия MUST «отдыхать», а не «сгорать»: при пропуске дней статус `resting` с `resting_days`, счётчик серии MUST NOT обнуляться.

#### Scenario: Ритуалы на сегодня

- **WHEN** пользователь запрашивает `GET /rituals/today`
- **THEN** возвращаются утренний и вечерний ритуалы с duration_seconds, completed и streak

#### Scenario: Серия после пропуска

- **WHEN** пользователь пропустил 3 дня и запрашивает ритуалы
- **THEN** серия имеет `status="resting"`, `resting_days=3`, счётчик серии сохранён (не обнулён)

### Requirement: Выполнение ритуала

Сервис SHALL фиксировать выполнение через `POST /rituals/{id}/complete` с опциональным `mood_note` (≤ 500 символов). Операция MUST быть идемпотентной в пределах дня: повторное выполнение того же ритуала в тот же день возвращает текущее состояние без дубля. Ответ MUST содержать обновлённую серию.

#### Scenario: Выполнение ритуала

- **WHEN** пользователь завершает утренний ритуал
- **THEN** выполнение зафиксировано, `completed=true`, серия обновлена (status active, count+1 при серии подряд)

#### Scenario: Повторное выполнение в тот же день

- **WHEN** пользователь повторяет `POST /rituals/{id}/complete` в тот же день
- **THEN** возвращается то же состояние без создания дубля

#### Scenario: Несуществующий ритуал

- **WHEN** пользователь завершает несуществующий ритуал
- **THEN** возвращается 404 `RITUAL_NOT_FOUND`

### Requirement: История ритуалов

Сервис SHALL возвращать историю выполнений через `GET /rituals/history` (cursor-пагинация, фильтр `kind` morning/evening).

#### Scenario: История выполнений

- **WHEN** пользователь запрашивает `GET /rituals/history?kind=evening`
- **THEN** возвращается страница выполнений вечерних ритуалов с датами и mood_note

### Requirement: Чекины состояния

Сервис SHALL фиксировать чекины через `POST /checkins` с обязательным заголовком `Idempotency-Key` (повтор с тем же ключом в течение 24 часов возвращает первый ответ без дубля). Типы и payload: `halt` (hungry/angry/lonely/tired + tension 1–10), `who5` (answers — 5 ответов 0–5, score = сумма × 4), `tension` (value 1–10). Лимит — 30 чекинов в час на пользователя (429 `RATE_LIMITED` с `Retry-After`). Ответ 201 MUST включать актуальный `clean_time_seconds` для режима recovery (иначе null).

#### Scenario: HALT-чекин

- **WHEN** пользователь режима recovery отправляет `halt`-чекин с валидным payload
- **THEN** возвращается 201 с чекином и актуальным счётчиком чистого времени

#### Scenario: WHO-5 с подсчётом score

- **WHEN** пользователь отправляет `who5`-чекин с answers [2,3,1,4,2]
- **THEN** сохранён score = (2+3+1+4+2) × 4 = 48

#### Scenario: Идемпотентность по ключу

- **WHEN** клиент повторяет чекин с тем же `Idempotency-Key` в течение 24 часов
- **THEN** возвращается первый ответ, дубль не создаётся

#### Scenario: Невалидный payload

- **WHEN** payload не соответствует схеме типа (например, tension вне 1–10)
- **THEN** возвращается 422 `VALIDATION_ERROR`

#### Scenario: Превышение лимита

- **WHEN** пользователь отправляет более 30 чекинов в час
- **THEN** возвращается 429 `RATE_LIMITED` с `Retry-After`

### Requirement: История чекинов и динамика благополучия

Сервис SHALL возвращать историю чекинов через `GET /checkins/history` (cursor-пагинация, фильтры `type`, `from`/`to`) с агрегатами: `who5_trend` (средний score по неделям) и `clean_time_seconds` (счётчик чистого времени для режима recovery).

#### Scenario: Динамика WHO-5

- **WHEN** пользователь с серией WHO-5 чекинов за несколько недель запрашивает историю
- **THEN** агрегат `who5_trend` содержит средний score по каждой неделе

#### Scenario: Счётчик чистого времени

- **WHEN** пользователь режима recovery запрашивает историю чекинов
- **THEN** агрегат `clean_time_seconds` отражает время с последнего срыва (или с начала использования режима)

### Requirement: Фоновая генерация ритуалов и напоминания

Сервис SHALL ежедневно генерировать персональные ритуалы (утро/вечер) из памяти пользователя фоновой задачей по расписанию и отправлять напоминания с учётом тихих часов пользователя. Напоминания MUST NOT приходить в тихие часы; тон — тёплый, без вины и давления.

#### Scenario: Генерация ритуалов на новый день

- **WHEN** наступает время ежедневной фоновой задачи
- **THEN** активным пользователям созданы персональные ритуалы дня, адаптированные из памяти

#### Scenario: Тихие часы

- **WHEN** время напоминания попадает в тихие часы пользователя
- **THEN** напоминание откладывается до конца тихих часов
