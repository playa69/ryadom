# Delta для sber500-dashboard

## ADDED Requirements

### Requirement: Metrics API для системы сбора

Сервис дашборда SHALL отдавать по адресу `/api/v1/metrics/daily` метрики за произвольный диапазон московских суток (Europe/Moscow): параметры `date_from` и `date_to` (обязательные, `YYYY-MM-DD`, включительно, диапазон не больше 90 дней, `date_to` не позже текущих суток). Авторизация — заголовок `Authorization: Bearer <METRICS_API_TOKEN>`: отдельный бессрочный токен, только чтение, не менее 32 символов; при утечке токен перевыпускается. С токена действует лимит не менее 10 запросов в минуту.

Ответ 200 MUST содержать `startup_id` (`ryadom`), `timezone` (`Europe/Moscow`), `generated_at` (время генерации с московским смещением) и `data` — по одной записи на каждый день диапазона, включительно, со строгим набором полей: `date`, `dau`, `llm_requests`, `tool_requests`, `total_users`, `new_users`, `is_final`. Все числа MUST быть целыми. День без активности и день раньше начала истории снимков MUST отдаваться нулями, а не пропуском. `is_final` MUST быть `false` только у текущих (не закрытых снимком) суток.

Источники данных MUST быть теми же, что у страницы и JSON дашборда: закрытые сутки — неизменяемые снимки, текущие сутки — предварительный расчёт из сырых источников. Внутренняя метрика `daily_active_account` наружу MUST NOT отдаваться. `total_users` дня без снимка MUST повторять последний известный итог, а на первый день диапазона MUST подкладываться итог последнего снимка строго раньше него, чтобы запрос куска истории не обнулял накопленную кривую. Восстановленные из журналов Cognee Tool calls (нижняя граница дней до непрерывного учёта) MUST учитываться тем же правилом «максимум из источников», что и в отчёте дашборда.

Наружу MUST уходить только агрегаты: ни текстов, ни идентификаторов людей. Endpoint MUST NOT принимать ничего кроме GET и не должен изменять состояние.

Ошибки MUST отдаваться с телом `{"error": "…"}`: 400 на неверный формат дат, `date_from` позже `date_to`, диапазон больше 90 дней и `date_to` в будущем; 401 без заголовка или с неверным токеном; 429 при превышении лимита; 5xx при внутреннем сбое (система сбора повторяет такой запрос сама).

Поверхности: dashboard

#### Scenario: Метрики за диапазон
- **WHEN** запрос `GET /api/v1/metrics/daily?date_from=2026-11-08&date_to=2026-11-14` с верным Bearer-токеном
- **THEN** ответ 200 содержит `startup_id`, `timezone` `Europe/Moscow`, `generated_at` и ровно 7 записей `data` — по одной на каждый день включительно; у закрытых дней `is_final=true` и числа совпадают со снимками, из которых отдаются `/dashboard` и `/dashboard/api` за те же сутки

#### Scenario: Текущие сутки предварительные
- **WHEN** диапазон включает текущие московские сутки
- **THEN** их запись содержит предварительные числа из того же расчёта, что у страницы, с `is_final=false`

#### Scenario: День без активности
- **WHEN** в диапазоне есть день без данных (нет активности или день раньше начала истории снимков)
- **THEN** его запись содержит нулевые метрики, `is_final=true`, а `total_users` повторяет последний известный итог

#### Scenario: Ошибки запроса
- **WHEN** запрос без токена, с неверным токеном, без дат, с датой не в формате `YYYY-MM-DD`, с `date_from` позже `date_to`, с диапазоном больше 90 дней или с `date_to` в будущем
- **THEN** ответы соответственно 401, 401, 400, 400, 400, 400 и 400, каждый с телом `{"error": "…"}`

#### Scenario: Лимит запросов
- **WHEN** с одного адреса за минуту приходит больше 30 запросов с верным токеном
- **THEN** лишние запросы получают 429 с телом `{"error": "…"}`, а после конца минуты лимит сбрасывается
