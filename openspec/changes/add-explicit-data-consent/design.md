## Context

Согласия уже записывает существующий API одним набором флагов; клиент вызывает его после входа по устройству, Telegram или подтверждения почты. Сервер не различает способ подтверждения и не требует новой версии условий. Веб и мобильный клиент имеют собственные компоненты юридической строки и свои элементы форм. Полный текст документов централизован на публичном сайте.

## Goals / Non-Goals

**Goals:**

- Сделать обязательную отметку локальным условием всех существующих путей первой записи согласия, не меняя API и не затрагивая уже принятые согласия.
- Сохранить текущие идиомы веба и Framework7, состояние черновика и необязательные настройки первого разговора.
- Дать всем клиентам один публичный адрес актуального текста согласия.

**Non-Goals:**

- Доказательство факта отметки новым полем API или отдельным видом записи в базе.
- Повторный ворот по новой версии условий.
- Изменение нативных возможностей и минимальной нативной сборки.

## Decisions

1. **Общий смысл, отдельные компоненты для двух клиентов.** В вебе обязательная отметка использует существующий `NativeCheckbox`, который не нарушает строгую CSP inline-стилем скрытого поля, в мобильном клиенте — нативный `input type="checkbox"` в текущем стиле. Компонент юридического текста получает отдельную ссылку `consentUrl`; универсальный компонент между Next.js и Framework7 не вводится.
2. **Отдельный входной ворот до чата.** Новый человек сначала видит только приветствие, обязательную отметку и «Продолжить», без поля ввода, микрофона и кнопки запуска. Продолжение переводит его на обычный главный экран с активными действиями и без повторной отметки. Обработчики запуска и регистрации дополнительно выходят без запроса при отсутствии подтверждения.
3. **Состояние только на экране.** Флажок по умолчанию `false` при каждом новом показе формы и не сохраняется в локальном хранилище. Продолжение входного ворота лишь открывает чат и не создаёт аккаунт: запись согласия выполняется при первом разговоре через существующий API. После неё работает существующее состояние аккаунта; повторная отметка на главной не нужна. Открытие документа выполняется внешней ссылкой и не вызывает запуск.
4. **Регистрация не получает новый параметр API.** Существующий признак `consented` передаётся дальше только после заполненной формы с отметкой. Это сохраняет совместимость и текущую запись после подтверждения почты.
5. **Статический `/consent`.** Страница использует общие `SiteHeader`, `LegalDocument` и `SiteFooter`; шесть пунктов оформляются нумерованным списком с жирными названиями. Предоставленный текст не сокращается. `/privacy` не редактируется, а в заключении добавляется обычная внутренняя ссылка на него.
6. **Версия условий остаётся `2026-10-04`.** Редакция отдельного согласия не подменяет версию условий. Альтернатива с повышением версии отклонена решением владельца: только новые записи согласия, без повторного запроса действующим аккаунтам.

## Risks / Trade-offs

- [Старый клиент до получения обновления продолжает показывать прежнее неявное согласие] → Ограничение принято выбором решения без изменения API; OTA доставит обновлённый JS существующим нативным сборкам, новой нативной сборки не требуется.
- [Дополнительная строка увеличивает первый экран на телефоне] → Компактная разметка, проверка 390 px и невысокого экрана; при необходимости прокрутка внутри страницы вместо скрытия обязательной отметки.
- [Клик по ссылке внутри label может переключить флажок] → Ссылки имеют собственные доступные имена и открывают документ без запуска; поведение проверяется e2e.
- [Запрет только неактивной кнопки обходится клавишей Enter] → Проверяется и визуальное состояние, и отсутствие сетевого запроса при Enter.

## Migration Plan

Миграции нет. Сначала публикуется `/consent`, затем обновляются web и OTA/PWA в рамках согласованного выката. Откат возвращает прежние клиенты и не требует изменений базы; уже записанные согласия остаются действительными.
