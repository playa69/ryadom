Задача: PROTEUS-267

# Proposal: add-yandex-metrika

## Why

Маркетингу нужна сквозная веб-аналитика в Яндекс Метрике (счётчик «Слышу Рядом», 114043323): откуда пришли, куда дошли, какая доля людей добирается до целевого действия. Счётчик нужен на всех поверхностях, а не только на лендинге, иначе воронка обрывается на переходе в продукт. Команда определила цели воронки (03.11.2026): основная — **первый разговор с 3+ репликами человека**; промежуточные — **переход в продукт** и **начало разговора (первая реплика)**. Эталон подключения — silqai-gitlab: номер счётчика берётся из окружения сервера, а не зашит в сборку; цели — JS-события `reachGoal`.

Продуктовая аналитика PostHog остаётся как есть. Метрика её не заменяет: она считает визиты и цели, PostHog — события продукта.

## What Changes

- **Один счётчик на шести поверхностях.** Номер задаёт сервер (`YANDEX_METRIKA_COUNTER_ID`), клиенты читают его из `GET /api/analytics/config` (новое необязательное поле `metrika`) и только потом загружают тег. Пустой номер — Метрика не грузится нигде. Отдельного `/runtime/analytics.js`, как в silqai, нет: у PWA и нативных оболочек нет Next-сервера, который бы его отдал, а общий конфиг уже читают все шесть поверхностей.
- **Приватность.** Запись сессий (Вебвизор) и карта кликов — только на лендинге и только если окружение разрешает; в приложении (веб, PWA, Telegram, Android, iOS) выключены при любых настройках: там разговоры, почта, SOS. Адреса страниц уходят без query и с `:id` вместо идентификаторов. Отказ человека от аналитики и Do Not Track действуют и для Метрики.
- **Три цели.** «Переход в продукт» — цель в кабинете по адресам страниц (`/app/` или `/pwa/`), кода не требует; `first_reply` и `first_dialog_3_replies` — JS-цели, их отправляет приложение (все три созданы в кабинете Метрики 03.11.2026).
- **Требования спеки.** Три новых требования в `product-analytics` и три уточнённых: прежние формулировки писались про PostHog («без cookie», «запись сессий выключена», «без `POSTHOG_KEY` аналитика выключена целиком») и теперь противоречили бы Метрике.
- **Признанные отличия от PostHog** (владелец решает, нужна ли правка политики конфиденциальности): Метрика ставит свои cookie (`_ym_*`), а адрес устройства приходит в Яндекс напрямую, без нашего прокси.

## Поверхности

| Поверхность | Статус |
|---|---|
| agent | нет |
| api | да: переменные `YANDEX_METRIKA_*`, поле `metrika` в `GET /api/analytics/config` |
| web | да: тег, цели, отказ и DNT; записи экрана нет |
| pwa | да: то же; в CSP nginx добавляются адреса Метрики |
| android | да: тот же код мобильного клиента; нужен дополнительный адрес `localhost` в счётчике (проверка на эмуляторе) |
| ios | да: тот же код; на устройстве не проверяется, пока нет сборки |
| tg | да: Mini App — сборка PWA |
| admin | нет (админка аналитики не содержит и счётчик не грузит) |
| landing | да: тег, запись экрана и карта кликов (если разрешены; номера линий помощи закрыты от записи) |

## Зависимости и миграции

- Миграций нет. Контракт `AnalyticsConfigApiResponse` меняется только добавлением необязательного поля: клиенты, выкаченные раньше, его игнорируют. Тронут `app/packages/contracts`, поэтому до сдачи нужен `release-check`.
- Нативный код не меняется, `OTA_MIN_NATIVE_BUILD` не трогаем: новый JS доезжает до Android и iOS пакетом OTA.
- В кабинете Метрики вручную (после «да» владельца): выключить «Автоматические цели» (клики по телефону и email: для линий помощи они привязаны к посетителю), добавить адрес `localhost` для нативных оболочек, если проверка покажет, что хиты отбрасываются.
- Открытых change'ей с требованиями `product-analytics` нет.

## Вне рамок

- Серверные цели через Measurement Protocol (как платежи в silqai): нужны токен и передача идентификатора посетителя на сервер. Рассмотреть позже, если клиентские цели будут терять данные из-за блокировщиков.
- Склейка посетителей по аккаунту (`setUserID`): отправляла бы в Яндекс идентификатор аккаунта.
- AppMetrica (SDK для нативных приложений), проксирование Метрики через наш домен, правка политики конфиденциальности.
