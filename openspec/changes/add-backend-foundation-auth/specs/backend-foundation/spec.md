# Дельта-спецификация: backend-foundation

## Purpose

Каркас backend-сервиса «Слышу Рядом»: единые правила конфигурации, логирования, обработки заголовков и ошибок, служебные эндпоинты и слоистая структура приложения, на которые опираются все остальные capability.

## ADDED Requirements

### Requirement: Конфигурация через типизированные настройки

Сервис SHALL читать всю конфигурацию из переменных окружения через типизированные pydantic-settings классы в одном модуле конфигурации. Каждое поле MUST иметь `validation_alias` с именем env-переменной и дефолт (кроме явно обязательных). Секреты MUST объявляться как `SecretStr` и не иметь дефолтов-значений. Прямое чтение `os.environ`/`os.getenv` вне модуля конфигурации запрещено. Конфигурация MUST быть неизменяемым синглтоном.

#### Scenario: Старт с валидной конфигурацией

- **WHEN** сервис стартует с корректно заданными env-переменными
- **THEN** конфигурация загружается в синглтон и доступна всем модулям без пересоздания

#### Scenario: Отсутствует обязательная переменная

- **WHEN** сервис стартует без обязательной env-переменной (например, секрет JWT)
- **THEN** старт прерывается с понятной ошибкой валидации до начала приёма запросов

#### Scenario: Некорректное значение критичной настройки

- **WHEN** критичная настройка (например, путь или DSN) не проходит валидацию
- **THEN** сервис падает на старте (fail-fast), а не в рантайме

### Requirement: Обработка сквозных заголовков запроса

Сервис SHALL извлекать заголовки белого списка (`x-trace-id`, `x-request-time`, `x-client-id`, `x-session-id`, `x-user-id`) в middleware один раз на входе и сохранять их в ContextVars, доступные из любого async-кода запроса. Сервис MUST NOT генерировать `x-trace-id` (rqUId) самостоятельно. В логи MUST NOT попадать заголовки вне белого списка (включая `Authorization`). Чтение `request.headers` в бизнес-логике запрещено.

#### Scenario: Запрос с полным набором заголовков

- **WHEN** входящий запрос несёт заголовки белого списка
- **THEN** их значения доступны через ContextVars во всех слоях обработки и подмешиваются в записи лога автоматически

#### Scenario: Запрос без x-trace-id

- **WHEN** входящий запрос не несёт `x-trace-id`
- **THEN** запрос обрабатывается нормально, записи лога не содержат сгенерированного rqUId

#### Scenario: Исходящий HTTP-вызов

- **WHEN** сервис выполняет исходящий HTTP-запрос к внешней зависимости
- **THEN** запрос несёт все заголовки белого списка с текущими значениями из ContextVars

### Requirement: Определение реального IP клиента

Сервис SHALL определять IP клиента для rate-limit и аудита с доверием к `X-Forwarded-For` только от trusted proxy, заданных в конфигурации (plain IP или CIDR). При доверенном прокси MUST использоваться последний адрес цепочки `X-Forwarded-For`. Без доверенного прокси MUST использоваться адрес прямого соединения.

#### Scenario: Запрос через доверенный ingress

- **WHEN** прямое соединение приходит с адреса из списка trusted proxies и присутствует цепочка `X-Forwarded-For`
- **THEN** IP клиента определяется как последний адрес цепочки

#### Scenario: Попытка подделки XFF от недоверенного источника

- **WHEN** прямое соединение приходит не от trusted proxy, но содержит `X-Forwarded-For`
- **THEN** заголовок игнорируется, IP клиента — адрес прямого соединения

### Requirement: Единый формат ошибок

Все ошибки API SHALL возвращаться в формате `{"error": {"code", "message", "details"}}`, где `code` — машиночитаемый код из каталога ниже, `message` — человекочитаемое сообщение на русском, `details` — null, объект или список полевых ошибок валидации (`[{"field", "message", "code"}]`). Ответ 429 MUST содержать заголовок `Retry-After`. Необработанные исключения MUST маппиться в `INTERNAL_ERROR` (500) без утечки внутренних деталей.

Каталог кодов (SCREAMING_SNAKE): `AUTH_TOKEN_EXPIRED` (401), `AUTH_TOKEN_INVALID` (401), `AUTH_REFRESH_TOKEN_INVALID` (401), `AUTH_INVALID_CREDENTIALS` (401), `AUTH_RESET_TOKEN_INVALID` (400), `AUTH_CODE_EXPIRED` (400), `AUTH_CODE_INVALID` (400), `AUTH_CODE_TOO_MANY_ATTEMPTS` (400), `AUTH_EMAIL_ALREADY_LINKED` (409), `AGE_RESTRICTED` (403), `CONSENT_REQUIRED` (403), `FORBIDDEN` (403), `VALIDATION_ERROR` (422), `NOT_FOUND` (404), `SESSION_NOT_FOUND` (404), `ENTRY_NOT_FOUND` (404), `FACT_NOT_FOUND` (404), `RITUAL_NOT_FOUND` (404), `NEWS_NOT_FOUND` (404), `SESSION_TRANSCRIPTS_DISABLED` (410), `SESSION_ALREADY_FINISHED` (409), `CONFLICT` (409), `RATE_LIMITED` (429), `SERVICE_UNAVAILABLE` (503), `INTERNAL_ERROR` (500).

#### Scenario: Доменная ошибка сервисного слоя

- **WHEN** сервисный слой отклоняет операцию (например, невалидный токен)
- **THEN** клиент получает ответ с соответствующим HTTP-статусом и телом `{"error": {"code": "<КОД>", "message": "<RU-текст>", "details": ...}}`

#### Scenario: Ошибка валидации тела запроса

- **WHEN** тело запроса не проходит валидацию схемы
- **THEN** клиент получает 422 с кодом `VALIDATION_ERROR` и списком полевых ошибок в `details`

#### Scenario: Непредвиденное исключение

- **WHEN** в обработчике возникает неперехваченное исключение
- **THEN** клиент получает 500 с кодом `INTERNAL_ERROR` и нейтральным сообщением, детали исключения остаются только в логе

### Requirement: Логирование

Сервис SHALL писать структурированные логи через loguru с автоматическим обогащением каждой записи полями контекста (rqUId, rqTime, systemId, gwSessionId, userId) из ContextVars. SHALL быть три раздельных sink'а: обычный лог, метрики, аудит-события. Тексты сообщений пользователей и PII MUST маскироваться до записи в лог. Служебные эндпоинты (`/health`, `/metrics`, `/openapi.json`, `/docs`) MUST NOT логироваться.

#### Scenario: Запись лога в HTTP-контексте

- **WHEN** код пишет `logger.info(...)` в обработчике запроса
- **THEN** запись автоматически содержит контекстные поля из ContextVars без явной передачи

#### Scenario: Логирование чувствительных данных

- **WHEN** в лог записывается структура, содержащая PII (email, тексты пользователя)
- **THEN** в записи оказываются маскированные значения

#### Scenario: Фоновая задача без HTTP-контекста

- **WHEN** лог пишется из фоновой задачи, где ContextVars пусты
- **THEN** контекст привязан явно (bind сохранённого rqUId) или поля контекста пусты — без ошибок сериализации

### Requirement: Security-заголовки ответов

Сервис SHALL добавлять к ответам security-заголовки: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security`; для auth-эндпоинтов — `Cache-Control: no-store`.

#### Scenario: Любой ответ API

- **WHEN** клиент получает ответ от API
- **THEN** ответ содержит перечисленные security-заголовки

#### Scenario: Ответ auth-эндпоинта

- **WHEN** клиент получает ответ от эндпоинта аутентификации
- **THEN** ответ дополнительно содержит `Cache-Control: no-store`

### Requirement: Служебные эндпоинты

Сервис SHALL предоставлять эндпоинты health (liveness/readiness) и version вне префикса `/api/v1`. Health MUST отражать состояние критичных зависимостей (PostgreSQL, Redis) для readiness. Эти эндпоинты MUST NOT требовать аутентификации и MUST NOT публиковаться наружу через ingress (фильтрация на уровне HTTPRoute).

#### Scenario: Readiness при живых зависимостях

- **WHEN** PostgreSQL и Redis доступны
- **THEN** readiness-эндпоинт возвращает успешный статус

#### Scenario: Readiness при недоступной критичной зависимости

- **WHEN** PostgreSQL или Redis недоступны
- **THEN** readiness-эндпоинт возвращает ошибку, и оркестратор снимает под с трафика

### Requirement: Слоистая структура приложения

Код сервиса SHALL быть организован в слои: роутеры (api/v1) → сервисы → репозитории → модели, с Pydantic-схемами запросов/ответов отдельно от ORM-моделей. Роутер MUST NOT обращаться к БД напрямую; зависимости MUST собираться через dependency-injection фабрики. Правила заголовков, конфигурации и логирования применяются единообразно во всех слоях.

#### Scenario: Обработка запроса

- **WHEN** запрос проходит обработку
- **THEN** роутер только валидирует схему и вызывает сервис, сервис работает через репозитории, доступ к БД инжектирован как зависимость
