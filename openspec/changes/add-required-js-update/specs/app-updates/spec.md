## MODIFIED Requirements

### Requirement: Откуда берётся политика релизов
Нативная ось SHALL читаться из переменных окружения процесса API: `MOBILE_ANDROID_MIN_VERSION_CODE`, `MOBILE_ANDROID_LATEST_VERSION_CODE`, `MOBILE_ANDROID_STORE_URL`, `MOBILE_ANDROID_DOWNLOAD_URL`, `MOBILE_IOS_MIN_VERSION_CODE`, `MOBILE_IOS_LATEST_VERSION_CODE`, `MOBILE_IOS_STORE_URL`; пустая строка означает «не задано», номера — неотрицательные целые, адреса — корректные URL. Ось JS SHALL браться из манифеста OTA-пакетов, запечённого в образ API: при `APP_ENV=prod` действует пакет варианта `prod`, при `APP_ENV=local` пакета нет (окружения staging нет). Минимальная версия JS SHALL читаться из переменной `MOBILE_JS_MIN_VERSION` (версия того же вида, что `js_version`; пустая строка — минимума нет). Политика MUST вычисляться один раз при старте процесса, поэтому изменение значений вступает в силу только после перезапуска; некорректное значение MUST останавливать запуск API с перечнем ошибок окружения, а отсутствующий или повреждённый манифест — только отключать ось JS, не мешая запуску.

Поверхности: api

#### Scenario: Правка номеров после релиза в магазине
- **WHEN** после публикации в магазине повышен `MOBILE_ANDROID_LATEST_VERSION_CODE` и API перезапущен
- **THEN** сборки Android ниже нового номера получают `runtimeUpdate` `available`

#### Scenario: Некорректное значение
- **WHEN** `MOBILE_ANDROID_MIN_VERSION_CODE` не целое число, `MOBILE_ANDROID_STORE_URL` не URL или `MOBILE_JS_MIN_VERSION` не версия (например, `latest`)
- **THEN** API при запуске завершается с перечнем ошибок окружения

#### Scenario: Окружение без пакета
- **WHEN** `APP_ENV=local` или манифеста пакетов в образе нет
- **THEN** ось JS отключена: `jsUpdate` равен `not_available`, `jsVersion` равен `null`, запуск не нарушен

#### Scenario: Пакет по окружению
- **WHEN** `APP_ENV=prod`
- **THEN** статус указывает на пакет варианта `prod`

#### Scenario: Минимум JS поднят после выката
- **WHEN** после выката образа с пакетом `0.1.0.42` задан `MOBILE_JS_MIN_VERSION=0.1.0.42` и API перезапущен
- **THEN** клиенты с версией JS ниже `0.1.0.42` получают `jsUpdate` `required`

### Requirement: Решение сервера по версии JS
Поле `jsUpdate` SHALL вычисляться только если клиент передал `js_version`, для окружения есть пакет, а нативная сборка клиента способна его выполнить (минимальная нативная сборка для пакета задаётся в коде по платформе; по умолчанию ограничений нет). Версии MUST сравниваться по сегментам как числа (недостающий сегмент равен нулю, `1.0.10` новее `1.0.9`, `1.2` равна `1.2.0`): версия клиента ниже серверной даёт `required`, если задан минимум JS и версия клиента ниже него, иначе `available`; выше серверной — `required` (откат: образ с прежней версией остаётся источником правды); равная — `not_available`. `jsBundleUrl` и `jsBundleChecksum` SHALL заполняться только при `available` и `required`, иначе быть `null`; `jsVersion` — версия пакета окружения (или `null`, если пакета нет). `jsBundleUrl` MUST строиться как `PUBLIC_APP_URL` + `/api/ota/` + имя файла, закодированное для URL. Заголовок `X-Js-Version` с мусорным значением считается версией `0`. Устаревший JS сам по себе MUST NOT давать ответ 426.

Поверхности: api

#### Scenario: Клиент отстал
- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0`
- **THEN** `jsUpdate` равен `available`, а `jsBundleUrl` и `jsBundleChecksum` заполнены

#### Scenario: Клиент ниже минимума JS
- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0` и минимуме JS `1.2.0`
- **THEN** `jsUpdate` равен `required`, а `jsBundleUrl` и `jsBundleChecksum` заполнены

#### Scenario: Клиент между минимумом и пакетом
- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0` и минимуме JS `1.1.0`
- **THEN** `jsUpdate` равен `available`

#### Scenario: Минимум выше пакета
- **WHEN** минимум JS `2.0.0` выше версии пакета `1.2.0`
- **THEN** клиент с `js_version=1.1.5` получает `required`, а клиент с `js_version=1.2.0` — `not_available`

#### Scenario: Клиент новее сервера
- **WHEN** клиент с `js_version=1.3.0` запрашивает статус при версии пакета `1.2.0`
- **THEN** `jsUpdate` равен `required`

#### Scenario: Версии совпадают
- **WHEN** `js_version` равна версии пакета
- **THEN** `jsUpdate` равен `not_available`, `jsBundleUrl` и `jsBundleChecksum` равны `null`

#### Scenario: Клиент без OTA
- **WHEN** запрос не содержит `js_version`
- **THEN** `jsUpdate` равен `not_available`

#### Scenario: Сравнение сегментов числами
- **WHEN** сравниваются `1.0.10` и `1.0.9`
- **THEN** `1.0.10` считается новее

#### Scenario: Нативная сборка слишком старая для пакета
- **WHEN** для платформы задана минимальная нативная сборка для пакетов, а клиент старше этой сборки
- **THEN** `jsUpdate` равен `not_available`, `jsBundleUrl` равен `null`

#### Scenario: Устаревший JS не отрезан
- **WHEN** сборка не ниже нативного минимума с версией JS ниже минимума JS обращается к `GET /api/auth/me`
- **THEN** ворота версий пропускают запрос, ответа 426 нет

### Requirement: Сборка OTA-пакета и манифест
Сборка образа API SHALL выполнять сборку OTA-пакета: собрать JS варианта `prod`, упаковать содержимое `dist/client` в zip так, чтобы `index.html` лежал в корне архива, с прямыми слэшами в путях, назвать его `ryadom-prod-<версия>.zip`, посчитать SHA-256 архива и записать `ota/manifest.json` вида `{ "prod": { "version", "file", "checksum" } }`. Версия пакета SHALL быть `<номер версии мобильного клиента>.<OTA_BUILD_NUMBER>` (без номера — `0`), и JS внутри пакета MUST сообщать серверу ровно эту версию. `OTA_BUILD_NUMBER` MUST быть целым числом из 1–6 цифр, иначе сборка прерывается. Адреса `VITE_PROD_API_URL` и `VITE_PROD_WEB_URL` передаются в сборку образа аргументами и вшиваются в пакет; каталог `ota` MUST копироваться в образ API рядом с серверным бандлом. Пакет уезжает тем же деплоем, что и сервер, отдельного шага публикации нет. Пакет варианта `dev` не собирается и не раздаётся.

Поверхности: api · android · ios

#### Scenario: Сборка с номером
- **WHEN** образ собирается при версии `0.1.0` и `OTA_BUILD_NUMBER=42`
- **THEN** создаётся `ryadom-prod-0.1.0.42.zip`, а в манифесте его `version` равна `0.1.0.42`

#### Scenario: Сборка без номера
- **WHEN** `OTA_BUILD_NUMBER` не задан
- **THEN** версия пакета равна `0.1.0.0`

#### Scenario: Пакет сообщает свою версию
- **WHEN** устройство применило пакет `0.1.0.42` и запрашивает статус
- **THEN** запрос содержит `js_version=0.1.0.42`, и сервер с тем же пакетом отвечает `jsUpdate` `not_available`

#### Scenario: Неверный номер сборки
- **WHEN** `OTA_BUILD_NUMBER` равен `abc` или содержит больше шести цифр
- **THEN** сборка прерывается, манифест не записывается

#### Scenario: Состав архива
- **WHEN** архив распакован
- **THEN** `index.html` лежит в его корне

#### Scenario: Ошибка шага сборки
- **WHEN** сборка JS или упаковка завершается ошибкой
- **THEN** сборка образа прерывается, манифест не записывается

### Requirement: Нативное приложение сообщает версии в заголовках
Нативное приложение SHALL добавлять к каждому запросу к API (включая обновление токена и выход) заголовки `X-Platform` (`android` или `ios`), `X-App-Version` (номер сборки) и, только если сборка на канале OTA, `X-Js-Version` — версию работающего JS: `<номер версии мобильного клиента>.<OTA_BUILD_NUMBER на момент сборки JS>` (без номера — `0`); у применённого пакета OTA это его версия из манифеста, у JS, встроенного в нативную сборку, — номер, с которым собирался её JS. Если номер сборки прочитать не удалось, заголовки MUST NOT добавляться. Браузер (веб-клиент, PWA, Telegram Mini App) MUST NOT отправлять эти заголовки.

Нативная сборка участвует в OTA (отправляет `X-Js-Version` и параметр `js_version`) только если это вариант `prod`: пакет собирается только для него. Вариант `dev`, направленный на `prod` или `local`, MUST NOT отправлять версию JS и получать чужой пакет, иначе чужой минимум мог бы его заблокировать.

Поверхности: android · ios

#### Scenario: Запрос из боевой сборки
- **WHEN** (Android) боевая сборка обращается к API
- **THEN** запрос содержит `X-Platform: android`, `X-App-Version` и `X-Js-Version`

#### Scenario: Версия применённого пакета
- **WHEN** (Android) на устройстве работает пакет `0.1.0.42`
- **THEN** запросы к API несут `X-Js-Version: 0.1.0.42`, а запрос статуса — `js_version=0.1.0.42`

#### Scenario: Встроенный JS без номера сборки
- **WHEN** (Android) JS нативной сборки собран при версии `0.1.0` без `OTA_BUILD_NUMBER`
- **THEN** сборка сообщает `X-Js-Version: 0.1.0.0` и получает любой пакет `0.1.0.N` с N больше нуля

#### Scenario: Dev-сборка на prod
- **WHEN** (Android) сборка варианта `dev` переключена на среду `prod`
- **THEN** запросы статуса и API идут без версии JS, и пакет не предлагается

#### Scenario: Номер сборки недоступен
- **WHEN** нативное приложение не смогло прочитать номер сборки
- **THEN** запросы уходят без заголовков версий
