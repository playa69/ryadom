# Proposal: add-required-js-update

## Why

Механизм обновлений должен давать четыре рычага: мягко и жёстко предложить новую нативную сборку и мягко и жёстко
обновить JS по воздуху (OTA). Проверка кода на 27.10.2026 показала, что из четырёх работают три, и то не до конца:

- **Версия JS не совпадает с версией пакета.** Пакет в манифесте называется `<версия клиента>.<OTA_BUILD_NUMBER>`
  (например, `0.1.0.42`), а сам пакет и встроенный в нативную сборку JS сообщают серверу версию `package.json`
  (`0.1.0`). Устройство никогда не догоняет сервер: после применения пакета ему снова предлагается тот же пакет,
  событие «пакет применён» не отправляется, а откат образа (более старый пакет на сервере) приходит мягко, при
  следующем уходе в фон, вместо немедленного применения — аварийный выключатель не срабатывает.
- **Жёстко обновить JS нельзя.** `jsUpdate` равен `required` только при откате и при первом запуске после установки
  новой нативной сборки. Выкатить исправление и заставить все устройства применить его сразу оператор не может.

Мягкое (`MOBILE_<ПЛАТФОРМА>_LATEST_VERSION_CODE`) и жёсткое (`MOBILE_<ПЛАТФОРМА>_MIN_VERSION_CODE`) обновление
нативной сборки устроены правильно; меняется только их описание для оператора.

## What Changes

- **Версия JS едина.** Пакет OTA и JS нативной сборки сообщают версию `<версия клиента>.<номер сборки>` — ту же, что
  записана в манифесте пакета; номер сборки — `OTA_BUILD_NUMBER` (без него — `0`). Неверный номер сборки
  останавливает сборку.
- **Минимальная версия JS.** Новая переменная окружения API `MOBILE_JS_MIN_VERSION` (пусто — не задано): клиент с
  версией JS ниже неё получает `jsUpdate` `required` и применяет пакет сразу, с экраном «Обновляемся». Выше минимума,
  но ниже пакета — по-прежнему `available` (тихая загрузка). Устаревший JS по-прежнему не получает 426.
- **Документация оператора.** В скилле `deploy` — как выполнить каждый из четырёх рычагов и откат пакета.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `app-updates`: MODIFIED «Откуда берётся политика релизов» (переменная `MOBILE_JS_MIN_VERSION`), «Решение сервера
  по версии JS» (минимум JS даёт `required`), «Сборка OTA-пакета и манифест» (пакет сообщает свою версию),
  «Нативное приложение сообщает версии в заголовках» (какую версию JS сообщает клиент).

## Impact

- `app/apps/mobile`: сборка JS (`vite.config.ts`, `scripts/build-ota-bundle.mjs`), клиент обновлений
  (`src/client/lib/app-update.ts`).
- `app/services/api`: политика релизов (`src/lib/release-policy.ts`); `app/packages/core`: схема окружения.
- `k8s/app/00-app-config.yaml` (описание ключей политики релизов), скилл `deploy`.
- Контракт `GET /api/app-status` не меняется: те же поля и значения. Миграций нет.
- Совместимость: уже установленные сборки сообщают `0.1.0`, это ниже любого пакета `0.1.0.N`, поэтому они
  получают пакет как раньше; после его применения сообщают уже его версию.
- Зависимостей от открытых change'ей нет.

## Вне рамок

- Ответ 426 для устаревшего JS (отрезает только нативный минимум, как и раньше).
- Плановая проверка статуса во время работы приложения: жёсткое обновление JS применяется при ближайшей проверке
  (запуск, возврат на передний план, появление сети, ответ 426).
- Сборка нативных релизов в CI: в репозитории её нет; как передать номер сборки — в `design.md`.
