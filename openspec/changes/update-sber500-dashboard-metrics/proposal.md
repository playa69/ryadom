# Обновить метрики дашборда Sber500

## Why

Дашборд для организаторов Sber500 (`/dashboard`) считает метрики по старым определениям от 11.11.2026: «активные» —
больше 10 реплик за сутки, «пользователи» — больше 3 реплик за всё время, «вызовы LLM» — все трассы Langfuse, а
тестовый трафик команды и автотесты не исключается. Владелец дал новые определения: настоящий DAU (≥1 сообщение),
новые и всего пользователи, точный учёт вызовов LLM, инициированных действиями пользователей, без приравнивания
трасс к вызовам, и поле вызовов инструментов. Кроме того, сейчас числа за прошлые сутки пересчитываются по живым
данным: удаление разговоров и аккаунтов переписывает прошлое. Нужен ежедневный стабильный снимок.

После выката 0.2.0 (17.11.2026) обнаружено: сохранённая история сообщений в базе агента неполна — дни
11–16.11.2026 в `messages` отсутствуют вовсе (DAU и вызовы за эти дни — 0 при живых разговорах), провалы есть
и в другие дни; живые трассы Langfuse за эти дни сохранились. Сообщения нужно восстанавливать из трейсинга
и считать по объединению источников, а снимки 05.11–16.11 — пересчитать.

## What Changes

- **Новые определения метрик** за сутки Europe/Moscow, из всех метрик исключается трафик не `real`
  (test/internal/боты/автотесты, по `traffic_type` аккаунта в базе приложения):
  - `dau` — уникальные аккаунты с ≥1 пользовательским сообщением за сутки;
  - `daily_active_account` — внутренняя метрика: уникальные аккаунты со строго >10 пользовательскими сообщениями
    (старое «активные»);
  - `new_users` — аккаунты (включая анонимные), впервые отправившие ≥1 сообщение в эти сутки;
  - `total_users` — накопленный итог: предыдущий снимок + `new_users`, удалённые аккаунты не вычитаются;
  - `llm_requests` — логические вызовы API LLM любых провайдеров, инициированные действиями пользователей
    (ответы в диалоге и вызванные разговором итоги, извлечение памяти, оценка настроения); технические ретраи
    одного вызова считаются один раз, чисто системные операции (прогревы, плановые сводки) не считаются;
  - `tool_requests` — успешно выполненные логические вызовы агента к серверу памяти (Cognee как MCP/tool
    server): поиск/чтение, запись (add+cognify — один логический вызов), удаление; ошибки и отказы не
    считаются, ретрай после 401 внутри одного вызова не дублирует метрику, действия в UI без агента не
    считаются.
- **Минимальная инструментация трейсинга агента**: на каждый логический вызов к Cognee — одна запись типа TOOL
  в Langfuse (имя операции, исход успех/ошибка, трасса с userId аккаунта; без текстов и содержимого памяти).
  По коду подтверждено (`agent/app/clients/cognee.py`): ретрай после 401 живёт внутри `_send`, логин и
  вспомогательное чтение списка датасетов — служебные и отдельных записей не создают. Нового журнала в БД нет.
- **Источник `llm_requests` — Langfuse, но не трассы**: агент уже создаёт по одной записи типа GENERATION на
  логический вызов модели (`start_turn` в `agent/app/core/tracing.py`); по коду подтверждено, что ретраи внутри
  клиентов новых записей не создают, а кризисный фиксированный текст, озвучка, прогревы и плановые сводки
  отличаются по имени записи и наличию userId трассы. Инструментация агента не меняется.
- **BREAKING** для JSON `/dashboard/api`: вместо `active_users`, `llm_calls`, `users_total` в каждом дне — поля
  `dau`, `llm_requests`, `tool_requests`, `total_users`, `new_users`, `daily_active_account`. Потребитель один
  (организаторы Sber500), переход объявляется, версионирование не вводится.
- **Ежедневный снимок**: после полуночи по Москве сутки закрываются в собственное хранилище дашборда (только
  агрегаты: дата и шесть чисел, без текстов и id людей) и дальше не пересчитываются. История до выката
  восстанавливается разовым backfill: `new_users` — по первому известному сообщению аккаунта (меньшее из
  `first_reply_at` и первого сохранённого сообщения в базе агента, дедупликация по аккаунту), потому что
  `first_reply_at` появился недавно и у legacy-аккаунтов остаётся NULL навсегда; `llm_requests` — из записей
  GENERATION Langfuse в пределах доступной истории; `tool_requests` — только со дня включения TOOL-записей
  агентом, дата начала честно названа на странице. Backfill и catch-up закрывают только завершённые сутки.
- **Период отчёта — весь конкурс**: с 2026-11-05 по текущие московские сутки включительно, а не последние 7
  полных суток. Прошлые сутки — по-прежнему только неизменяемые снимки; текущие сутки — реальные
  предварительные данные из сырых источников, обновляемые при каждом обновлении часового кэша, снимком не
  закрываются и в хранилище не пишутся. Состав из семи полей дня JSON (`date` + шесть метрик) не меняется.
- **Восстановление сообщений из Langfuse (версия 0.2.1)**: «сообщения» для `dau`/`daily_active_account`
  считаются по объединению базы агента и записей GENERATION `live_turn_voice`/`live_turn_text` (одна трасса —
  одно сообщение, дедупликация по (сутки, аккаунт, traceId), исключение test/internal и пустого userId); для
  пары «день, аккаунт» — max двух источников, не сумма, чтобы одни и те же ходы не считались дважды. Первый
  известный день `new_users` — минимум трёх источников (`first_reply_at`, первое сохранённое сообщение,
  первая live-turn трасса). Расчёт единый для снимков, backfill и предварительных текущих суток. Снимки
  05.11–16.11.2026, записанные 0.2.0 по неполной базе, пересчитываются отдельно: только после разрешения
  владельца на удаление этих строк и повторный backfill из образа 0.2.1.
- **Источники**: дашборд читает базы `agent` и `app` (обе — только чтение) и API Langfuse (как сейчас), пишет
  только в свою базу снимков. Сервис перестаёт быть чисто read-only: запись — только агрегаты в свою базу.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `sber500-dashboard`: определения и состав метрик, поля JSON, стабильность прошлых суток (снимки), источники
  данных и нагрузка на них.

## Impact

- **Поверхности**: dashboard — да; agent — да (минимальный трейсинг TOOL-вызовов памяти в
  `agent/app/core/tracing.py` и точках клиента Cognee, плюс тесты); api, web, pwa, android, ios, tg, admin,
  landing — нет.
- **Код**: `dashboard/app.py` (определения, запросы к базам и Langfuse, снимки, страница, JSON),
  `dashboard/tests/test_app.py`, `dashboard/README.md`; `agent/app/core/tracing.py` (TOOL-наблюдения),
  `agent/app/clients/cognee.py` / `agent/app/memory/*` (точки вызова), `agent/tests/` (тесты трейсинга).
- **Инфраструктура** (`k8s/dashboard/` + база): новая база `dashboard` в кластере CNPG `ryadom-db` с одной таблицей
  снимков; в Secret `dashboard-secrets` добавляются `APP_DATABASE_URL` (база `app`, чтение) и
  `DASHBOARD_DATABASE_URL` (своя база, запись); ключи Langfuse остаются — дашборд продолжает читать API Langfuse.
  Сетевая политика к `ryadom-db` и Langfuse уже есть.
- **Порядок выката**: сначала образ агента с TOOL-трейсингом (записи начинают появляться), затем образ
  дашборда `0.2.0` и backfill.
- **Секреты**: новые записи в Lockbox, значения хранятся у администратора; в репозитории — только ключи Secret'а.
- **Миграция API**: `/dashboard/api` меняет поля дней (см. BREAKING выше); страница `/dashboard` показывает новые
  названия и определения.
- **Зависимости от других change'ей**: нет (открытые change'и `sber500-dashboard` и точки трейсинга агента не
  трогают).
- **Вне рамок**: инструментация будущих tool/function calls помимо памяти (когда они появятся, их записи TOOL
  попадут в тот же подсчёт); изменения api приложения и PostHog; сутки по Москве остаются фиксированными для
  всех.
