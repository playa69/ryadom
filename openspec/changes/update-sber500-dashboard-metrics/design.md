# Дизайн: метрики дашборда Sber500 v2

## Context

Сейчас `dashboard/app.py` раз в час пересчитывает всё по живым источникам: база `agent` (таблицы `dialogs`,
`messages`) для реплик и API метрик Langfuse (все трассы) для «вызовов LLM». Прошлые сутки не закреплены:
удаление разговора или аккаунта меняет вчерашние числа. Сервис работает в read-only сессии и ничего не пишет.

Факты об источниках, на которых строится дизайн:

- База `agent` (CNPG `ryadom-db`): `messages` (role, created_at), `dialogs` (user_id — id аккаунта приложения).
  Сохранённая история `messages` неполна (подтверждено 17.11.2026): дни 11–16.11.2026 отсутствуют вовсе,
  провалы есть и в другие дни; живые трассы Langfuse за эти дни при этом сохранились — см. D8.
- База `app`: `users` (`properties->>'traffic_type'` = `real`/`test`/`internal`; отсутствие метки = real;
  `is_deleted` — мягкое удаление, строка остаётся), `user_reply_counts` (по строке на аккаунт: `day`, `replies`,
  `first_reply_at`). Миграция 0014 завела строки `replies=0, first_reply_at=NULL` всем аккаунтам, существовавшим
  на её момент, а обработчик `CountReplyCommand` при конфликте `first_reply_at` НЕ обновляет — то есть у
  legacy-аккаунтов (в том числе ни разу не говоривших) `first_reply_at` остаётся NULL навсегда, и их первое
  сообщение после миграции этим полем не отмечается.
- Разговоры с галочкой «Не сохранять этот разговор» не хранятся нигде: ни в базе агента, ни в
  `user_reply_counts` (шлюз пропускает `countReply` для unsaved). Это общая граница всех метрик по сообщениям,
  включая DAU продукта в PostHog.
- **Langfuse: какие записи реально создаются** (проверено по `agent/app/core/tracing.py` и точкам вызова).
  Записи типа GENERATION создаёт только `Tracer.start_turn`; всё остальное (распознавание, озвучка внутри
  диалога) — SPAN (`start_span`) и в выборку GENERATION не попадает. Полный перечень GENERATION в агенте:

  | Имя записи | Где | Это |
  |---|---|---|
  | `live_turn_voice`, `live_turn_text` | `dialog_session.py` | логический вызов модели на реплику человека (оба голосовых пути) |
  | `live_turn_recovery` | `dialog_session.py` (`metadata.recovery=true`) | технический повтор просьбы ответить на реплику, оставшуюся без ответа — ретрай, не новый вызов |
  | `text_turn` | `dialog_session.py` (`metadata.crisis=true`) | кризисный путь: говорится фиксированный текст, вызова модели НЕТ |
  | `mood_classify_sber`, `mood_classify_gemini` | `sber_voice.py`, `mood_classifier.py` | оценка настроения реплики; прогрев `warm()` зовёт `classify("привет")` без userId |
  | `dialog_recap` | `services/recaps.py` | итог разговора (вызван разговором) |
  | `memory_extract`, `memory_instruct` | `memory/extractor.py` | извлечение памяти после разговора / правка по просьбе (вызваны действиями человека) |
  | `weekly_digest` | `api/digests.py` | плановая сводка недели — системная |
  | `gemini_tts_phrase` | `gemini_live.py` (tags `tts`, userId пуст) | озвучка фраз через live-модель: обращение к модели, но не LLM-ответ |

  **Ретраи.** Ретраи внутри клиентов (у `mood_classify_sber` цикл `for attempt in (1, 2)`, у дайджеста цикл
  попыток) живут внутри одной записи: запись создаётся один раз до цикла. Ретраи, видимые как отдельные записи,
  — только `live_turn_recovery`, и они отличаются по имени. Правок трейсинга не требуется: существующих имён и
  `metadata.recovery` достаточно, чтобы отличить ретрай.
  **userId** записывается на трассе (`update_trace(user_id=...)`), а не на observation: выборка GENERATION
  связывается с трассами по `traceId`, и только у трассы читается userId. У прогревов (`warm()`,
  `gemini_tts_phrase`) userId пуст — это и есть их отличие от пользовательских вызовов с тем же именем.
- **Cognee (сервер памяти)**: REST-клиент `agent/app/clients/cognee.py`. Реально вызываемые операции
  (по `agent/app/memory/cognee_backend.py` и `memory/indexer.py`): `recall_chunks` (поиск CHUNKS в фоне на
  реплику человека), `read_consent` (зерно согласия), `add_document` (`/add` + `/cognify` — запись транскрипта
  после разговора), `delete_document` (удаление документа разговора), `forget_dataset` (удаление всей памяти);
  `recall` (GRAPH_COMPLETION) и `remember` сейчас не вызываются, но остаются публичными методами клиента.
  Ретрай в клиенте один: протухший токен (401) → перелогин и повтор внутри `_send`; логин (`/auth/login`) и
  вспомогательный `_dataset_id` (GET /datasets) — служебные обращения, а не операции памяти. Сейчас эти вызовы
  не создают никаких записей в Langfuse. Точки вызова знают `user_id` (датасет строится из него), в том числе
  фоновые (indexer после разговора, очередь `memory_outbox`). SDK Langfuse 3.15 (в `.venv` агента) умеет
  observations типа TOOL: `start_observation(name=..., as_type="tool")`, `trace_context` позволяет привязать
  запись к существующей трассе, а `update_trace(user_id=...)` — выставить аккаунт на трассе.

## Goals / Non-Goals

**Goals:**

- Шесть метрик по определениям владельца за московские сутки, без трафика test/internal/ботов/автотестов.
- Отчёт за весь период конкурса с 2026-11-05 по текущие московские сутки включительно: завершённые сутки —
  неизменяемые снимки, текущие сутки — реальные предварительные данные из сырых источников.
- Точный `llm_requests`: логические вызовы LLM, инициированные действиями пользователей, ретраи как один вызов.
- Неизменяемый ежедневный снимок: прошлое не переписывается удалением данных.
- Минимальное хранение у дашборда: только дата и шесть целых чисел, без текстов и идентификаторов людей.
- Дашборд по-прежнему ничего не пишет в базы `agent` и `app`.

**Non-Goals:**

- Инструменты учёта tool calls (их пока нет; `tool_requests` = 0).
- Почасовые/реал-тайм метрики, алерты, Grafana-дашборды.
- Учёт разговоров в режиме «не сохранять» — их не видит ни один существующий источник (см. Context).
- Изменения трейсинга агента: существующих записей GENERATION достаточно (см. Context).

## Decisions

### D1. `llm_requests` из записей GENERATION Langfuse

Считаются записи типа GENERATION за московские сутки, у которых:

1. имя в списке пользовательских вызовов: `live_turn_voice`, `live_turn_text`, `mood_classify_sber`,
   `mood_classify_gemini`, `dialog_recap`, `memory_extract`, `memory_instruct`;
2. у трассы есть userId (отсекает прогревы: `warm()` классификатора и любые записи без человека);
3. userId не входит в множество test/internal из базы `app` (та же механика исключения, что у остальных метрик).

Не считаются (по имени): `text_turn` (кризис, вызова модели нет), `live_turn_recovery` (технический ретрай уже
посчитанного хода), `gemini_tts_phrase` (озвучка), `weekly_digest` (плановая сводка). Правило «ретрай = один
вызов» выполняется самим устройством трейсинга: запись одна на логический вызов (см. Context).

Связь с трассами без выдумывания возможностей API: публичный API Langfuse отдаёт списки —
`GET /api/public/observations?type=GENERATION&fromStartTime=…&toStartTime=…` (постранично; у записи есть
`name`, `startTime`, `traceId`) и `GET /api/public/traces?fromTimestamp=…&toTimestamp=…` (у трассы есть `id` и
`userId`). Дашборд выгружает оба списка за закрываемые сутки, сводит по `traceId` и считает в памяти. Метрики-
эндпоинт (`/api/public/metrics`), которым дашборд пользуется сейчас, для `llm_requests` не подходит: агрегация
по observations не даёт userId трассы и не позволяет исключить test/internal — им продолжают пользоваться только
если понадобится сверка порядка величин. Имена записей зашиты списком в коде дашборда: новое имя GENERATION в
агенте в метрику не попадёт, пока его осознанно не добавят, — это защита от случайного завышения, а не пробел
(новые имена проходят ревью кода агента, задача на пополнение списка — в tasks).

Отвергнутые альтернативы источника `llm_requests`:

- **Все трассы Langfuse** (текущее поведение) — трасса это ход/задача, а не вызов модели; кризисные тексты,
  озвучка и плановые сводки считаются наравне с ответами людям.
- **`model_usage` базы агента** — не учёт вызовов: строка на direction/modality расхода (у live несколько строк
  на вызов), вызванные разговором фоновые вызовы (recap, memory, mood вне диалога) в таблицу не попадают,
  привязка к диалогу обнуляется при чистке.
- **Новый журнал в базе агента** — дублирует то, что Langfuse уже фиксирует точно (проверено по коду); отвергнуто
  владельцем.
- **Prometheus `agent_component_calls_total`** — правильная гранулярность, но нет привязки к аккаунту и нет
  истории для backfill; остаётся для сверки порядка величин.

### D2. `tool_requests`: TOOL-observations Langfuse для вызовов памяти

Минимальная инструментация агента (без журнала в БД):

- В `Tracer` добавляется метод `start_tool(name, *, user_id, metadata)` — по образцу `start_turn`, но запись
  типа TOOL (`client.start_observation(name=name, as_type="tool")`, SDK 3.15 это умеет) и сразу
  `update_trace(user_id=user_id, session_id=...)`. Каждый вызов памяти — **своя трасса с одной TOOL-записью**:
  фоновые операции (indexer после разговора, outbox-удаления) идут, когда трасса хода уже закрыта, и надёжного
  способа прикрепиться к ней нет — поэтому не прикрепляемся, а создаём новую трассу с тем же userId (и
  session_id = id диалога, где он известен). Это корректно для метрики: связь с аккаунтом идёт через userId
  трассы, как у GENERATION. Input/output не пишутся вовсе, metadata — только имя операции и короткие флаги без
  текстов (маскирование `_mask_metadata` действует и здесь).
- Инструментация — на уровне публичных методов `CogneeClient`, через обёртку, которой точка вызова передаёт
  `user_id`: `recall`/`recall_chunks`/`read_consent` → `memory_search`, `add_document`/`remember`
  (add+cognify) → `memory_write` (один логический вызов записи), `delete_document` → `memory_delete_document`,
  `forget_dataset` → `memory_forget_dataset`. Логин, `_dataset_id`/`dataset_exists` и 401-ретрай внутри `_send`
  записей не создают: `_send` — деталь транспорта одного логического вызова, поэтому повтор после 401 метрику
  не дублирует.
- Исход: метод завершился без исключения (и для поиска — с HTTP 200) → запись успешна (level по умолчанию);
  исключение/не-200 → запись с `level=ERROR`. Дашборд считает только успешные.
- UI-действия без агента не считаются автоматически: записи создаёт только агент.

Подсчёт на стороне дашборда — как у `llm_requests` (D1): `GET /api/public/observations?type=TOOL` за
закрываемые сутки, связь с трассами по `traceId`, успех по `level`, исключение test/internal по userId из базы
`app`. Имена — константа-список в `dashboard/app.py`.

Отвергнутые альтернативы: счётчик в базе агента (владелец отклонил новый журнал БД); Prometheus
`agent_component_calls_total{component=memory}` (уже есть, но без исхода успеха в привязке к аккаунту и без
истории для backfill — остаётся для сверки порядка величин).

### D3. Источники остальных метрик

| Метрика | Источник | Почему |
|---|---|---|
| `dau`, `daily_active_account` | объединение двух разбивок «день × user_id → число сообщений»: `agent.messages` (role='user') ⋈ `dialogs` и восстановленные из Langfuse live-turn ходы (D8), max по паре «день, аккаунт»; исключение по `app.users.traffic_type` | Сохранённая история неполна (дни 11–16.11.2026 в `messages` отсутствуют, провалы есть и в другие дни): один источник занижает, сумма двух задваивает — max берёт более полный |
| `new_users` | первый известный день аккаунта = минимум из `user_reply_counts.first_reply_at`, `min(messages.created_at)` по аккаунту в базе `agent` и первой live-turn трассы Langfuse, дедупликация по аккаунту; исключение test/internal | `first_reply_at` у legacy-аккаунтов NULL навсегда (см. Context), а база агента потеряла часть истории — поэтому три источника; `min(messages)` и live-turn трассы покрывают аккаунты, которых нет в счётчике реплик |
| `total_users` | накопленный итог по снимкам: вчерашний `total_users` + сегодняшний `new_users` | Определение владельца («без вычитания удалённых») выполняется самой схемой, а не запросом |
| `llm_requests` | D1 (Langfuse GENERATION) | Единственный существующий источник с гранулярностью «логический вызов» и привязкой к аккаунту |
| `tool_requests` | D2 (Langfuse TOOL) | Тот же механизм, что у `llm_requests`; записи создаёт минимальная инструментация агента этого change'а |

Устойчивое продолжение `new_users` после выката: каждый ночной снимок считает кандидатов из обоих источников
(новые `first_reply_at` за сутки + legacy-аккаунты с NULL, чей `min(messages)` пал на эти сутки), дедупликация по
аккаунту гарантирует, что аккаунт считается новым ровно один день за всю историю. Со временем все активные
аккаунты получают `first_reply_at`, и доля второго источника сходит на нет.

Связность двух баз: SQL-джойна между `agent` и `app` нет (разные базы одного кластера). Сервис берёт из базы
`agent` помянтную разбивку «день × user_id → число сообщений» и первые дни аккаунтов, из базы `app` — множество
id с `traffic_type != 'real'` и пары `user_id → first_reply_at`, из Langfuse — записи GENERATION и TOOL и трассы,
и сводит всё в памяти процесса. Наружу уходят только суммы; id живут внутри одного пересчёта и в логи не пишутся.

### D4. Хранилище снимков: своя база `dashboard` в CNPG `ryadom-db`

Одна база `dashboard` в существующем кластере, одна таблица:

```
daily_metrics(day date PRIMARY KEY,
              dau int, daily_active_account int, new_users int,
              total_users int, llm_requests int, tool_requests int,
              computed_at timestamptz)
```

Почему так:

- Дашборд остаётся read-only к чужим базам и Langfuse; запись — только в свою. Это минимальное расширение модели
  доступа: один новый пользователь БД с правами только на `dashboard.daily_metrics`.
- Альтернатива «писать снимки в базу `app`» смешивает агрегаты отчётности с боевой схемой приложения и требует
  выдавать сервису дашборда запись в чужую базу — хуже по изоляции.
- Альтернатива «файл на PVC» не переживает пересоздание пода без выделения volume и ломает примитивное
  развёртывание (readOnlyRootFilesystem, emptyDir только для /tmp).

Строка снимка пишется один раз (`INSERT ... ON CONFLICT (day) DO NOTHING`): повторный запуск не переписывает
прошлое даже при ошибке в коде расчёта.

### D5. Расписание снимка и обслуживание страницы

- Отчёт покрывает каждый день конкурса с 2026-11-05 по текущие московские сутки включительно (а не последние
  7 полных суток). Состав полей дня JSON прежний: `date` и шесть метрик.
- Завершённые сутки читаются только из `daily_metrics` — неизменяемые снимки.
- Текущие сутки снимком не закрываются. При каждом обновлении часового кэша их шесть метрик считаются из
  сырых источников (базы `agent` и `app`, API Langfuse) по тем же определениям, что и снимок, и добавляются
  в отчёт последним предварительным днём; в `daily_metrics` они не пишутся. Предварительные числа могут
  уточняться до закрытия суток (опоздавшие записи Langfuse, удалённые в течение дня разговоры) — после снимка
  в 00:15 день фиксируется навсегда. `total_users` текущих суток = `total_users` снимка за вчера +
  `new_users` текущих суток: цепочка итога остаётся аддитивной.
- Фоновый таймер в процессе: в 00:15 Europe/Moscow считается вчерашние сутки из сырых источников и пишется
  снимок (15 минут — запас на опоздавшие записи, фоновые вызовы после разговора на границе суток и доставку
  трейсинга; Langfuse SDK шлёт фоном, пауза покрывает его очередь).
- При старте и после каждого снимка — catch-up: каждый завершённый день периода без строки в `daily_metrics`
  досчитывается из сырых источников и дописывается (пробелы после простоя закрываются сами). Текущие сутки
  catch-up не закрывает.
- Запросы страницы и JSON обслуживаются из кэша в памяти (не дольше часа): хранилище снимков и сырые
  источники читаются при обновлении кэша, а не на каждый запрос. При недоступности своей базы или сырых
  источников отдаётся последний удачный отчёт из памяти, при холодном старте без базы — 503.
- Один под (replicas: 1) остаётся: гонки двух писателей не бывает, `ON CONFLICT DO NOTHING` страхует ретраи.

### D6. Backfill истории

Один раз при выкате отдельной Job **до запуска нового Deployment**, идемпотентно (пишет только дни без снимка). Backfill
закрывает только завершённые сутки (по вчера по Москве включительно): текущие сутки снимком не пишутся, в отчёте они —
предварительные из сырых источников (D5). История
обрабатывается окнами не больше 7 суток, каждое окно сохраняется до загрузки следующего: вся история Langfuse не
собирается в память одним списком. Одновременная работа Job и фонового snapshotter недопустима, иначе catch-up пода
может закрыть дни до backfill и закрепить неверную базу `total_users`.

1. `dau`, `daily_active_account` за прошлые сутки — по объединению базы `agent` и восстановленных из
   Langfuse live-turn ходов (D8): max по паре «день, аккаунт», исключение test/internal (метки
   `traffic_type` текущие: аккаунт, помеченный тестовым сегодня, вычитается из всей истории; принимаемое
   допущение).
2. `new_users` — по правилу D8 (минимум из `first_reply_at`, `min(messages)` и первой live-turn трассы,
   дедупликация по аккаунту; первые live-turn дни накапливаются через границу окон).
   Честное ограничение: первые сообщения, физически удалённые до backfill (удалённые аккаунты и разговоры), не
   восстанавливаются — глубина истории `new_users` занижена на уже потерянные данные.
3. `llm_requests` — из записей GENERATION Langfuse по правилу D1 **в пределах доступной истории Langfuse**
   (self-hosted, история ограничена хранилищем; дни, для которых записей уже нет, получают 0, и страница честно
   называет день начала точного учёта).
4. `tool_requests` — из записей TOOL Langfuse; они появляются только со дня выката агента с инструментацией
   (D2), более ранние дни получают 0, и страница называет этот день началом учёта.
5. `total_users` первого дня истории = сумме `new_users` всех предыдущих дней backfill; дальше — накопление по
   снимкам, в том числе между окнами.

### D7. Миграция API и выкат

Потребитель JSON один — организаторы Sber500 (человек со ссылкой). Порядок:

1. Образ агента с TOOL-инструментацией (D2): записи TOOL начинают появляться, поведение диалогов не меняется
   (трейсинг никогда не влияет на диалог — сбой записи это warning).
2. Создать базу `dashboard` и пользователя в CNPG, таблицу `daily_metrics`.
3. Добавить в Lockbox записи `APP_DATABASE_URL` (пользователь с read-only к базе `app`) и
   `DASHBOARD_DATABASE_URL` (запись только в `dashboard`), пересобрать Secret `dashboard-secrets` (сначала
   `--dry-run=server`, по ранбуку `k8s/dashboard/README.md`); ключи Langfuse остаются как были.
4. Собрать образ `dashboard:0.2.0`, запустить Job backfill и дождаться Complete. Только затем выкатить Deployment
   с новыми env и проверить `/dashboard/api` — новые поля. Старый под 0.1.0 во время backfill обслуживает страницу,
   но в хранилище снимков не пишет.
5. Откат: дашборд — старым образом в любой момент (`DIALOG_DATABASE_URL` и ключи Langfuse на месте); агент —
   старым образом, записи TOOL перестают появляться, дашборд посчитает за те сутки меньшее, но честное число.

### D8. Восстановление сообщений из Langfuse (версия 0.2.1)

Причина: после выката 0.2.0 обнаружено, что сохранённая история сообщений в базе `agent` неполна — дни
11–16.11.2026 в `messages` отсутствуют вовсе (DAU и tool calls за эти дни — 0 при живых разговорах),
провалы есть и в другие дни. Живые трассы Langfuse за эти дни сохранились. Поэтому «сообщения» для
`dau`/`daily_active_account` и первый известный день для `new_users` считаются по объединению источников,
а не только по базе:

- Второй источник сообщений — записи GENERATION `live_turn_voice`/`live_turn_text` (подмножество списка
  D1): одна трасса (traceId) с такой записью — одно сообщение. Это приближение: traceId — это ход
  live-диалога, а не строка `messages`; расхождения возможны (ход, оборвавшийся до записи в базу, виден
  только в трейсинге — это и есть цель; ход, потерянный обоими источниками, недосчитан).
- Дедупликация по (московские сутки, userId, traceId): повторная GENERATION той же трассы (ретрай клиента)
  сообщение не дублирует. `live_turn_recovery` (ретрай хода), `dialog_recap`, `mood_classify_*`,
  `memory_*` и записи TOOL сообщениями не считаются. Привязка к аккаунту — userId трассы, как в D1/D2;
  трассы без userId и аккаунты test/internal отбрасываются.
- Объединение с базой — **max по паре «день, аккаунт», не сумма**: оба источника описывают одни и те же
  ходы, сумма посчитала бы сохранённые сообщения дважды; max берёт более полный источник (при полной базе —
  её count, при провале — трейсинг). Завышения за счёт двойного счёта нет; возможная остаточная недооценка
  (источники потеряли разные ходы одного дня) принимается как меньшее зло.
- Первый известный день `new_users` — минимум трёх источников: `first_reply_at`, первое сохранённое
  сообщение и первая live-turn трасса. Так как выгрузка Langfuse ограничена окном, backfill и catch-up
  накапливают первые live-turn дни аккаунтов через границу окон: аккаунт, известный только по трейсингу,
  считается новым один раз, а не в каждом окне заново.
- Для предварительных текущих суток оконного накопления мало: их окно — один день, а первый известный день
  нужен по всей истории конкурса, иначе аккаунт, говоривший раньше только в трейсинге, ошибочно стал бы
  «новым» сегодня и раздул бы `total_users` (найдено ревью). Поэтому `compute_report` сворачивает историю
  постранично (`langfuse_first_turns`: трассы → словарь traceId→userId, observations — с фильтром `name`
  на стороне API по проходу на каждое live-turn имя, страницы в памяти не накапливаются). Полная выгрузка
  истории в списки отвергнута: она убивала под по лимиту памяти 128Mi (exit 137).
- Единый расчёт для всех путей: ночной снимок, backfill и предварительные текущие сутки используют одну и
  ту же функцию объединения.

Пересчёт уже записанных снимков 05.11–16.11.2026 (они посчитаны 0.2.0 по неполной базе и занижены):
снимки неизменны по дизайну, поэтому backfill их не перепишет — нужен ручной `DELETE` строк `daily_metrics`
за эти дни по отдельному разрешению владельца и повторный backfill из образа 0.2.1 (ранбук —
`k8s/dashboard/README.md`, «Выкат 0.2.1»). Автоматического переписывания не вводим: неизменяемость снимков —
требование, а не побочный эффект.

Отвергнутые альтернативы:

- **Сумма источников** — завышает: у каждого сохранённого сообщения есть и трасса.
- **Только Langfuse для «сообщений»** — трейсинг не гарантирует доставку и хранит историю ограниченно;
  база при здоровой записи полнее.
- **Перезапись снимков новым расчётом** — нарушает неизменяемость прошлого; пересчёт только через явное
  удаление по разрешению владельца.

## Risks / Trade-offs

- [Текущие сутки считаются из живых источников и предварительны: опоздавшие записи Langfuse и удаления в течение дня
  меняют число до закрытия] → на странице текущие сутки помечены предварительными; после снимка в 00:15 день
  фиксируется навсегда; при сбое сырых источников при обновлении кэша отдаётся последний удачный отчёт из памяти.
- [Самые ранние аккаунты: первые сообщения, удалённые до backfill, не восстановить] → занижение `new_users`
  только в глубине истории; seed из `users.created_at` отвергнут: создание аккаунта — не первое сообщение.
- [История `llm_requests` ограничена хранилищем Langfuse; история `tool_requests` начинается со дня выката
  агента] → backfill берёт что есть; дни старше — 0 с честной пометкой в определениях на странице.
- [TOOL-запись — своя трасса, а не дочерняя запись трассы хода: фоновые вызовы памяти идут после закрытия
  трассы хода] → связь с аккаунтом через userId трассы сохраняется, чего метрике достаточно; в Langfuse UI
  вызов памяти не виден внутри трассы хода — принимаем.
- [Классификация записей по имени: новое имя GENERATION или TOOL в агенте не попадёт в метрику до правки
  списка] → это осознанная защита от завышения; список зафиксирован в коде дашборда с тестом, ревизия при
  изменениях трейсинга агента названа в tasks.
- [Запись GENERATION создаётся до ответа модели: логический вызов, окончательно упавший, в Langfuse всё равно
  есть] → такие вызовы считаются (обращение к API состоялось); допуск назван в определении.
- [Метка `traffic_type` меняется задним числом] → влияет только на будущие снимки и backfill; записанные снимки
  неизменны — это и есть требуемая стабильность.
- [Часовой пояс зашит: Europe/Moscow без перехода на летнее время (с 2014)] → как в текущем коде; метрика
  продукта едина и московская, это решение владельца.
- [Снимок в 00:15 МСК: запись, дошедшая до источника позже с отметкой вчерашних суток, попадает в уже закрытый
  день] → разница единиц; снимок не переписывается, принимаем.
- [Пагинация Langfuse на больших сутках] → объёмы продукта малы; лимит страницы и цикл по страницам с таймаутом,
  сбой Langfuse откладывает снимок (catch-up), страницу это не ломает.
- [«Сообщение» из Langfuse — приближение: traceId хода live-диалога, а не строка `messages`; источники могут
  потерять разные ходы одного дня] → объединение через max даёт оценку без двойного счёта с возможной
  остаточной недооценкой; допуск назван в определениях на странице и в README.
- [Аккаунт, известный только по трейсингу и активный в нескольких окнах backfill, мог бы считаться новым в
  каждом окне] → первые live-turn дни накапливаются через границу окон одного прогона; угловой случай
  «первая трасса раньше первого сообщения в базе, обе отметки из баз приложения отсутствуют» между отдельными
  прогонами (снимок уже закрыт) не разрешается — снимки неизменны, класс тот же, что у удалённой истории.
