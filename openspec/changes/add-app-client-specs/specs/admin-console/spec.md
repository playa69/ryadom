# Дельта-спецификация: admin-console

## Purpose

Внутренняя админка «Рядом» для сотрудников: вход по одноразовому коду на почту из списка `ADMIN_EMAILS`, поиск пользователей и просмотр карточки, блокировка и разблокировка, ручное подтверждение почты, удаление аккаунта вместе с данными у агента диалогов и журнал действий администраторов. Администратор — это адрес из `ADMIN_EMAILS`; ролей у пользователей приложения нет и выдать их нельзя. Админка рассчитана на экран рабочего места и под телефон намеренно не адаптирована; содержимое разговоров она не показывает. Вход, диалог и профиль пользователя описаны в capability `client-auth`, `client-dialog`, `client-profile`; публичный сайт — в `landing-site`; развёртывание здесь не описывается. Реализовано в `app/apps/admin/` и в бизнес-логике `app/packages/core/src/processes/admin-authentication/`, `app/packages/core/src/processes/user-management/`, `app/packages/core/src/managers/users-manager/`, `app/packages/core/src/managers/audit-log-manager/`.

## ADDED Requirements

### Requirement: Доступ только по сессии

Все страницы и все действия админки, кроме `/login` и `/logout`, SHALL требовать действующей сессии администратора; без неё запрос MUST перенаправляться на `/login`. Каждое действие над пользователем MUST проверять сессию заново, а не полагаться на проверку при показе страницы. Корень `/` MUST вести на `/users`, а `/login` при действующей сессии — тоже на `/users`.

#### Scenario: Страница без сессии

- **WHEN** посетитель без сессии открывает `/users`, `/users/{id}` или `/audit`
- **THEN** он перенаправляется на `/login`

#### Scenario: Действие с истёкшей сессией

- **WHEN** сессия истекла, а администратор нажимает кнопку действия на ранее открытой карточке
- **THEN** действие не выполняется и администратор перенаправляется на `/login`

#### Scenario: Вход при действующей сессии

- **WHEN** администратор с действующей сессией открывает `/login` или `/`
- **THEN** он попадает на `/users`

### Requirement: Запрос кода входа

Экран входа SHALL принимать адрес почты и отправлять шестизначный одноразовый код только на адрес из `ADMIN_EMAILS`; сравнение MUST не зависеть от регистра и пробелов по краям. Ответ экрана MUST быть одинаковым для любого корректного адреса, чтобы по нему нельзя было узнать, кто входит в список. Адрес в неверном формате MUST отклоняться сообщением «Проверьте адрес почты.» без отправки. Код живёт 10 минут (`PROCESSES_CONFIG.CODES.TTL_MINUTES`); новый запрос MUST заменять предыдущий код для этого адреса. Если `ADMIN_EMAILS` пуст, войти не может никто.

#### Scenario: Адрес из списка

- **WHEN** администратор вводит свой адрес и нажимает «Прислать код»
- **THEN** на этот адрес уходит письмо с шестизначным кодом
- **AND** экран переходит на шаг ввода кода и показывает адрес, на который отправлено письмо

#### Scenario: Адрес не из списка

- **WHEN** посетитель вводит корректный адрес, которого нет в `ADMIN_EMAILS`
- **THEN** экран переходит на тот же шаг ввода кода, письмо не отправляется и код не создаётся

#### Scenario: Неверный формат адреса

- **WHEN** посетитель отправляет строку, не являющуюся адресом почты
- **THEN** экран остаётся на шаге ввода адреса и показывает «Проверьте адрес почты.»

#### Scenario: Повторный запрос кода

- **WHEN** администратор на шаге ввода кода нажимает «Прислать код ещё раз»
- **THEN** отправляется новый код, а прежний перестаёт действовать

#### Scenario: Список администраторов пуст

- **WHEN** `ADMIN_EMAILS` пуст
- **THEN** запрос кода завершается так же, как для любого адреса, но письма не уходят

### Requirement: Лимиты запросов на экране входа

Экран входа SHALL ограничивать частоту попыток счётчиками в памяти процесса (`ADMIN_LIMITS` в `app/apps/admin/lib/rate-limit.ts`): запросы кода — не более 5 за 10 минут на адрес почты и не более 20 за час на IP; отправка кода — не более 30 за 10 минут на IP. Счётчики MUST быть раздельными у каждого экземпляра админки и MUST обнуляться при перезапуске. IP MUST определяться по первому адресу заголовка `X-Forwarded-For`, затем по `X-Real-IP`; без этих заголовков все посетители делят один счётчик. При превышении администратор видит «Слишком много попыток. Подождите немного и попробуйте снова.».

#### Scenario: Много запросов кода для одной почты

- **WHEN** за 10 минут с одного адреса почты сделано шестое обращение за кодом
- **THEN** код не отправляется, а экран возвращается на шаг ввода адреса с сообщением о слишком большом числе попыток

#### Scenario: Много запросов кода с одного IP

- **WHEN** с одного IP за час сделан двадцать первый запрос кода, даже на разные адреса
- **THEN** запрос отклоняется с тем же сообщением

#### Scenario: Много попыток ввода кода

- **WHEN** с одного IP за 10 минут отправлено тридцать первое значение кода
- **THEN** проверка не выполняется, экран остаётся на шаге ввода кода и показывает то же сообщение

### Requirement: Подтверждение кода и сессия администратора

Шаг ввода кода SHALL принимать ровно шесть цифр; иначе MUST показываться «Код состоит из шести цифр.» без обращения к проверке. Верный код MUST гаситься сразу: повторно им войти нельзя. Неверный или истёкший код MUST давать «Код неверный или истёк. Запросите новый.» с сохранением введённого адреса; после пятой неверной попытки код сгорает, и экран MUST вернуть на шаг ввода адреса с сообщением «Слишком много неверных попыток. Запросите новый код.». Если адрес убран из `ADMIN_EMAILS` после выдачи кода, вход MUST отклоняться сообщением «Доступ закрыт.» даже при верном коде. После успешного входа админка MUST выдать подписанную сессию в cookie `admin_session` на 24 часа (`httpOnly`, `SameSite=Lax`, `secure` в рабочем окружении) и перенаправить на `/users`.

#### Scenario: Верный код

- **WHEN** администратор вводит верный код в течение 10 минут
- **THEN** выдаётся cookie `admin_session` на 24 часа и открывается `/users`

#### Scenario: Неверный код

- **WHEN** администратор вводит неверный шестизначный код
- **THEN** экран остаётся на шаге ввода кода с тем же адресом и сообщением «Код неверный или истёк. Запросите новый.»

#### Scenario: Пять неверных попыток

- **WHEN** подряд введено пять неверных кодов к одному коду
- **THEN** код больше не принимается даже верный, экран возвращается на шаг ввода адреса и просит запросить новый код

#### Scenario: Код истёк или уже использован

- **WHEN** администратор вводит код старше 10 минут или тот, которым уже входил
- **THEN** вход отклоняется сообщением «Код неверный или истёк. Запросите новый.»

#### Scenario: Адрес убран из списка после выдачи кода

- **WHEN** адрес удалён из `ADMIN_EMAILS` между выдачей кода и его вводом
- **THEN** вход отклоняется сообщением «Доступ закрыт.» и экран возвращается на шаг ввода адреса с пустым полем

#### Scenario: Сессия сверяется со списком

- **WHEN** адрес убран из `ADMIN_EMAILS`, сервис перезапущен, а у администратора остаётся неистёкшая cookie
- **THEN** cookie перестаёт давать доступ, и следующий запрос перенаправляется на `/login`

### Requirement: Выход

Выход SHALL выполняться только запросом `POST /logout` из кнопки «Выйти» в шапке: он MUST очищать cookie `admin_session` и перенаправлять на `/login`. `GET /logout` MUST NOT выходить из системы, чтобы чужая страница не могла разлогинить администратора.

#### Scenario: Выход

- **WHEN** администратор нажимает «Выйти»
- **THEN** cookie `admin_session` сбрасывается и открывается `/login`
- **AND** возврат на закрытую страницу без нового входа перенаправляет на `/login`

#### Scenario: Выход запросом GET

- **WHEN** на `/logout` приходит запрос методом GET
- **THEN** сессия не сбрасывается

### Requirement: Каркас админки и рабочий стол

Разделы админки SHALL открываться в общем каркасе: боковое меню фиксированной ширины с пунктами «Пользователи» (`/users`) и «Журнал действий» (`/audit`), шапка с адресом вошедшего администратора и кнопкой «Выйти», внизу меню — ссылка «Перейти на сайт» на `PUBLIC_WEB_URL` в новой вкладке. Админка MUST быть рассчитана на экран рабочего места (проверяется на ширине 1280 и 1920 пикселей); раскладки для телефона (сворачиваемое меню, карточки вместо таблиц) в ней нет, и это не дефект. Все страницы MUST быть закрыты от индексации (`robots: noindex, nofollow`).

#### Scenario: Навигация

- **WHEN** администратор находится на карточке пользователя
- **THEN** в меню подсвечен пункт «Пользователи», а переход в «Журнал действий» открывает `/audit`

#### Scenario: Переход на сайт

- **WHEN** администратор нажимает «Перейти на сайт»
- **THEN** адрес `PUBLIC_WEB_URL` открывается в новой вкладке (см. capability `landing-site`)

#### Scenario: Закрыто от индексации

- **WHEN** поисковый робот загружает страницу админки
- **THEN** в метаданных страницы указано `noindex, nofollow`

### Requirement: Список пользователей

Страница `/users` SHALL показывать таблицу пользователей по 25 записей на страницу (`PAGE_SIZE`) со столбцами «Почта» (ссылка на карточку), «Имя» (прочерк, если не задано), «Статус» («Активен», «Заблокирован», «Удалён»), «Почта подтверждена» («да» или «нет») и «Регистрация» (московское время). Удалённый пользователь MUST показываться со статусом «Удалён», даже если он тоже неактивен. Под таблицей MUST быть число найденных записей, «Страница N из M» и кнопки «Назад» и «Вперёд». По умолчанию список отсортирован по дате регистрации от новых к старым, удалённые показываются.

#### Scenario: Открытие списка

- **WHEN** администратор открывает `/users`
- **THEN** он видит первые 25 пользователей от новых к старым и под таблицей «Найдено: N»

#### Scenario: Переход по страницам

- **WHEN** администратор нажимает «Вперёд»
- **THEN** открывается следующая страница с теми же поиском, фильтрами и сортировкой в адресе, а на первой странице «Назад» недоступна

#### Scenario: Страница за пределами списка

- **WHEN** в адресе указан номер страницы больше последней
- **THEN** показывается пустое состояние «Никого не нашлось. Попробуйте изменить условия поиска.», а «Назад» ведёт на последнюю существующую страницу

#### Scenario: Некорректный номер страницы

- **WHEN** параметр `page` не число или не больше нуля
- **THEN** открывается первая страница, ошибки нет

#### Scenario: Пустой результат

- **WHEN** по условиям поиска никого нет
- **THEN** вместо таблицы показывается «Никого не нашлось. Попробуйте изменить условия поиска.», а «Найдено» равно 0

### Requirement: Поиск, фильтры и сортировка списка

Список SHALL искать подстрокой без учёта регистра по почте и имени, а при вводе полного идентификатора пользователя (UUID) — ещё и по точному совпадению с ним; строка поиска обрезается по краям и ограничена 120 символами, служебные символы шаблона (`%`, `_`, `\`) MUST искаться как обычные. Фильтры: «Доступ» («Активен» / «Заблокирован»), «Почта» («Подтверждена» / «Не подтверждена»), «Удалённые» («Показывать» / «Скрыть» / «Только удалённые»). Сортировка: «По дате» (по умолчанию, новые первыми), «По почте» и «По имени» (по возрастанию). Условия MUST храниться в адресе страницы (`q`, `active`, `confirmed`, `deleted`, `sort`, `order`, `page`), любая смена условий MUST возвращать на первую страницу; неизвестные значения параметров MUST заменяться значениями по умолчанию без ошибки.

#### Scenario: Поиск по набору символов

- **WHEN** администратор вводит часть почты или имени
- **THEN** через 300 мс без ввода список обновляется, а `q` попадает в адрес; нажатие Enter обновляет список сразу

#### Scenario: Поиск по идентификатору

- **WHEN** администратор вставляет полный UUID пользователя
- **THEN** в списке остаётся этот пользователь

#### Scenario: Сортировка по почте

- **WHEN** выбрана сортировка «По почте»
- **THEN** список идёт по возрастанию почты, а в адресе появляются `sort=email` и `order=asc`

#### Scenario: Сброс условий

- **WHEN** задан поиск, фильтр или сортировка не по дате
- **THEN** появляется кнопка «Сбросить», которая очищает все условия и открывает `/users` без параметров

#### Scenario: Неизвестные параметры

- **WHEN** в адресе указаны `sort=foo`, `order=bar` или `active=maybe`
- **THEN** действуют сортировка по дате, порядок от новых к старым и отсутствие фильтра

### Requirement: Карточка пользователя

Страница `/users/{id}` SHALL показывать почту как заголовок, значки статуса и подтверждения почты, блок «Профиль» (идентификатор, имя или «не указано», подтверждена ли почта, даты регистрации и последнего изменения, а для удалённого — дату удаления), блок «Действия», блок «Опасная зона» (только для не удалённого), ссылку на журнал этого пользователя и пояснение, что содержание разговоров в админке не показывается. Идентификатор не в формате UUID и несуществующий пользователь MUST давать страницу «Страница не найдена» внутри каркаса. На ширине от 1280 пикселей карточка раскладывается в две колонки (профиль, история и разговоры слева, действия и опасная зона справа), уже — в одну колонку в порядке: профиль, действия, опасная зона, история, разговоры.

#### Scenario: Открытие карточки

- **WHEN** администратор открывает `/users/{id}` существующего пользователя
- **THEN** он видит профиль, действия и ссылку «Что администраторы делали с этим аккаунтом», ведущую на `/audit?user={id}`

#### Scenario: Разговоры не показываются

- **WHEN** администратор просматривает карточку
- **THEN** тексты разговоров не показываются, вместо них выведено пояснение, что доступ к ним есть только у самого человека

#### Scenario: Несуществующий пользователь

- **WHEN** открывается `/users/not-a-uuid` или `/users/{id}` с незанятым идентификатором
- **THEN** показывается «Страница не найдена» с кнопкой «К пользователям», меню и шапка сохраняются

#### Scenario: Удалённый пользователь

- **WHEN** открывается карточка удалённого пользователя
- **THEN** профиль содержит дату удаления, блок «Опасная зона» отсутствует, а вместо кнопок действий написано, что аккаунт удалён и действия недоступны

### Requirement: Блокировка и ручное подтверждение почты

Блок «Действия» SHALL содержать кнопку «Заблокировать» у активного пользователя и «Разблокировать» у заблокированного; нажатие MUST применяться сразу, без окна подтверждения, и MUST давать «Доступ закрыт.» или «Доступ восстановлен.». Кнопка «Подтвердить почту вручную» MUST показываться только у пользователя с неподтверждённой почтой и давать «Почта отмечена подтверждённой.». Блокировка MUST закрывать пользователю вход (при верном пароле — отказ `USER_INACTIVE`), продление сессии (`ACCOUNT_INACTIVE`) и операции с диалогами; уже выданный токен доступа при этом действует до 15 минут. Блокировка удалённого аккаунта MUST отклоняться. Каждое действие MUST писать запись в журнал в одной транзакции с самим изменением.

#### Scenario: Блокировка

- **WHEN** администратор нажимает «Заблокировать» у активного пользователя
- **THEN** показывается «Доступ закрыт.», статус меняется на «Заблокирован», кнопка становится «Разблокировать»
- **AND** в журнале появляется запись «Заблокирован»
- **AND** вход этого пользователя отклоняется (см. capability `client-auth`)

#### Scenario: Разблокировка

- **WHEN** администратор нажимает «Разблокировать»
- **THEN** показывается «Доступ восстановлен.», пользователь снова может войти, в журнале появляется запись «Разблокирован»

#### Scenario: Подтверждение почты

- **WHEN** администратор нажимает «Подтвердить почту вручную» у пользователя с неподтверждённой почтой
- **THEN** почта отмечается подтверждённой, кнопка исчезает, пользователь может войти, в журнале появляется запись «Почта подтверждена вручную»

#### Scenario: Пользователь удалён, пока открыта карточка

- **WHEN** пользователь удалён другим администратором, а на старой карточке нажата «Заблокировать»
- **THEN** показывается «Аккаунт удалён: блокировка к нему больше не применима.»

#### Scenario: Пользователь исчез

- **WHEN** действие выполняется над идентификатором, которого нет в базе
- **THEN** показывается «Пользователь не найден.»

### Requirement: Подтверждение удаления вводом почты

Кнопка «Удалить аккаунт» в «Опасной зоне» SHALL открывать окно «Удалить аккаунт?», где администратор MUST ввести почту пользователя. Кнопка «Удалить навсегда» MUST оставаться недоступной, пока введённое значение (без пробелов по краям и без учёта регистра) не совпадёт с почтой карточки. Сервер MUST повторно сравнить введённое значение с адресом карточки и при несовпадении отказать сообщением «Почта не совпала. Удаление отменено.» без каких-либо изменений. При каждом открытии окна поле пустое, прежняя ошибка не показывается.

#### Scenario: Почта не введена

- **WHEN** окно открыто, а поле пустое или содержит другой адрес
- **THEN** кнопка «Удалить навсегда» недоступна

#### Scenario: Почта совпала

- **WHEN** администратор вводит почту пользователя в любом регистре
- **THEN** кнопка «Удалить навсегда» становится доступной

#### Scenario: Несовпадение на сервере

- **WHEN** на сервер приходит запрос на удаление с не совпавшим адресом
- **THEN** показывается «Почта не совпала. Удаление отменено.», агент не вызывается, пользователь не меняется

#### Scenario: Отмена

- **WHEN** администратор закрывает окно кнопкой «Отмена»
- **THEN** ничего не удаляется, а при повторном открытии поле пустое

### Requirement: Удаление аккаунта стирает данные у агента и анонимизирует запись

Удаление SHALL сначала стирать данные пользователя у агента диалогов запросом `DELETE /v1/users/{id}` (ответы 200, 204 и 404 считаются успехом) и только после этого, в одной транзакции, сохранять снимок персональных данных, удалять пароль и коды из писем, анонимизировать запись и писать в журнал запись «Аккаунт удалён» с почтой пользователя на момент удаления. Анонимизация MUST заменять почту на `deleted+{id}@anonymized.local`, обнулять имя, снимать признаки активности и подтверждения и ставить отметку удаления с датой; исходный адрес после этого свободен для новой регистрации. Перед анонимизацией MUST сохраняться снимок персональных данных (причина `admin_request`, почта, имя, статусы, дата регистрации, хеш пароля) в служебном поле записи `properties.deletion`; в админке он не показывается. Совместимо ли это с тем, что обещает публичная страница `/delete-account`, и на какой срок снимок хранится, в этом change не утверждается — см. «Open Questions» в `design.md`. Повторное удаление MUST отклоняться сообщением «Аккаунт уже удалён.».

#### Scenario: Успешное удаление

- **WHEN** администратор подтвердил удаление существующего пользователя
- **THEN** у агента стираются данные этого пользователя, а в списке и карточке он показан как «Удалён» с анонимизированной почтой и без имени
- **AND** пользователь больше не может войти, а его прежний адрес можно использовать при новой регистрации
- **AND** в журнале появляется запись «Аккаунт удалён» с исходной почтой

#### Scenario: Агенту нечего стирать

- **WHEN** агент отвечает на стирание кодом 404
- **THEN** удаление завершается успешно так же, как при ответе 200 или 204

#### Scenario: Карточка после удаления

- **WHEN** удаление завершено
- **THEN** карточка обновляется: статус «Удалён», блок «Опасная зона» исчезает, кнопки действий заменены пояснением

#### Scenario: Повторное удаление

- **WHEN** удаление запрашивается для уже удалённого пользователя
- **THEN** показывается «Аккаунт уже удалён.»

### Requirement: Сбой агента при удалении

Если агент не ответил (сетевая ошибка, превышение `AGENT_TIMEOUT_MS`, по умолчанию 10 000 мс, ответ 5xx, ответ не в формате JSON), админка SHALL не менять ничего в базе и показывать в окне «Сервис диалогов недоступен, данные не тронуты. Повторите позже.»; аккаунт остаётся прежним, запись в журнал не пишется. Ответ агента 4xx, кроме 404, MUST также оставлять данные нетронутыми (какое сообщение при этом видит администратор — «Open Questions» в `design.md`). Повтор удаления после сбоя MUST быть безопасным: стирание у агента идемпотентно.

#### Scenario: Агент недоступен

- **WHEN** администратор подтверждает удаление, а агент не отвечает или отвечает 5xx
- **THEN** в окне показывается «Сервис диалогов недоступен, данные не тронуты. Повторите позже.»
- **AND** пользователь остаётся активным, пароль и журнал не изменены, записи об удалении нет

#### Scenario: Повтор после сбоя

- **WHEN** администратор повторяет удаление после восстановления агента
- **THEN** удаление проходит в обычном порядке

#### Scenario: Агент отказал кодом 4xx

- **WHEN** агент отвечает на стирание, например, 401 или 400
- **THEN** удаление не выполняется, данные не тронуты

### Requirement: Журнал действий

Страница `/audit` SHALL показывать журнал действий администраторов над аккаунтами по 50 записей на страницу, от новых к старым. Журнал MUST содержать ровно четыре вида записей: «Заблокирован», «Разблокирован», «Почта подтверждена вручную», «Аккаунт удалён»; входы, выходы и просмотры в него не попадают. У записи MUST показываться время (московское), адрес администратора, действие, пользователь (ссылка на карточку с почтой на момент действия) и подробности (пары «ключ: значение», `reason` показывается как «причина», при отсутствии — прочерк). В админке MUST NOT быть действий, меняющих или удаляющих записи журнала. Параметр `user` MUST ограничивать журнал записями об одном пользователе; значение, не являющееся UUID, MUST давать пустой журнал без ошибки.

#### Scenario: Просмотр журнала

- **WHEN** администратор открывает `/audit` после блокировки пользователя
- **THEN** первая запись содержит время, адрес администратора, действие «Заблокирован» и почту пользователя со ссылкой на его карточку

#### Scenario: Журнал одного пользователя

- **WHEN** администратор переходит по ссылке «Что администраторы делали с этим аккаунтом»
- **THEN** страница показывает только записи об этом пользователе и ссылку «Показать все»

#### Scenario: Пустой журнал

- **WHEN** записей нет
- **THEN** показывается «Пока ничего не происходило.» и «Найдено: 0»

#### Scenario: Пользователь удалён

- **WHEN** в журнале есть запись о пользователе, который потом был удалён
- **THEN** запись показывает почту, какой она была в момент действия, и ссылку на карточку

#### Scenario: Некорректный идентификатор пользователя

- **WHEN** в адресе указано `user=not-a-uuid`
- **THEN** журнал пуст, ошибки нет

#### Scenario: Подробности без данных

- **WHEN** у записи нет дополнительных данных
- **THEN** в столбце «Подробности» стоит прочерк, а не `{}`

### Requirement: Ошибки и страницы «не найдено»

Непредвиденная ошибка при показе страницы админки SHALL выводить по центру карточку «Что-то сломалось» с кнопкой «Повторить», которая повторяет отрисовку; если у ошибки есть `digest`, он MUST показываться на карточке, чтобы найти запись в журналах сервиса. Неизвестный адрес вне разделов MUST показывать карточку «Страница не найдена» с кнопкой «К пользователям»; внутри разделов (например, карточка несуществующего пользователя) — то же сообщение в каркасе с меню и шапкой.

#### Scenario: Сбой отрисовки

- **WHEN** при открытии `/users` происходит непредвиденная ошибка
- **THEN** администратор видит «Что-то сломалось», при наличии — строку `digest`, и кнопку «Повторить»

#### Scenario: Повтор

- **WHEN** администратор нажимает «Повторить»
- **THEN** страница отрисовывается заново

#### Scenario: Неизвестный адрес

- **WHEN** открывается адрес, которого нет в админке
- **THEN** показывается «Страница не найдена» и кнопка «К пользователям»
