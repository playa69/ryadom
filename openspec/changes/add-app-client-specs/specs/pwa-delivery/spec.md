# Дельта-спецификация: pwa-delivery

## Purpose

Мобильный клиент открывается в браузере как PWA: собранную оболочку, манифест и service worker раздаёт отдельный контейнер `app-pwa` (nginx, образ из `app/apps/mobile/Dockerfile`), который публикуется на том же хосте, что и API, под путём `/pwa/`; клиент предлагает поставить приложение на домашний экран и открывается без сети. Процесс `app/services/api` клиент не раздаёт и отвечает только за `/api/*`, а какой путь хоста кому принадлежит, решает шлюз. Спека описывает только доставку PWA (что раздаётся и под каким адресом, как кэшируется и обновляется, как предлагается установка) — для тех, кто выпускает версии и проверяет кэши. Индикатор офлайна внутри оболочки описан в `client-shell`, обновление нативных сборок — в `app-updates`, нативные сборки — в `native-app-build`, карточка установки на сайте — в `landing-site`. Манифесты шлюза и развёртывание контейнера здесь не описываются: спека фиксирует, что видит браузер и что делает контейнер. Реализовано в `app/apps/mobile/Dockerfile`, `app/apps/mobile/nginx/` (`nginx.conf.template`, `pwa-shell.inc`, `entrypoint.sh`), `app/apps/mobile/vite.config.ts`, `app/apps/mobile/public/manifest.webmanifest`, `app/apps/mobile/src/sw/sw.ts`, `app/apps/mobile/src/client/lib/service-worker.ts`, `app/apps/mobile/src/client/lib/install-prompt.ts` и `app/apps/mobile/src/client/components/InstallBanner.tsx`; имена метатегов заданы в `app/packages/contracts/src/pwa.ts`.

## ADDED Requirements

### Requirement: Раздача PWA отдельным контейнером

PWA (браузерная сборка мобильного клиента, `vite build --mode web`) SHALL раздаваться отдельным контейнером `app-pwa`: образ собирается из `app/apps/mobile/Dockerfile`, статические файлы сборки отдаёт nginx. Процесс `app/services/api` MUST NOT раздавать клиент (ни файлы, ни оболочку): он отвечает только за `/api/*`, а образ API содержит лишь OTA-пакеты нативных сборок (см. `app-updates`).

#### Scenario: Контейнер с PWA

- **WHEN** контейнер `app-pwa` запущен с верными настройками
- **THEN** nginx отдаёт файлы веб-сборки мобильного клиента, процесс API для этого не нужен

#### Scenario: API не раздаёт клиент

- **WHEN** к процессу API приходит `GET /` или `GET /pwa/`
- **THEN** оболочка не отдаётся: ответ 404, как для любого адреса без маршрута

#### Scenario: Образ API без PWA

- **WHEN** собирается образ API
- **THEN** в нём нет веб-сборки мобильного клиента, есть только OTA-пакеты

### Requirement: Префикс адреса задаётся при сборке образа

Путь, под которым PWA опубликована на хосте (префикс), SHALL задаваться при сборке образа аргументом `PWA_BASE_PATH` и MUST NOT меняться при запуске контейнера: он записывается в `base` Vite (адреса всех файлов сборки, область service worker и манифеста) и в конфигурацию nginx. Значение — пустое (PWA владеет всем хостом) или вида `/pwa`: косая черта в начале, без завершающей, сегменты из латинских букв, цифр, `_` и `-`; любое другое значение MUST прерывать сборку образа. На общем хосте вместе с сайтом, веб-клиентом и API PWA публикуется под `/pwa/`.

#### Scenario: Образ для общего хоста

- **WHEN** образ собран с `PWA_BASE_PATH=/pwa`
- **THEN** файлы открываются под `/pwa/`, адреса файлов в `index.html` начинаются с `/pwa/`, область service worker и манифеста — `/pwa/`

#### Scenario: Образ для собственного хоста

- **WHEN** образ собран без `PWA_BASE_PATH` (пустой префикс)
- **THEN** PWA открывается с корня хоста `/`, перенаправлений на префикс нет, область service worker и манифеста — `/`

#### Scenario: Некорректный префикс

- **WHEN** образ собирается с `PWA_BASE_PATH=/pwa/` (завершающая косая черта) или `pwa` (нет косой черты в начале)
- **THEN** сборка образа завершается ошибкой с пояснением, а не откладывается до запуска контейнера

#### Scenario: Смена префикса

- **WHEN** PWA нужно опубликовать под другим путём
- **THEN** собирается новый образ с другим `PWA_BASE_PATH`: переменной окружения запуска, меняющей префикс, нет

### Requirement: Перенаправления и пути вне префикса

При непустом префиксе контейнер SHALL отвечать так: `GET /pwa` — 301 на `/pwa/`; `GET /` — 302 на `/pwa/`; любой другой путь вне префикса, кроме проверки живости, — 404 обычной страницей nginx (не JSON формата API: пути `/api/*` до контейнера не доходят). Строка запроса при перенаправлениях MUST сохраняться, а заголовок `Location` MUST быть относительным (без схемы и хоста): за шлюзом, завершающим TLS, абсолютный адрес содержал бы внутренние схему и порт контейнера. Через шлюз корень хоста принадлежит сайту, поэтому перенаправление с `/` срабатывает при прямом обращении к контейнеру. При пустом префиксе этих правил нет: все пути принадлежат PWA.

#### Scenario: Адрес без завершающей косой черты

- **WHEN** приходит `GET /pwa?from=landing`
- **THEN** ответ 301 с `Location: /pwa/?from=landing`

#### Scenario: Корень хоста

- **WHEN** к контейнеру приходит `GET /` (при префиксе `/pwa`)
- **THEN** ответ 302 с `Location: /pwa/`

#### Scenario: Чужой путь

- **WHEN** к контейнеру приходит `GET /journal/` или `GET /other.js` (при префиксе `/pwa`)
- **THEN** ответ 404 обычной страницей nginx, оболочка не отдаётся

#### Scenario: Пустой префикс

- **WHEN** образ собран без префикса и приходит `GET /journal/`
- **THEN** отдаётся оболочка со статусом 200, а не 404

### Requirement: Оболочка для маршрутов приложения

Под префиксом на запрос контейнер SHALL отдавать файл сборки, если он есть, а иначе — оболочку (`index.html` с метатегами из требования «Контейнер вписывает адрес сайта и окружение в оболочку при запуске») со статусом 200, `Content-Type: text/html; charset=utf-8` и `Cache-Control: no-cache`; дальше маршрут разбирает клиент. Исключение: отсутствующий файл под `<префикс>/assets/` MUST давать настоящий 404, а не оболочку, чтобы устаревшая оболочка не получала HTML вместо скрипта или стиля. Перенаправлений на адрес с косой чертой в конце контейнер не делает.

#### Scenario: Корень приложения

- **WHEN** браузер запрашивает `GET /pwa/`
- **THEN** приходит оболочка, статус 200, `Cache-Control: no-cache`

#### Scenario: Глубокая ссылка на экран приложения

- **WHEN** браузер запрашивает `GET /pwa/dialog/d-1/`, а такого файла в сборке нет
- **THEN** приходит та же оболочка со статусом 200, и клиент сам открывает нужный экран

#### Scenario: Неизвестный путь под префиксом

- **WHEN** браузер запрашивает `GET /pwa/no-such-file.js`, которого нет в сборке и который лежит не в `assets/`
- **THEN** приходит оболочка со статусом 200

#### Scenario: Файл сборки

- **WHEN** браузер запрашивает файл, который есть в сборке (например, `/pwa/manifest.webmanifest`)
- **THEN** приходит сам файл, а не оболочка

#### Scenario: Отсутствующий файл в assets

- **WHEN** браузер запрашивает `GET /pwa/assets/index-старый-хэш.js`, которого в этой сборке нет
- **THEN** ответ 404, а не оболочка со статусом 200

### Requirement: Контейнер вписывает адрес сайта и окружение в оболочку при запуске

При каждом запуске контейнер SHALL вставить перед `</head>` оболочки метатеги `ryadom-web-url` (значение `PUBLIC_WEB_URL` без завершающих косых черт) и `ryadom-app-env` (значение `APP_ENV`) один раз, а не на каждый запрос; значения MUST экранироваться как HTML-атрибуты (`&`, `"`, `<`, `>`). Один образ обслуживает локальный стенд и prod, поэтому адреса в сборку не вшиваются. И `/pwa/`, и `/pwa/index.html` (и любой путь, получивший оболочку) SHALL отдавать один и тот же файл с метатегами: service worker предкэширует `index.html`, а исходный файл сборки без метатегов MUST NOT отдаваться никогда. Смена значений требует перезапуска контейнера; до уже установленных service worker она доходит только со следующей сборкой образа, потому что ревизия записи `index.html` в предкэше (Workbox) — хэш содержимого на момент сборки. PWA SHALL брать адрес сайта (юридические документы, страница загрузки) из `ryadom-web-url`, а адрес API — свой же origin.

#### Scenario: Метатеги в ответе

- **WHEN** контейнер запущен с `PUBLIC_WEB_URL=https://site.example/` и `APP_ENV=prod`, и приходит `GET /pwa/`
- **THEN** в `<head>` ответа есть `<meta name="ryadom-web-url" content="https://site.example">` и `<meta name="ryadom-app-env" content="prod">`

#### Scenario: Спецсимволы в значении

- **WHEN** значение `PUBLIC_WEB_URL` содержит `"`, `<`, `>` или `&`
- **THEN** в метатеге они заменены на `&quot;`, `&lt;`, `&gt;`, `&amp;`

#### Scenario: Одинаковая оболочка по двум адресам

- **WHEN** браузер запрашивает `GET /pwa/` и `GET /pwa/index.html`
- **THEN** оба ответа содержат один и тот же `index.html` с одними и теми же метатегами
- **AND** исходного `index.html` без метатегов контейнер не отдаёт ни по какому адресу

#### Scenario: Смена значений

- **WHEN** `PUBLIC_WEB_URL` изменён и контейнер перезапущен
- **THEN** новые запросы получают оболочку с новым значением
- **AND** уже установленный service worker продолжает отдавать прежнюю оболочку из предкэша, пока не выйдет новая сборка образа и человек не обновится кнопкой

#### Scenario: Ссылки на документы в PWA

- **WHEN** человек открывает из PWA условия использования или политику конфиденциальности
- **THEN** адрес строится от значения метатега `ryadom-web-url`, а запросы к API идут на тот же origin, откуда загружена оболочка

### Requirement: Контейнер не запускается с неверными настройками

Контейнер SHALL проверять настройки при старте и MUST завершаться с ненулевым кодом и сообщением в stderr, не запуская nginx, если `PUBLIC_WEB_URL` не задан, не начинается с `http://` или `https://` либо содержит пробельные символы, если `APP_ENV` не задан или не равен `local` или `prod`, либо если в собранном `index.html` нет `</head>`. Отдавать клиентам оболочку без метатегов или с неверными значениями MUST NOT.

#### Scenario: Нет адреса сайта

- **WHEN** контейнер запускается без `PUBLIC_WEB_URL`
- **THEN** он завершается с ненулевым кодом и сообщением, что `PUBLIC_WEB_URL` обязателен, а nginx не стартует

#### Scenario: Адрес без схемы или с пробелом

- **WHEN** `PUBLIC_WEB_URL` равен `site.example` либо `https://site .example`
- **THEN** контейнер завершается с ненулевым кодом и сообщением о неверном адресе

#### Scenario: Неизвестное окружение

- **WHEN** `APP_ENV=production` либо `APP_ENV` не задан
- **THEN** контейнер завершается с ненулевым кодом и сообщением о допустимых значениях `local`, `prod`

#### Scenario: Верные настройки

- **WHEN** заданы `PUBLIC_WEB_URL=https://site.example` и `APP_ENV=prod`
- **THEN** контейнер стартует и отдаёт оболочку с метатегами

### Requirement: Статические файлы и кэш-заголовки

Файлы сборки (ресурсы, иконки, манифест, `sw.js`) SHALL отдаваться как есть, манифест — с типом `application/manifest+json`. Заголовок `Cache-Control` MUST выбираться по виду файла: только хэшированные файлы под `<префикс>/assets/` (JS, CSS и шрифты, чьи имена содержат хэш содержимого) получают `public, max-age=31536000, immutable`; иконки (`png`, `svg`, `ico`) — `public, max-age=86400`; всё остальное — оболочка, `sw.js`, `manifest.webmanifest`, `voice-worklet.js` — `no-cache`. Файлы из `public/` без хэша в имени, в отличие от прежней раздачи через API, MUST NOT получать `immutable`. Заголовок MUST выставляться только успешным ответам и перенаправлениям: ответ с ошибкой не получает `Cache-Control`, чтобы 404 не стал `immutable`.

#### Scenario: Service worker не кэшируется

- **WHEN** браузер запрашивает `/pwa/sw.js`
- **THEN** ответ содержит `Cache-Control: no-cache`, и новая версия воркера подхватывается при проверке обновления

#### Scenario: Ресурс с хэшем в имени

- **WHEN** браузер запрашивает файл вида `/pwa/assets/index-<хэш>.js`
- **THEN** ответ содержит `Cache-Control: public, max-age=31536000, immutable`

#### Scenario: Иконка

- **WHEN** браузер запрашивает `/pwa/pwa-192x192.png`
- **THEN** ответ содержит `Cache-Control: public, max-age=86400`

#### Scenario: Файл из public без хэша

- **WHEN** браузер запрашивает `/pwa/voice-worklet.js`
- **THEN** ответ содержит `Cache-Control: no-cache`, а не `immutable`

#### Scenario: Манифест

- **WHEN** браузер запрашивает `/pwa/manifest.webmanifest`
- **THEN** ответ содержит `Cache-Control: no-cache` и `Content-Type: application/manifest+json`

#### Scenario: Ошибка не кэшируется навсегда

- **WHEN** браузер запрашивает отсутствующий файл под `/pwa/assets/`
- **THEN** ответ 404 не содержит `Cache-Control: public, max-age=31536000, immutable`

### Requirement: Сжатие текстовых ресурсов

Контейнер SHALL сжимать gzip текстовые ответы (HTML, CSS, JS, JSON, манифест, SVG, шрифты TTF) для клиентов, которые принимают сжатие, и добавлять `Vary: Accept-Encoding`; ответы короче 1024 байт MAY отдаваться без сжатия.

#### Scenario: Запрос со сжатием

- **WHEN** браузер запрашивает JS-файл сборки с `Accept-Encoding: gzip`
- **THEN** ответ приходит с `Content-Encoding: gzip`

### Requirement: Заголовки безопасности ответов PWA

Каждый ответ контейнера (файл, оболочка, перенаправление, 404, проверка живости) SHALL нести `X-Robots-Tag: noindex`, `X-Content-Type-Options: nosniff` и `Content-Security-Policy` с директивами `default-src 'self'`, `script-src 'self' 'wasm-unsafe-eval'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: blob:`, `font-src 'self' data:`, `media-src 'self' blob:`, `connect-src 'self' ws: wss:`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors https://web.telegram.org`. Диалог идёт по WebSocket на тот же origin, поэтому `connect-src` MUST разрешать `ws:` и `wss:`. Встраивание приложения во фрейм MUST быть разрешено только Telegram Web (`https://web.telegram.org`), который показывает Telegram Mini App во фрейме, и запрещено всем остальным; приложения Telegram для телефона и компьютера открывают Mini App в собственном WebView без фрейма. `'wasm-unsafe-eval'` разрешает странице только компиляцию WebAssembly (не `eval`): без него браузер без собственного декодера Opus (iOS до 26, Firefox на Android) не загрузит WASM-декодер озвучки, и агент будет звучать в μ-law.

#### Scenario: Политика на оболочке

- **WHEN** браузер запрашивает `GET /pwa/`
- **THEN** в ответе есть `Content-Security-Policy`, содержащая `connect-src` и `frame-ancestors https://web.telegram.org`

#### Scenario: Чужой сайт во фрейме

- **WHEN** сайт, отличный от `https://web.telegram.org`, встраивает `/pwa/` во фрейм
- **THEN** браузер не показывает приложение во фрейме

#### Scenario: Заголовки на ресурсе

- **WHEN** браузер запрашивает любой файл сборки
- **THEN** в ответе есть `X-Robots-Tag: noindex`, `X-Content-Type-Options: nosniff` и `Content-Security-Policy`

#### Scenario: Заголовки на 404

- **WHEN** контейнер отвечает 404 (путь вне префикса или отсутствующий файл в `assets/`)
- **THEN** в ответе тоже есть `Content-Security-Policy`, `X-Robots-Tag` и `X-Content-Type-Options`

### Requirement: Проверка живости контейнера

Контейнер SHALL отвечать на `GET /healthz` статусом 200 и телом `ok` (`text/plain`). Адрес лежит вне префикса и предназначен только для проб оркестратора и проверки состояния образа: шлюз его не публикует. Обращения к нему MUST NOT попадать в журнал доступа.

#### Scenario: Проба

- **WHEN** оркестратор запрашивает `GET /healthz` у работающего контейнера
- **THEN** ответ 200 с телом `ok`, даже при непустом префиксе (перенаправления и 404 вне префикса на него не действуют)

### Requirement: Контейнер PWA не обрабатывает `/api/*`: путь на общем хосте выбирает шлюз

PWA SHALL ходить в API на свой origin: адрес API клиента пуст, адрес WebSocket диалога строится от `window.location`, поэтому CORS не используется. Контейнер `app-pwa` MUST NOT обрабатывать пути `/api/*` и MUST NOT отдавать на них оболочку: запросы `/api` того же хоста шлюз направляет в API (по префиксу `/api`), а `/pwa` — в `app-pwa`, до nginx PWA пути `/api/*` не доходят. У контейнера нет настройки адреса API: ему нужны только `PUBLIC_WEB_URL` и `APP_ENV`.

#### Scenario: Запрос данных из PWA

- **WHEN** PWA, открытая по `https://<хост>/pwa/`, выполняет fetch к `/api/dialogs`
- **THEN** запрос уходит на `https://<хост>/api/dialogs` — тот же origin, без CORS — и его обслуживает API

#### Scenario: Диалог по WebSocket

- **WHEN** PWA открывает диалог на странице `https://<хост>/pwa/`
- **THEN** WebSocket подключается к `wss://<хост>/api/dialogs/ws`: схема и хост берутся из `window.location`

#### Scenario: Адрес API на общем хосте

- **WHEN** браузер запрашивает `https://<хост>/api/health`
- **THEN** отвечает API, а не контейнер PWA

### Requirement: API и PWA выкатываются независимо

API и PWA SHALL выпускаться отдельными образами с собственными тегами, поэтому версии клиента и сервера на хосте могут расходиться. API MUST оставаться совместимым с предыдущей сборкой PWA: установленный service worker обновляется только по кнопке человека (см. «Обновление service worker только по кнопке»), и PWA может подолгу работать на оболочке старой сборки; контракт `/api/*` для неё меняется только добавлением полей (см. «Совместимость старых сборок» в `app-updates`). Ворота версий PWA не касаются: она не шлёт `X-Platform` и `X-App-Version`, и выкладка нового API этого MUST NOT менять.

#### Scenario: Новый API, старая оболочка

- **WHEN** выкачен новый образ API, а у человека установлен service worker предыдущей сборки PWA
- **THEN** старая оболочка продолжает работать с новым API, ответа 426 она не получает

#### Scenario: Выкладка только PWA

- **WHEN** выкачен новый образ PWA, а образ API не менялся
- **THEN** у уже установленных клиентов после проверки обновления появляется баннер новой версии, API не затронут

### Requirement: Web app manifest

Манифест `manifest.webmanifest` (под префиксом `/pwa` — `GET /pwa/manifest.webmanifest`) SHALL содержать: `name` и `short_name` «Рядом», `lang` `ru`, `start_url` и `scope` `./` (каталог манифеста: `/pwa/` при префиксе `/pwa`, `/` при пустом), `display` `standalone`, `background_color` и `theme_color` `#00051a`, `categories` `health` и `lifestyle`, иконки `pwa-192x192.png` (192x192), `pwa-512x512.png` (512x512) и `maskable-icon-512x512.png` (512x512, `purpose: maskable`). В `<head>` веб-сборки SHALL быть ссылка на манифест, `apple-touch-icon` (`apple-touch-icon-180x180.png`), `mobile-web-app-capable`, `apple-mobile-web-app-capable`, стиль строки состояния `black-translucent` и название «Рядом» для iOS; адреса манифеста и значка MUST строиться от префикса сборки; в нативные сборки эти теги MUST NOT попадать.

#### Scenario: Манифест отдаётся

- **WHEN** браузер запрашивает `/pwa/manifest.webmanifest`
- **THEN** статус 200, JSON с `name` «Рядом», `display` `standalone`, областью `/pwa/` и непустым списком `icons`

#### Scenario: Теги веб-сборки

- **WHEN** контейнер отдаёт `index.html` веб-сборки с префиксом `/pwa`
- **THEN** в нём есть `<link rel="manifest" href="/pwa/manifest.webmanifest">`, `apple-touch-icon` с адресом `/pwa/apple-touch-icon-180x180.png` и перечисленные теги для iOS

#### Scenario: Нативная сборка (мобильный)

- **WHEN** собран JS для нативной сборки (`--mode dev` или `--mode prod`)
- **THEN** в его `index.html` нет ссылки на манифест и тегов `apple-*`

### Requirement: Регистрация service worker

В веб-сборке клиент SHALL при старте регистрировать `sw.js`, лежащий рядом с `index.html`, с областью, равной префиксу сборки: `/pwa/sw.js` с областью `/pwa/` (без префикса — `/sw.js` с областью `/`). Воркер MUST NOT управлять страницами вне префикса (сайт, веб-клиент, `/api/`). Если браузер не поддерживает service worker или регистрация не удалась, приложение MUST продолжать работать без офлайн-режима и без сообщения о новой версии, не показывая ошибку.

#### Scenario: Воркер зарегистрирован

- **WHEN** человек открывает PWA по `/pwa/` в браузере с поддержкой service worker
- **THEN** у страницы появляется регистрация service worker с областью `/pwa/`

#### Scenario: Другие приложения хоста

- **WHEN** на том же хосте человек открывает сайт, веб-клиент или адрес `/api/…`
- **THEN** service worker PWA их запросы не перехватывает

#### Scenario: Регистрация не удалась

- **WHEN** регистрация `/pwa/sw.js` отклонена браузером
- **THEN** приложение работает как обычная страница, человек ошибки не видит

#### Scenario: Нативная сборка (мобильный)

- **WHEN** приложение запущено как нативное (Android или iOS)
- **THEN** service worker не регистрируется

### Requirement: Что кэширует service worker

Service worker SHALL при установке предкэшировать `index.html`, JS и CSS сборки (предел размера одного предкэшируемого файла — 4 МиБ, `maximumFileSizeToCacheInBytes`) и удалять устаревшие предкэши прежних версий. Предкэшируемый `index.html` — оболочка с метатегами, которую отдаёт контейнер (`/pwa/index.html`). На навигационные запросы (переход по адресу страницы) он SHALL отвечать закэшированным `index.html` — и онлайн, и без сети, — кроме адресов, начинающихся с `/api/` (под префиксом такие адреса лежат вне области воркера, правило страхует сборку без префикса). Он MUST NOT кэшировать ответы `/api/*` и MUST NOT перехватывать остальные запросы (fetch, WebSocket): они идут в сеть.

#### Scenario: Переход на внутренний маршрут

- **WHEN** воркер установлен и браузер переходит на `/pwa/journal/`
- **THEN** страница отвечается закэшированным `index.html`

#### Scenario: Навигация на адрес API

- **WHEN** браузер переходит по адресу, начинающемуся с `/api/`
- **THEN** воркер не подставляет `index.html`, запрос уходит в сеть

#### Scenario: Запрос данных

- **WHEN** клиент выполняет fetch к `/api/dialogs`
- **THEN** ответ не берётся из кэша воркера и не сохраняется в нём

#### Scenario: Новая версия сборки

- **WHEN** воркер новой версии установлен и активирован
- **THEN** предкэш прежней версии удаляется

### Requirement: Обновление service worker только по кнопке

Новая версия service worker SHALL ждать действия человека и MUST NOT активироваться сама: смена версии посреди разговора перезагрузила бы экран. Когда есть ожидающий воркер и страница уже управляется воркером, клиент SHALL показать баннер о новой версии с кнопками «Обновить» и «Скрыть»; «Обновить» SHALL отправить воркеру `SKIP_WAITING` и один раз перезагрузить страницу, когда новый воркер возьмёт управление; «Скрыть» MUST скрывать баннер только до перезагрузки страницы. Пока страница открыта, клиент SHALL проверять наличие новой версии раз в час (`60 * 60 * 1000` мс).

#### Scenario: Вышла новая версия

- **WHEN** новый воркер установился, а старый ещё управляет страницей
- **THEN** внизу появляется баннер о новой версии с кнопкой «Обновить», страница не перезагружается

#### Scenario: Человек нажал «Обновить»

- **WHEN** человек нажимает «Обновить»
- **THEN** ожидающий воркер получает `SKIP_WAITING`, и страница один раз перезагружается уже под новой версией

#### Scenario: Человек скрыл баннер

- **WHEN** человек нажимает «Скрыть» на баннере о новой версии
- **THEN** баннер исчезает до перезагрузки страницы
- **AND** после перезагрузки, пока воркер всё ещё ждёт, баннер появляется снова

#### Scenario: Первая установка

- **WHEN** воркер устанавливается впервые и страница ещё не управляется воркером
- **THEN** баннер о новой версии не показывается

#### Scenario: Долго открытая PWA

- **WHEN** установленная PWA остаётся открытой больше часа
- **THEN** клиент по таймеру запрашивает обновление воркера, не дожидаясь перезагрузки

### Requirement: Работа без сети

Когда service worker установлен, открытие приложения без сети (в том числе переход по любому маршруту оболочки) SHALL показывать оболочку из кэша; запросы к API без сети MUST завершаться сетевой ошибкой, обрабатываемой клиентом, а индикатор офлайна описан в `client-shell`. Без установленного воркера (первое открытие, браузер без поддержки, неудачная регистрация) оболочка без сети MUST NOT быть доступна.

#### Scenario: Повторное открытие без сети

- **WHEN** PWA уже открывалась с установленным воркером, а сети нет, и человек открывает приложение
- **THEN** оболочка загружается из кэша

#### Scenario: Первое открытие без сети

- **WHEN** сети нет, а воркер ещё ни разу не устанавливался
- **THEN** оболочка не открывается: показывать нечего, кроме страницы ошибки браузера

#### Scenario: Запрос к API без сети

- **WHEN** оболочка открыта без сети и клиент обращается к `/api/*`
- **THEN** запрос завершается сетевой ошибкой, ответ из кэша не подставляется

### Requirement: Условия показа баннера установки

В веб-сборке клиент SHALL показывать баннер установки (`InstallBanner`) внизу экрана поверх интерфейса, если приложение открыто не как установленное (ни `display-mode: standalone`, ни признак `standalone` в iOS), этот браузер не знает об установленном приложении и баннер не закрывали в последние 14 дней. В нативных сборках, в установленном PWA и в Telegram Mini App баннер MUST NOT показываться.

Вкладка браузера не может спросить, установлено ли приложение: после установки Chrome перестаёт присылать `beforeinstallprompt`, и это неотличимо от браузера, который его не присылает. Поэтому установка запоминается в `localStorage` под ключом `ryadom.install.installedAt` (общему для вкладки и окна приложения на компьютере и Android): метка SHALL записываться по событию `appinstalled` и при каждом запуске в режиме `standalone`, а при новом `beforeinstallprompt` SHALL сниматься — браузер предлагает установку, только пока приложения нет. Пока метка есть, баннер MUST NOT показываться, в том числе в открытой вкладке сразу после установки. Если хранилище недоступно, метка не записывается и баннер может показываться во вкладке.

#### Scenario: Вкладка браузера

- **WHEN** человек открывает PWA во вкладке браузера, приложение не установлено и баннер не закрывали
- **THEN** внизу экрана появляется баннер установки

#### Scenario: Установленное приложение

- **WHEN** PWA открыта с домашнего экрана в режиме `standalone`
- **THEN** баннер не показывается

#### Scenario: Вкладка браузера при установленном приложении

- **WHEN** приложение установлено, а человек открывает тот же адрес во вкладке браузера
- **THEN** баннер не показывается, даже если `beforeinstallprompt` не приходит

#### Scenario: Установка из баннера

- **WHEN** человек нажимает «Установить» и принимает системный диалог
- **THEN** баннер в этой вкладке исчезает, а не меняется на подсказку про меню браузера

#### Scenario: Приложение удалили

- **WHEN** приложение удалено, метка осталась, и браузер снова присылает `beforeinstallprompt`
- **THEN** метка снимается, баннер появляется с кнопкой «Установить»

#### Scenario: Нативная сборка (мобильный)

- **WHEN** приложение запущено как нативное
- **THEN** баннер установки не показывается

#### Scenario: Telegram Mini App

- **WHEN** PWA открыта как Mini App бота в Telegram
- **THEN** баннер установки не показывается

### Requirement: Запуск как Telegram Mini App

Та же веб-сборка SHALL работать как Telegram Mini App бота `@slyshu_ryadom_bot`: кнопка меню «Открыть» и главный Mini App бота открывают `https://слышу-рядом.рф/pwa/`. Клиент SHALL распознавать запуск из Telegram по данным запуска в адресе (`#tgWebAppData=…`) или по их копии, которую скрипт Telegram оставляет в `sessionStorage` (`__telegram__initParams`) на случай перезагрузки, и только тогда загружать скрипт Telegram (`telegram-web-app.js` из пакета `@twa-dev/sdk`, собранный в бандл с нашего origin: CSP `script-src 'self'` не меняется). В обычной вкладке скрипт Telegram MUST NOT загружаться. Mini App без подписанных данных запуска (`initData` пуст) клиент считает обычной вкладкой.

В Mini App клиент SHALL до первого экрана сообщать Telegram о готовности (`ready`), разворачиваться на всю высоту (`expand`), окрашивать шапку и фон Telegram в цвет фона приложения (`#00051a`, с версии Bot API 6.1) и отключать закрытие свайпом вниз (`disableVerticalSwipes`, с версии 7.7). Системная кнопка «Назад» Telegram SHALL показываться, когда шаг назад внутри приложения есть (открыто модальное окно, в вкладке есть шаг назад или открыта не главная вкладка), и скрываться на главном экране; её нажатие выполняет тот же шаг назад, что аппаратная кнопка Android. Ловушка истории браузера для кнопки «Назад» в Mini App MUST NOT ставиться. Пока открыт экран разговора, закрытие Mini App SHALL спрашивать подтверждение (`enableClosingConfirmation`, с версии 6.2).

События аналитики Mini App SHALL нести платформу `telegram`, а запросы — заголовок `x-client-id: ryadom-telegram` (в списке сессий — «Мини-приложение в Telegram»).

#### Scenario: Открытие из бота

- **WHEN** человек нажимает «Открыть» в чате с ботом
- **THEN** PWA открывается во весь экран Telegram, шапка Telegram окрашена в цвет приложения
- **AND** свайп вниз не закрывает приложение

#### Scenario: Кнопка «Назад» Telegram

- **WHEN** человек открыл экран внутри вкладки (например, «Память» из профиля)
- **THEN** в шапке Telegram видна кнопка «Назад», и её нажатие возвращает на предыдущий экран
- **AND** на главном экране без модальных окон кнопки «Назад» нет

#### Scenario: Закрытие во время разговора

- **WHEN** открыт экран разговора и человек закрывает Mini App
- **THEN** Telegram спрашивает подтверждение закрытия

#### Scenario: Обычная вкладка

- **WHEN** PWA открыта в браузере по адресу без данных запуска Telegram
- **THEN** скрипт Telegram не загружается и приложение ведёт себя как PWA

### Requirement: Текст подсказки и кнопка «Установить»

Содержимое баннера установки SHALL зависеть от среды. Если браузер выдал системное предложение установки (`beforeinstallprompt`), баннер предлагает установить приложение и показывает кнопку «Установить», которая вызывает системный диалог. Иначе, если страница открыта во встроенном браузере мессенджера или соцсети (Telegram, VK, Facebook, Instagram, Line), баннер просит открыть её в Safari (iOS) или в браузере. Иначе, на iOS (включая iPadOS, представляющийся Mac с сенсорным экраном), баннер подсказывает путь «Поделиться» → «На экран «Домой»». Иначе баннер подсказывает пункт меню браузера «Установить приложение». Кнопка «Установить» MUST показываться только в первом случае; системное предложение MUST использоваться один раз — после ответа человека или события `appinstalled` кнопка исчезает.

#### Scenario: Браузер предлагает установку

- **WHEN** браузер сообщил `beforeinstallprompt`
- **THEN** баннер предлагает установку и показывает «Установить»
- **AND** по нажатию открывается системный диалог установки

#### Scenario: Safari на iPhone

- **WHEN** событие `beforeinstallprompt` недоступно и страница открыта в Safari на iPhone
- **THEN** баннер без кнопки «Установить» подсказывает «Поделиться» → «На экран «Домой»»

#### Scenario: Встроенный браузер мессенджера

- **WHEN** страница открыта во встроенном браузере Telegram
- **THEN** баннер без кнопки «Установить» просит открыть страницу в системном браузере

#### Scenario: Браузер без события

- **WHEN** событие `beforeinstallprompt` не приходило, страница открыта не на iOS и не во встроенном браузере
- **THEN** баннер без кнопки «Установить» подсказывает найти «Установить приложение» в меню браузера

#### Scenario: Диалог использован

- **WHEN** человек ответил на системный диалог установки (принял или отклонил)
- **THEN** кнопка «Установить» больше не показывается

### Requirement: Закрытие баннера установки и память о нём

Кнопка закрытия баннера (доступное имя «Скрыть») SHALL сразу скрывать баннер и записывать текущее время в `localStorage` под ключом `ryadom.install.dismissedAt`; следующие 14 дней (`DISMISS_DAYS`) баннер MUST NOT показываться при любых загрузках, после 14 дней — SHALL появиться снова. Если хранилище недоступно, баннер скрывается только на текущей странице и MAY вернуться при следующей загрузке.

#### Scenario: Закрыли и перезагрузили

- **WHEN** человек нажимает «Скрыть» и затем перезагружает страницу
- **THEN** баннер не показывается

#### Scenario: Прошло больше 14 дней

- **WHEN** с момента закрытия прошло больше 14 дней и человек открывает PWA в браузере
- **THEN** баннер показывается снова

#### Scenario: Хранилище недоступно

- **WHEN** `localStorage` недоступен, человек закрывает баннер и перезагружает страницу
- **THEN** баннер после закрытия исчезает, а после перезагрузки показывается снова

### Requirement: Веб-клиент не поставляется как PWA

Веб-клиент (`app/apps/web`, Next.js) SHALL NOT поставляться как PWA: у него нет манифеста, service worker и баннера установки. PWA-доставку обеспечивает только мобильный клиент (`app/apps/mobile`), который раздаёт контейнер `app-pwa`.

#### Scenario: Открытие веб-клиента (веб)

- **WHEN** человек открывает веб-клиент в браузере
- **THEN** страница не регистрирует service worker, не ссылается на манифест и не показывает баннер установки
