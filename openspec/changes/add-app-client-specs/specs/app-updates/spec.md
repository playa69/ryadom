# Дельта-спецификация: app-updates

## Purpose

Нативные приложения узнают об обновлениях, спрашивая API: по номеру сборки решается, нужно ли обновить приложение через магазин (блокирующий экран или мягкое предложение), а по версии JS — можно ли без магазина подтянуть новый пакет интерфейса (OTA). Веб-клиент и PWA в этом не участвуют: у них ворот версий нет, а оболочка PWA обновляется по кнопке (см. `pwa-delivery`). Спека описывает ответ `GET /api/app-status`, ворота версий (426), раздачу `GET /api/ota/<file>`, политику релизов и то, что видит человек; нативные сборки описаны в `native-app-build`. Реализовано в `app/services/api/src/lib/release-policy.ts`, `app/services/api/src/lib/version-gate.ts`, `app/services/api/src/lib/ota-bundle.ts`, `app/services/api/src/routes/app-status.ts`, `app/services/api/src/routes/ota-bundle.ts`, `app/apps/mobile/scripts/build-ota-bundle.mjs`, `app/apps/mobile/src/client/lib/app-update.ts`, `app/apps/mobile/src/client/components/AppUpdateGate.tsx` и `app/packages/contracts/src/api/app-status.ts`.

## ADDED Requirements

### Requirement: Запрос статуса версий

`GET /api/app-status` SHALL быть открыт для клиента любой версии и без авторизации. Параметры: `platform` (`android` или `ios`), `version_code` (десятичное целое, от 1 до 10 цифр) и необязательный `js_version` (версия из одного–четырёх числовых сегментов по 1–6 цифр, например `1.2.3`). Отсутствующие или непригодные параметры MUST давать 400 с телом `{ "errorMessage": … }`. Успешный ответ — конверт `{ "status": true, "result": … }`, где `result` содержит `runtimeUpdate`, `latestVersionCode`, `storeUrl`, `downloadUrl`, `jsUpdate`, `jsVersion`, `jsBundleUrl` и `jsBundleChecksum` (тип `AppStatusApiResponse` из `app/packages/contracts/src/api/app-status.ts`).

#### Scenario: Статус для Android

- **WHEN** клиент запрашивает `GET /api/app-status?platform=android&version_code=12&js_version=1.2.0`
- **THEN** ответ 200 с конвертом и полями `runtimeUpdate`, `latestVersionCode`, `storeUrl`, `downloadUrl`, `jsUpdate`

#### Scenario: Непригодные параметры

- **WHEN** запрос содержит `platform=web`, или `version_code=abc`, или не содержит параметров вовсе
- **THEN** ответ 400 с телом `{ "errorMessage": … }`

#### Scenario: Версия ниже минимальной

- **WHEN** `version_code` ниже минимума платформы
- **THEN** маршрут всё равно отвечает 200, ворота версий его не блокируют

### Requirement: Нативная ось — минимум и последняя сборка

Поле `runtimeUpdate` SHALL принимать значение `required`, если `version_code` ниже минимального номера сборки платформы; `available`, если он не ниже минимума, но ниже последнего номера сборки платформы; иначе `not_available`. `latestVersionCode` SHALL быть последним номером сборки платформы, `storeUrl` — адресом магазина платформы (или `null`), `downloadUrl` — прямой ссылкой на APK только для Android (для iOS и при незаданной ссылке — `null`). Нулевой минимум MUST отключать блокировку, нулевая последняя сборка — предложение; по умолчанию оба значения равны 0.

#### Scenario: Ниже минимума

- **WHEN** для Android минимум 10, последняя 12, а клиент сообщает `version_code=9`
- **THEN** `runtimeUpdate` равен `required`

#### Scenario: Между минимумом и последней

- **WHEN** для Android минимум 10, последняя 12, а клиент сообщает `version_code=11`
- **THEN** `runtimeUpdate` равен `available`

#### Scenario: Последняя сборка

- **WHEN** для Android последняя 12, а клиент сообщает `version_code=12`
- **THEN** `runtimeUpdate` равен `not_available`

#### Scenario: Платформы независимы

- **WHEN** для iOS минимум 5, последняя 7, а клиент сообщает `platform=ios&version_code=6`
- **THEN** `runtimeUpdate` равен `available`, `latestVersionCode` равен 7, `downloadUrl` равен `null`

#### Scenario: Политика не задана

- **WHEN** минимум и последняя сборка платформы равны 0
- **THEN** любой `version_code` получает `runtimeUpdate` `not_available`

### Requirement: Откуда берётся политика релизов

Нативная ось SHALL читаться из переменных окружения процесса API: `MOBILE_ANDROID_MIN_VERSION_CODE`, `MOBILE_ANDROID_LATEST_VERSION_CODE`, `MOBILE_ANDROID_STORE_URL`, `MOBILE_ANDROID_DOWNLOAD_URL`, `MOBILE_IOS_MIN_VERSION_CODE`, `MOBILE_IOS_LATEST_VERSION_CODE`, `MOBILE_IOS_STORE_URL`; пустая строка означает «не задано», номера — неотрицательные целые (по умолчанию 0), адреса — корректные URL. Ось JS SHALL браться из манифеста OTA-пакетов, запечённого в образ: при `APP_ENV=staging` действует пакет варианта `dev`, при `APP_ENV=prod` — варианта `prod`, при `APP_ENV=local` пакета нет. Политика MUST вычисляться один раз при старте процесса, поэтому изменение значений вступает в силу только после перезапуска; некорректное значение MUST останавливать запуск API, а отсутствующий или повреждённый манифест — только отключать ось JS, не мешая запуску.

#### Scenario: Правка номеров после релиза в магазине

- **WHEN** после публикации в магазине повышен `MOBILE_ANDROID_LATEST_VERSION_CODE` и API перезапущен
- **THEN** сборки Android ниже нового номера получают `runtimeUpdate` `available`

#### Scenario: Некорректное значение

- **WHEN** `MOBILE_ANDROID_MIN_VERSION_CODE` не целое число или `MOBILE_ANDROID_STORE_URL` не URL
- **THEN** API при запуске завершается с перечнем ошибок окружения

#### Scenario: Окружение без пакета

- **WHEN** `APP_ENV=local` или манифеста пакетов в образе нет
- **THEN** ось JS отключена: `jsUpdate` равен `not_available`, `jsVersion` равен `null`, запуск не нарушен

#### Scenario: Пакет по окружению

- **WHEN** `APP_ENV=staging`
- **THEN** статус указывает на пакет варианта `dev`, а при `APP_ENV=prod` — на пакет варианта `prod`

### Requirement: Ворота версий отвечают 426

HTTP-запрос с допустимым `X-Platform` (`android` или `ios`) и заголовком `X-App-Version` SHALL получать ответ 426 с телом `{ "errorMessage": … }`, если номер сборки ниже минимума платформы; нечисловой номер считается нулём. Запросы без этих заголовков (веб, PWA, мониторинг), запросы с неизвестной платформой и запросы `OPTIONS` MUST NOT проверяться. `/api/app-status`, `/api/health` и `/api/ota/*` MUST оставаться открытыми для любой версии. Ответ 426 SHALL нести заголовки CORS. Устаревший JS сам по себе клиента не отрезает. Ворота действуют на HTTP-запросы; подключение WebSocket `/api/dialogs/ws` ими не проверяется.

#### Scenario: Сборка ниже минимума

- **WHEN** сборка Android с `X-App-Version: 9` при минимуме 10 обращается к `GET /api/auth/me`
- **THEN** ответ 426, в нём есть заголовок `Access-Control-Allow-Origin`

#### Scenario: Нет заголовков версии

- **WHEN** браузер обращается к `GET /api/auth/me` без `X-Platform` и `X-App-Version`
- **THEN** ворота пропускают запрос, дальше отвечает сам маршрут (например, 401 без токена)

#### Scenario: Открытые адреса

- **WHEN** сборка ниже минимума обращается к `/api/app-status`, `/api/health` или `/api/ota/<файл>`
- **THEN** запрос доходит до маршрута, а не получает 426

#### Scenario: Нечисловой номер

- **WHEN** заголовок `X-App-Version` не число, а минимум платформы больше нуля
- **THEN** ответ 426

#### Scenario: Минимум не задан

- **WHEN** минимум платформы равен 0
- **THEN** ни одна сборка этой платформы не получает 426

### Requirement: Решение сервера по версии JS

Поле `jsUpdate` SHALL вычисляться только если клиент передал `js_version` и для окружения есть пакет, а нативная сборка клиента способна его выполнить (константа `OTA_MIN_NATIVE_BUILD` на платформу; по умолчанию ограничений нет). Версии MUST сравниваться по сегментам как числа (недостающий сегмент равен нулю, `1.0.10` новее `1.0.9`, `1.2` равна `1.2.0`): версия клиента ниже серверной даёт `available`, выше — `required` (откат: образ с прежней версией остаётся источником правды), равная — `not_available`. `jsBundleUrl` и `jsBundleChecksum` SHALL заполняться только при `available` и `required`, иначе быть `null`; `jsVersion` — версия пакета окружения (или `null`, если пакета нет). `jsBundleUrl` MUST строиться как `PUBLIC_APP_URL` + `/api/ota/` + имя файла, закодированное для URL.

#### Scenario: Клиент отстал

- **WHEN** клиент с `js_version=1.1.5` запрашивает статус при версии пакета `1.2.0`
- **THEN** `jsUpdate` равен `available`, а `jsBundleUrl` и `jsBundleChecksum` заполнены

#### Scenario: Клиент новее сервера

- **WHEN** клиент с `js_version=1.3.0` запрашивает статус при версии пакета `1.2.0`
- **THEN** `jsUpdate` равен `required`

#### Scenario: Версии совпадают

- **WHEN** `js_version` равна версии пакета
- **THEN** `jsUpdate` равен `not_available`, `jsBundleUrl` и `jsBundleChecksum` равны `null`

#### Scenario: Клиент без OTA

- **WHEN** запрос не содержит `js_version`
- **THEN** `jsUpdate` равен `not_available`

#### Scenario: Сравнение сегментов числами

- **WHEN** сравниваются `1.0.10` и `1.0.9`
- **THEN** `1.0.10` считается новее

#### Scenario: Нативная сборка слишком старая для пакета

- **WHEN** для платформы задан `OTA_MIN_NATIVE_BUILD`, а клиент старше этой сборки
- **THEN** `jsUpdate` равен `not_available`, `jsBundleUrl` равен `null`

### Requirement: Раздача пакета OTA

`GET /api/ota/<file>` SHALL отдавать zip-архив только под тем именем файла, которое пакет окружения указал в статусе; для любого другого имени, а также когда пакета нет, ответ MUST быть 404. Успешный ответ SHALL иметь `Content-Type: application/zip` и `Cache-Control: public, max-age=31536000, immutable` (имя файла содержит версию). Маршрут MUST быть открыт без авторизации и для любой версии клиента.

#### Scenario: Имя из статуса

- **WHEN** клиент запрашивает `GET /api/ota/<file>` с именем, полученным из `jsBundleUrl`
- **THEN** ответ 200 с архивом и заголовками `application/zip` и `immutable`

#### Scenario: Чужое или старое имя

- **WHEN** запрашивается имя файла другого варианта или прежней версии
- **THEN** ответ 404 с телом `{ "errorMessage": … }`

#### Scenario: Пакета нет

- **WHEN** окружение без пакета (`APP_ENV=local` или нет манифеста) получает запрос к `/api/ota/<file>`
- **THEN** ответ 404, и даже сборка ниже минимума получает 404, а не 426

### Requirement: Сборка OTA-пакетов и манифест

Сборка образа API SHALL после сборки PWA выполнять `build:ota` (`scripts/build-ota-bundle.mjs`): для вариантов `prod` и `dev` собрать JS (`vite build --mode <вариант>`), упаковать содержимое `dist/client` в zip так, чтобы `index.html` лежал в корне архива, назвать его `ryadom-<вариант>-<версия>.zip`, посчитать SHA-256 архива и записать `ota/manifest.json` вида `{ "prod": { version, file, checksum }, "dev": { … } }`. Версия пакета SHALL быть `<version из app/apps/mobile/package.json>.<OTA_BUILD_NUMBER>` (без номера — `0`). Адреса `VITE_PROD_API_URL`, `VITE_PROD_WEB_URL`, `VITE_STAGING_API_URL`, `VITE_STAGING_WEB_URL` MUST передаваться в сборку образа аргументами и вшиваться в пакеты; каталог `ota` MUST копироваться в образ рядом с `pwa`. Пакет уезжает тем же деплоем, что и сервер, отдельного шага публикации нет.

#### Scenario: Сборка с номером

- **WHEN** образ собирается при `version` `0.1.0` и `OTA_BUILD_NUMBER=42`
- **THEN** создаются `ryadom-prod-0.1.0.42.zip` и `ryadom-dev-0.1.0.42.zip`, а в манифесте у обоих `version` равна `0.1.0.42`

#### Scenario: Сборка без номера

- **WHEN** `OTA_BUILD_NUMBER` не задан
- **THEN** версия пакета равна `0.1.0.0`

#### Scenario: Состав архива

- **WHEN** архив распакован
- **THEN** `index.html` лежит в его корне, пути внутри архива с прямыми слэшами

#### Scenario: Ошибка шага сборки

- **WHEN** сборка JS или упаковка одного из вариантов завершается ошибкой
- **THEN** сборка образа прерывается, манифест не записывается

### Requirement: Нативное приложение сообщает версии в заголовках

Нативное приложение SHALL добавлять к каждому запросу к API (включая обновление токена) заголовки `X-Platform` (`android` или `ios`), `X-App-Version` (номер сборки) и, только если сборка находится на своём канале OTA, `X-Js-Version` (версия `version` из `app/apps/mobile/package.json` на момент сборки JS). Если номер сборки прочитать не удалось, заголовки MUST NOT добавляться. Браузер (веб и PWA) MUST NOT отправлять эти заголовки.

#### Scenario: Запрос из боевой сборки

- **WHEN** боевая сборка Android обращается к API
- **THEN** запрос содержит `X-Platform: android`, `X-App-Version` и `X-Js-Version`

#### Scenario: Номер сборки недоступен

- **WHEN** нативное приложение не смогло прочитать номер сборки
- **THEN** запросы уходят без заголовков версий

### Requirement: Канал OTA зависит от среды сборки

Нативная сборка SHALL участвовать в OTA (отправлять `X-Js-Version` и параметр `js_version`) только если это вариант `prod` или среда выбрана `staging`: пакеты собираются по вариантам, `prod` получает пакет `prod`, `staging` — пакет `dev`. Вариант `dev`, направленный на `prod` или `local`, MUST NOT отправлять версию JS и получать чужой пакет, иначе чужой минимум мог бы его заблокировать.

#### Scenario: Dev-сборка на staging

- **WHEN** сборка варианта `dev` работает со средой `staging`
- **THEN** она отправляет версию JS и получает пакет варианта `dev`

#### Scenario: Dev-сборка на prod

- **WHEN** сборка варианта `dev` переключена на среду `prod`
- **THEN** запросы статуса и API идут без версии JS, и пакет не предлагается

#### Scenario: Боевая сборка

- **WHEN** работает сборка варианта `prod`
- **THEN** она всегда участвует в OTA и получает пакет варианта `prod`

### Requirement: Когда клиент проверяет статус версий

Нативное приложение SHALL запрашивать `GET /api/app-status` (без авторизации и без заголовков версий, номер сборки и платформа — в параметрах, `js_version` — если сборка на канале OTA) при запуске, при возврате на передний план, при появлении сети после потери и при любом ответе 426. Проверки при возврате и при появлении сети MUST выполняться не чаще раза в минуту (60 с от последней успешной проверки), запуск и ответ 426 — всегда; одновременные проверки MUST объединяться в одну. Сбой запроса (нет сети, ответ не 2xx, неожиданный формат тела) MUST оставлять экран без изменений: при ответе не 2xx и неожиданном формате ошибка пишется в консоль, повтор — по следующему поводу. Если номер сборки прочитать не удалось, проверка MUST NOT выполняться. Веб-клиент и PWA статус не запрашивают.

#### Scenario: Запуск

- **WHEN** нативное приложение запускается
- **THEN** выполняется проверка статуса, независимо от времени последней проверки

#### Scenario: Частое возвращение в приложение

- **WHEN** человек возвращается в приложение чаще раза в минуту после успешной проверки
- **THEN** повторного запроса статуса нет

#### Scenario: Ответ 426 на любой запрос

- **WHEN** любой запрос к API вернул 426
- **THEN** выполняется проверка статуса, даже если с прошлой прошло меньше минуты

#### Scenario: Сеть вернулась

- **WHEN** после потери сети она появилась и с последней успешной проверки прошло больше минуты
- **THEN** выполняется проверка статуса

#### Scenario: Сбой проверки

- **WHEN** запрос статуса вернул 500 или тело неожиданного формата
- **THEN** человек ничего не видит, в консоль пишется ошибка, следующая проверка пройдёт по следующему поводу

### Requirement: Блокирующий экран «нужно обновить приложение»

Если статус содержит `runtimeUpdate` `required`, нативное приложение SHALL показать поверх всего экран «Нужно обновить приложение», который нельзя закрыть; кнопка «Назад» на Android MUST сворачивать приложение. Экран SHALL предлагать «Обновить в магазине», если есть `storeUrl`, и «Скачать напрямую», если есть `downloadUrl`; если нет ни одного адреса, он MUST предлагать «Открыть страницу загрузки» (адрес сайта + `/download`). Обновление JS в этом случае MUST NOT применяться. Сессия человека MUST сохраняться: ответ 426 не завершает вход, поэтому после обновления входить заново не нужно.

#### Scenario: Есть магазин и прямая ссылка

- **WHEN** статус содержит `required`, `storeUrl` и `downloadUrl`
- **THEN** на экране две кнопки: «Обновить в магазине» и «Скачать напрямую»

#### Scenario: Адресов нет

- **WHEN** статус содержит `required`, а `storeUrl` и `downloadUrl` равны `null`
- **THEN** на экране одна кнопка «Открыть страницу загрузки», ведущая на `/download` сайта

#### Scenario: Кнопка «Назад»

- **WHEN** на Android человек нажимает «Назад» на этом экране
- **THEN** приложение сворачивается, экран остаётся

#### Scenario: Сессия после 426

- **WHEN** обновление токена вернуло 426
- **THEN** токены не стираются и после установки новой сборки человек остаётся в аккаунте

#### Scenario: Проверка статуса не удалась

- **WHEN** запрос статуса после ответа 426 завершился ошибкой
- **THEN** экран не показывается, запросы к API продолжают получать 426, а проверка повторится по следующему поводу

### Requirement: Мягкое предложение обновить приложение

Если статус содержит `runtimeUpdate` `available`, нативное приложение SHALL показать закрываемый баннер о новой версии с кнопкой «Обновить», которая открывает `storeUrl`, а если его нет — `downloadUrl`, а если нет и его — адрес сайта + `/download`. Кнопка закрытия (доступное имя «Скрыть») MUST запоминать `latestVersionCode` в локальном хранилище (ключ `ryadom.update.dismissedVersionCode`): для того же номера баннер больше не показывается, для более нового — показывается снова. Если хранилище недоступно, баннер MAY показываться снова. Статус `not_available` MUST убирать баннер.

#### Scenario: Вышла новая версия

- **WHEN** статус содержит `available` и `storeUrl`
- **THEN** показывается баннер, «Обновить» открывает магазин

#### Scenario: Закрыли баннер

- **WHEN** человек закрывает баннер при `latestVersionCode` 12 и приложение перезапускается
- **THEN** при том же `latestVersionCode` баннера нет

#### Scenario: Вышла ещё более новая версия

- **WHEN** после закрытия баннера последняя сборка платформы выросла с 12 до 13
- **THEN** баннер показывается снова

### Requirement: Применение пакета OTA на устройстве

Если `jsUpdate` равен `required` и есть `jsBundleUrl`, нативное приложение SHALL показать экран обновления, скачать пакет (если пакет этой версии уже скачан, использовать его), передав плагину контрольную сумму, и применить его перезапуском WebView; при ошибке экран MUST убираться, человека не блокировать, повтор — по следующему поводу проверки. Если `jsUpdate` равен `available` и есть `jsBundleUrl`, приложение SHALL тихо скачать пакет и назначить его на следующий запуск, не повторяя загрузку для уже скачанной версии (ключ `ryadom.update.nextJsVersion`); при ошибке загрузка повторяется при следующей проверке. При первом запуске после установки новой нативной сборки (в хранилище уже есть номер прежней сборки, и он отличается от текущего; при чистой установке номера нет) `available` MUST обрабатываться как `required`. `required` без `jsBundleUrl` MUST игнорироваться.

#### Scenario: Обязательное применение

- **WHEN** статус содержит `jsUpdate` `required` и `jsBundleUrl`
- **THEN** показывается экран обновления, пакет скачивается и применяется, WebView перезапускается

#### Scenario: Скачивание не удалось

- **WHEN** при `required` загрузка пакета завершилась ошибкой
- **THEN** экран обновления исчезает, человек продолжает работу, повтор будет при следующей проверке

#### Scenario: Тихая загрузка

- **WHEN** статус содержит `jsUpdate` `available`
- **THEN** пакет скачивается в фоне без экранов и применяется при следующем запуске приложения

#### Scenario: Версия уже скачана

- **WHEN** пакет этой версии уже назначен на следующий запуск
- **THEN** новая загрузка не начинается

#### Scenario: Первый запуск после обновления из магазина

- **WHEN** приложение впервые запускается после установки новой нативной сборки и статус содержит `available`
- **THEN** пакет применяется немедленно, как при `required`

#### Scenario: Обязательное обновление без адреса

- **WHEN** статус содержит `jsUpdate` `required`, а `jsBundleUrl` равен `null`
- **THEN** обновление JS не выполняется

### Requirement: Целостность и откат пакета на устройстве

Нативное приложение SHALL передавать плагину обновлений SHA-256 архива из `jsBundleChecksum`: архив, не совпавший с суммой, плагин отвергает, и загрузка считается неудачной. При каждом запуске нативной сборки приложение MUST вызывать `notifyAppReady`, подтверждая, что интерфейс стартовал; если подтверждения нет, плагин возвращает предыдущий пакет. Сбой этого вызова MUST фиксироваться в консоли.

#### Scenario: Подменённый архив

- **WHEN** скачанный архив не совпадает с `jsBundleChecksum`
- **THEN** загрузка считается неудачной, пакет не применяется

#### Scenario: Пакет не запустился

- **WHEN** после применения пакета интерфейс не дошёл до старта и `notifyAppReady` не вызван
- **THEN** плагин возвращает предыдущий пакет

#### Scenario: Откат образа на сервере

- **WHEN** на сервере задеплоен образ с более старой версией пакета, чем версия JS, которую сообщает устройство
- **THEN** сервер отвечает `jsUpdate` `required`
- **AND** сработает ли это для устройства, пока версия пакета содержит номер сборки, а клиент сообщает только `version` из `package.json`, — «Open Questions» в `design.md`

### Requirement: Ворота версий и OTA не действуют в вебе и PWA

Веб-клиент (`app/apps/web`) и PWA SHALL работать без ворот версий: они не отправляют `X-Platform` и `X-App-Version`, поэтому не получают 426, не запрашивают `/api/app-status` и не получают OTA-пакеты. Оболочка PWA обновляется только service worker по кнопке (см. `pwa-delivery`).

#### Scenario: PWA при высоком минимуме (мобильный)

- **WHEN** минимум нативной платформы поднят, а человек работает в PWA
- **THEN** запросы PWA не получают 426 и экран обновления не показывается

#### Scenario: Запуск PWA (мобильный)

- **WHEN** PWA запускается в браузере
- **THEN** запрос `/api/app-status` не отправляется, регистрируется только service worker

#### Scenario: Веб-клиент (веб)

- **WHEN** человек работает в веб-клиенте
- **THEN** экрана «нужно обновить приложение» и баннера новой версии нет

### Requirement: Совместимость старых сборок

Нативные сборки живут месяцами, поэтому сервер MUST отрезать старую сборку только по нативному минимуму, а контракт диалогов (REST и WebSocket, `app/packages/contracts/src/api/dialogs.ts`) SHALL оставаться стабильным и меняться только добавлением полей. Клиент SHALL читать ответ `app-status` терпимо: неизвестные поля игнорируются, а ответ, где `runtimeUpdate` или `jsUpdate` не из допустимых значений (`not_available`, `available`, `required`), считается неисправным — экран не меняется, ошибка пишется в консоль.

#### Scenario: Новое поле в ответе

- **WHEN** сервер добавляет в ответ `app-status` новое поле
- **THEN** сборки, не знающие о нём, продолжают работать, поле игнорируется

#### Scenario: Неизвестное значение

- **WHEN** `runtimeUpdate` или `jsUpdate` в ответе имеет значение вне допустимых
- **THEN** клиент не показывает ни блокировку, ни баннер, в консоль пишется ошибка

#### Scenario: Старая сборка выше минимума

- **WHEN** сборка старше последней, но не ниже минимума, обращается к API
- **THEN** она получает ответы без 426, а предложение обновиться для неё мягкое (баннер)
