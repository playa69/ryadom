# Design: add-agent-service

## Context

Backend «Слышу Рядом» распланирован (5 change'ов в openspec/changes/), но конвейер реплики в add-backend-sessions-streaming пока вписан внутрь backend с GigaChat. Фактические вводные изменились: получен OpenAI-совместимый ключ, модели крутятся в Cloud.ru (Evolution Foundation Models, endpoint `https://foundation-models.api.cloud.ru/v1`, данные в РФ), а в k8s выделен namespace `agent`. Требования — см. specs `agent-core`, `speech-pipeline`, `agent-api` этого change'а.

## Goals / Non-Goals

**Goals:**

- Отдельный сервис `agent/` в монорепо: весь конвейер реплики (ASR → safety → эмоции → retrieval → LLM → TTS) за внутренним HTTP/WS API.
- LLM — только OpenAI-совместимый интерфейс (Cloud.ru), без привязки к GigaChat SDK.
- Кризисная ветвь — детерминированная и быстрая, не зависящая от генеративной модели.
- Независимый деплой/масштабирование agent в одноимённом namespace.

**Non-Goals:**

- Консолидация памяти L2/L3 и фоновые задачи (отдельные change'ы); сводку диалога agent строит сам при завершении (см. specs `agent-api`).
- Публичный API agent (наружу смотрит только вызывающая сторона — шлюз).
- Замена SaluteSpeech как голосового провайдера.
- Переписывание уже распланированного backend (координация — через openspec-update-change для add-backend-sessions-streaming).

## Decisions

### D1: Отдельный сервис, а не библиотека в backend

`agent/` — самостоятельное FastAPI-приложение с собственным Dockerfile, деплоится в ns `agent`. Альтернатива — Python-пакет, импортируемый backend'ом: проще на старте, но связывает релизы, мешает масштабировать LLM/ASR/TTS-поды отдельно от API-подов и размазывает ПДн-обработку по двум контурам. Выбран сервис: в ONBOARDING.md ns `agent` уже выделен именно под «сервисы логики агента».

### D2: Транспорт шлюз → agent: REST для диалогов и один WebSocket на диалог

Диалог — ресурс agent: `POST/GET /v1/users/{userId}/dialogs…` для начала, журнала, истории, завершения и стирания, а текстовые и голосовые реплики идут по одному WebSocket `/v1/users/{userId}/dialogs/{dialogId}/ws`. Голос — двоичные кадры PCM16 внутри того же сокета, текст — JSON-кадры (`user_message`, `assistant_delta`, …). Полный перечень кадров — в specs `agent-api`; шлюз проксирует их клиенту почти 1:1.

Первоначальная версия — «ход»: `POST /internal/v1/turns` (SSE) для текста и WS `/internal/v1/turns/ws` для голоса, со всем контекстом (`session_id`, `mode`, `incognito`, `voice_id`, флаги) в каждом запросе. Не выбрана по трём причинам: (1) у «хода без состояния» нет журнала, истории и сводки, а экраны приложения (возобновление диалога, журнал, итог «что забираешь с собой») их требуют, так что хранение всё равно пришлось бы строить на стороне вызывающей; (2) два транспорта дублируют код хода (этот риск был в первой версии design); (3) перебивание озвучки (`tts_cancel`) и приветствие естественно живут в уже открытом сокете диалога. Кроме того, у «хода» нет понятия «клиент оборвался — перечитал историю»: надёжность доставки здесь строится на истории агента как источнике истины, а не на повторной отправке.

Альтернативы: gRPC (нет в стеке, лишняя toolchain-сложность); chunked-upload поверх HTTP (полудуплекс — нет partial-транскриптов, пока пользователь говорит).

### D3: LLM-провайдер — OpenAI-совместимый API Cloud.ru через официальный `openai` SDK

Один клиент `CloudRuLLMClient` поверх `openai.AsyncOpenAI(base_url=..., api_key=...)`: chat completions со `stream=True` для генерации, отдельные модели из конфига для кризис/эмоции-классификаторов (дешёвые, с `response_format=json`) и эмбеддингов. Альтернатива — GigaChat SDK: отпала, т.к. выдан OpenAI-совместимый ключ и модели уже в Cloud.ru (152-ФЗ, данные в РФ). Замена провайдера в будущем = смена `base_url`/моделей в конфиге, код не трогаем.

### D4: Конвейер как LangGraph-граф состояний

Граф `turn_graph` (StateGraph): `safety_fast` (словари/эвристики, локально, ~0 мс) → `safety_llm` (классификатор на дешёвой модели, только если эвристики не дали `red`) → условная ветвь `crisis` (детерминированный шаблон + ресурсы помощи, END) | `emotion` → `retrieve` → `generate` (стрим) → `tts` (если голосовой ход). Состояние — `TurnState` (текст реплики, контекст сессии, safety, эмоции, память, артефакты). Альтернатива — ручная оркестрация async-функциями: дешевле по зависимостям, но режимы/ветвления (кризис, инкогнито, деградации) быстро превращаются в лапшу if'ов; LangGraph даёт явный граф, стриминг событий нод и готовые точки расширения (инструменты, memory). Инкогнито — флаг в состоянии: нода `retrieve` пропускается, артефакты для памяти не формируются.

### D5: Режимы диалога — промпт-пакеты, а не отдельные графы

Один граф; режим (`vent`/`chat`/`gestalt_diary`/`recovery`/`rituals`) выбирает системный промпт-пакет (системка + few-shot + ограничения стиля) из реестра `app/graph/prompts/<mode>.py`. `warmth` отклоняется валидацией на границе API. Отдельные графы на режим — избыточны: ветвления хватает на уровне промптов и параметров retrieval.

### D6: Agent владеет данными диалогов — собственная БД `agent` (pgvector)

Agent хранит диалоги, сообщения (с `emo_tags` и эмбеддингом), сводки и факты памяти L2 в собственной БД `agent` (PostgreSQL 16 + pgvector; БД `agent` и роль `developer` уже выданы в ns `agent`), со своими миграциями. Вызывающая сторона диалогов не хранит: она проверяет аккаунт и лимиты канала, а принадлежность диалога пользователю проверяет agent (`404` на любую пару `userId`/`dialogId` без совпадения, см. specs `agent-api`). Удаление аккаунта вызывает `DELETE /v1/users/{userId}`, и agent синхронно стирает всё, что знает о человеке. Retrieval: vector-поиск по `messages.embedding` + факты L2 + вес давности + время с последнего диалога (из собственной истории).

Первоначальная версия: agent читает БД backend (SELECT на `memory_facts`, `messages`, `session_summaries`) и ничего не пишет, а артефакты для записи уходят backend'у в `turn.done`. Не выбрана: (1) coupling на чужую схему был главным риском этого change'а, у собственной БД его нет; (2) историю, журнал и сводки пришлось бы отдавать клиенту через backend, хотя обрабатывает их agent: лишний хоп и дублирование схем; (3) «стереть всё» пришлось бы выполнять у двух владельцев данных вместо одного; (4) agent использует историю для памяти и антизависимого контура, и с собственной БД ему не нужно ждать записи backend'а, чтобы её увидеть.

Trade-off: agent становится владельцем ПДн-данных (152-ФЗ, данные в РФ — БД остаётся в нашем кластере), ему нужны миграции, бэкапы и план удаления.

### D7: Кризис-классификатор — две ступени, recall-first

Ступень 1: локальные словари/регулярки суицидальных маркеров (мгновенно, без сети). Ступень 2: LLM-классификатор (JSON: level + rationale) на дешёвой модели. Любое сомнение → эскалация уровня вверх. Ответ при `red` — статичные шаблоны деэскалации (кадр `safety` с текстом). Горячие линии agent не присылает: список линий помощи ведёт вызывающая сторона (экран «Если сейчас тяжело» подставляет их из своего справочника), так номера живут в одном месте. Никакой генеративной импровизации в кризисной ветви.

### D8: PII-фильтрация — локальный NER (natasha) + regex

Перед внешними вызовами текст прогоняется через natasha (русский NER: PER/LOC/ORG) и regex (телефоны, паспорта, email): сущности → плейсхолдеры `[PER_1]` с маппингом в памяти запроса; после генерации — обратная подстановка. Альтернатива — NER через LLM: внешний вызов сам по себе утёк бы ПДн. Аудио не фильтруется (уходит в SaluteSpeech — РФ-провайдер по стеку), фильтруется только текст для LLM/эмбеддингов.

### D9: TTS-кэш в Redis

Ключ `tts:{voice_id}:{sha256(text)}` → кадры PCM16 24 кГц (по 200 мс, как в контракте), TTL 7 дней. Кэшируются только фразы из белого списка (ритуалы, приветствия, кризисное вмешательство) — кэшировать произвольную генерацию бессмысленно и растит Redis.

### D10: Каркас — по проектным правилам, как у backend

Конфиг — env-config-rules (pydantic-settings, `validation_alias`, `SecretStr` для ключа Cloud.ru и внутреннего токена, fail-fast, агрегатор `APP_CONFIG`). Логи — logging-rules (loguru + ContextVars + patcher, три sink'а, маскирование ПДн). Заголовки — api-headers-rules (middleware извлекает x-trace-id/rqUId и ко в ContextVars, проброс во внешние вызовы). Ошибки — `{"error":{code,message,details}}` по каталогу specs `agent-api`. Структура `agent/app/`: `api/` (internal роутеры), `graph/` (LangGraph: state, nodes, prompts), `services/` (safety, emotion, memory, pii), `clients/` (cloudru_llm, salutespeech, redis, postgres), `core/` (config, logging, errors), `schemas/`.

### D11: Деплой

Multi-stage Dockerfile на uv (как у backend), образ `cr.yandex/crpsqeamqpuvrkm5tpr9/agent/agent:<tag>`, манифесты в `k8s/` для ns `agent`: Deployment (2 реплики, resources с лимитами), Service ClusterIP (без HTTPRoute — недоступен снаружи), `imagePullSecrets: registry-pull`, env из нового Secret `agent-secrets` (`<CHANGE_ME_*>` в git, реальные значения — `kubectl create secret`). NetworkPolicy: ingress только из ns `backend`. Внутренний токен обязателен на `/v1/**` (specs `agent-api`, «Внутренняя авторизация»): политика защищает от посторонних клиентов, токен — от тех, кто дошёл до сервиса сам.

Реплики и остановка пода: состояние диалога живёт в БД и Redis, а не в памяти реплики, поэтому любой запрос (REST и сокет) может прийти на любую реплику, и число реплик можно менять автоматически. По `SIGTERM` реплика перестаёт принимать новые сокеты и реплики, дописывает идущие ответы и сохраняет их в историю, затем закрывает сокеты кодом `1012`; в манифесте задаётся `terminationGracePeriodSeconds` 30 (ориентир 20–30 секунд). Клиент после такого обрыва переподключается к другой реплике и находит законченный ответ в истории (specs `agent-api`, «Работа нескольких реплик и остановка пода»). Автоскейлинг (HPA) вне прав роли `developer` — запрос владельцу кластера.

## Risks / Trade-offs

- [Качество/стилистика моделей Cloud.ru для эмпатичного русского диалога не проверена] → промпт-пакеты изолированы (D5), Langfuse scores на качество ответов, замена модели — конфиг (D3).
- [Лимиты/латентность Cloud.ru (rate limits, очереди)] → стриминг с первого токена, таймауты + деградация `AGENT_LLM_UNAVAILABLE`, отдельные дешёвые модели для классификаторов снижают нагрузку.
- [Agent — владелец ПДн-данных диалогов (D6): бэкапы, миграции, удаление] → собственная БД `agent` с миграциями, синхронное `DELETE /v1/users/{userId}`, бэкапы и политика хранения — задачи 2.4 и 5.6; данные остаются в кластере (152-ФЗ).
- [«Качели» при двух соединениях на один диалог: любой код закрытия, кроме `1000`/`1012`, клиент отрабатывает переподключением] → agent не вытесняет живой сокет, а отклоняет новое соединение `409` (specs `agent-api`, «Обрыв и переподключение»).
- [SaluteSpeech — единая точка отказа голоса] → circuit breaker + деградация в текст (specs speech-pipeline), TTS-кэш критичных фраз.
- [PII-маскирование natasha несовершенно (пропуск сущности → утечка в Cloud.ru)] → Cloud.ru — РФ-провайдер (152-ФЗ допустимо), regex-добор для телефонов/документов, логи внешних вызовов только с маскированным текстом.

## Migration Plan

1. Развёртывание agent в ns `agent` с `AGENT_LLM_API_KEY` (Cloud.ru) — независимо от backend, проверка `/health/ready`.
2. Вызывающая сторона: клиент agent (env `AGENT_API_URL` + `AGENT_API_TOKEN`) вызывает диалоговый API; хранение диалогов, сообщений и сводок у неё отсутствует. Если вызывающей стороной остаётся backend из add-backend-sessions-streaming, его design/tasks пересматриваются отдельно (openspec-update-change): диалоги, сообщения и сводки переезжают к agent, backend остаётся транспортом (аккаунты, лимиты канала, reconnect).
3. Feature flag `AGENT_ENABLED` у вызывающей стороны: выкатка → проверка диалоговой регрессии → снятие флага. Rollback: флаг off, возврат к прежнему поведению.

## Open Questions

- Конкретные идентификаторы моделей Cloud.ru (генерация / классификаторы / эмбеддинги) — выбираются при реализации из доступных в выданном проекте Cloud.ru; фиксируются в конфиге, не в specs.
- **Кто вызывает agent:** шлюз приложения «Рядом» (он не хранит диалоги) или backend из add-backend-sessions-streaming. От ответа зависит задача 7.4: если backend, он должен проксировать диалоговый API и сокет, а его собственные таблицы сессий и сообщений становятся лишними.
- **Озвучка по требованию.** Agent не знает, слушают его или читают, и озвучивает всё; в текстовом режиме клиент кадры выбрасывает, а трафик (около 48 КБ/с вниз) и синтез тратятся зря. Предложение: вызывающая сторона сообщает режим при открытии сокета и отдельным кадром при переключении. Пока не реализовано.
- **Дописывать ли ответ после разрыва клиента.** Если клиент оборвался посреди генерации, agent может отменить её (экономит токены, но реплику придётся повторить) или дописать и сохранить (клиент находит ответ в истории). В контракте обязателен только законченный ответ в истории; поведение при отмене — на усмотрение реализации.
- **Куда попадает текст деэскалации.** Кадр `safety` несёт текст, но сохраняется ли он сообщением `assistant` в историю диалога, контракт не оговаривает. Нужно решить, чтобы журнал и экран «Если сейчас тяжело» не расходились.
- **Реплика без `audio_end`.** По контракту она отбрасывается (экран закрыт, обрыв), а не получает ответа; заглушка агента у вызывающей стороны сейчас отвечает после паузы в 700 мс без кадров. Подтвердить намерение.
- **Opus и VAD.** Конец фразы без кнопки и Ogg/Opus вместо PCM — в каком виде и когда (v2); формат PCM16 в v1 зафиксирован.
