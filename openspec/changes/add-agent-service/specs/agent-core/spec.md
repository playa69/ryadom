# Дельта-спецификация: agent-core

## Purpose

Ядро диалоговой логики агента «Слышу Рядом»: конвейер обработки реплики, режимы диалога, кризисный протокол с приоритетом над всем, классификация эмоций, retrieval памяти и стрим-генерация ответов через OpenAI-совместимый LLM API (модели в Cloud.ru, данные в РФ).

## ADDED Requirements

### Requirement: Конвейер обработки реплики

Агент SHALL обрабатывать каждую реплику пользователя конвейером: (1) получение текста реплики (напрямую или из ASR — см. speech-pipeline) и её сохранение в историю диалога; (2) кризис-классификация; (3) классификация эмоций; (4) retrieval памяти; (5) стрим-генерация ответа LLM и его сохранение; (6) TTS (см. speech-pipeline). Порядок MUST гарантировать, что кризис-классификация выполняется до генерации ответа. Каждый этап MUST быть независимо наблюдаем (трейсинг этапа с длительностью и результатом).

#### Scenario: Текстовая реплика полного цикла

- **WHEN** агент получает текстовую реплику в открытом диалоге с `level=green`
- **THEN** выполняются этапы 2–5, ответ стримится токенами, каждый этап покрыт трейсом с длительностью

#### Scenario: Кризис перекрывает генерацию

- **WHEN** кризис-классификатор возвращает `level=red` на любой реплике
- **THEN** этапы retrieval и обычной генерации пропускаются, запускается кризисная ветвь (см. «Кризисный протокол»)

### Requirement: Режимы диалога

Агент SHALL вести реестр режимов диалога `vent`, `chat`, `gestalt_diary`, `recovery`, `rituals` как промпт-пакетов. Режим MUST определять системный промпт, набор инструментов и стиль ответов (vent — без советов, если не просят; recovery — бережный, с учётом HALT; rituals — ведение ритуала утро/вечер) и MUST передаваться в каждый вызов генерации. В контракте agent-api v1 режим не передаётся: у приложения сегодня один способ разговора, и каждый диалог идёт в режиме `vent`. Когда другим режимам появится экран, в `POST …/dialogs` добавится поле `mode` (новое поле не меняет версию контракта); значение `warmth` при этом MUST отклоняться ошибкой валидации (зарезервировано под v1).

#### Scenario: Режим vent без советов

- **WHEN** диалог идёт в режиме `vent` и пользователь выговаривается без явного запроса совета
- **THEN** ответы сгенерированы по промпту режима `vent` (отражение чувств, без непрошеных рекомендаций)

#### Scenario: Режим по умолчанию

- **WHEN** диалог создан через `POST …/dialogs` без указания режима
- **THEN** все ответы диалога генерируются по промпту режима `vent`

### Requirement: Кризисный протокол

Агент SHALL классифицировать каждую реплику двухступенчатым классификатором с приоритетом recall (быстрые эвристики/словари → LLM-классификатор на дешёвой модели) с уровнями `green`/`yellow`/`red`. При `level=red` агент MUST прервать обычный конвейер и выдать кризисное вмешательство: детерминированный деэскалационный текст кадром `safety` (см. agent-api «Тревога»), независимо от режима диалога, лимитов и метрик. Линии помощи (горячие линии) показывает вызывающая сторона из своего списка, поэтому агент в v1 их не присылает. Кризисное вмешательство MUST быть детерминированным (не зависеть от LLM-генерации в момент срабатывания). При `level=yellow` агент MUST смягчить стиль ответа и усилить мониторинг без прерывания диалога; уровень вызывающей стороне не передаётся (кадр `safety` означает только «помощь нужна сейчас»), он фиксируется в трейсе и в данных агента.

#### Scenario: Срабатывание red в любом режиме

- **WHEN** реплика с признаками суицидального риска приходит в диалоге любого режима
- **THEN** агент немедленно выдаёт детерминированное кризисное вмешательство (кадр `safety` с текстом деэскалации), обычная генерация не выполняется

#### Scenario: Уровень yellow

- **WHEN** классификатор возвращает `yellow`
- **THEN** диалог продолжается, ответ генерируется в смягчённом стиле, кадр `safety` не отправляется, уровень зафиксирован в трейсе

### Requirement: Классификация эмоций

Агент SHALL определять эмоциональные теги каждой реплики пользователя (набор тегов с валентностью, напр. anxiety/sadness/anger/joy + интенсивность). Теги MUST сохраняться агентом вместе с сообщением (`emo_tags`) и использоваться для персонализации. Вызывающей стороне в v1 теги не передаются: ни один экран приложения их не показывает.

#### Scenario: Теги эмоций сохранены

- **WHEN** обработка реплики завершена без кризиса
- **THEN** в данных агента у сообщения есть эмоциональные теги с интенсивностью, в кадрах для вызывающей стороны их нет

### Requirement: Retrieval памяти

Агент SHALL обогащать контекст генерации сводкой памяти пользователя: активными фактами (близкие, обстоятельства, что помогает, как говорить, о чём не говорить) с весом важности, давности и подтверждений, в пределах бюджета 300–600 токенов (потолок 800). Эмбеддинги, векторный поиск и профиль личности (черты, Big Five, веса приёмов) не используются. Запись фактов MUST выполнять сам агент (фоновое извлечение моделью в РФ после разговора, с маскированием и серверными проверками). Сводка MUST учитывать только данные пользователя из пути запроса (`userId`). Диалог «Без памяти» (`memory: "off"` при создании) MUST NOT читать долговременную память и MUST NOT записывать в неё данные такого диалога. Подробности — в спецификации памяти v1.0 (`docs/agent-memory-spec.md`, удалена из репозитория, есть в истории git).

#### Scenario: Персонализированный ответ

- **WHEN** у пользователя есть факты памяти и прошлые диалоги, релевантные реплике
- **THEN** генерация использует их как контекст (упоминание близких, триггеров, что работало раньше)

#### Scenario: Данные только своего пользователя

- **WHEN** retrieval выполняется для `userId` из пути запроса
- **THEN** в контекст не попадают сообщения и факты других пользователей

### Requirement: Генерация ответа через OpenAI-совместимый API

Агент SHALL генерировать ответы стримом (токен за токеном) через OpenAI-совместимый Chat Completions API с endpoint и ключом из конфигурации (провайдер Cloud.ru). Модель генерации, модель классификаторов и модель эмбеддингов MUST задаваться конфигурацией независимо друг от друга. При недоступности LLM-провайдера агент MUST прислать кадр `error` с кодом `AGENT_LLM_UNAVAILABLE` (см. agent-api «Формат ошибок»), а не молча зависнуть. Эмбеддинги для retrieval MUST получаться тем же OpenAI-совместимым интерфейсом.

#### Scenario: Стрим-генерация

- **WHEN** конвейер дошёл до генерации
- **THEN** токены ответа передаются вызывающей стороне кадрами `assistant_delta` по мере поступления, по завершении — `assistant_end` с полным текстом

#### Scenario: Недоступность провайдера

- **WHEN** LLM-провайдер недоступен или истёк таймаут
- **THEN** вызывающая сторона получает `error` с кодом `AGENT_LLM_UNAVAILABLE` или `AGENT_TIMEOUT` и показывает человеку мягкий фолбэк

### Requirement: PII-фильтрация перед внешними вызовами

Агент SHALL маскировать персональные данные (NER: ФИО, телефоны, адреса, документы) в тексте, отправляемом внешним моделям (LLM, классификаторы, эмбеддинги), и восстанавливать маскированные сущности в сгенерированном ответе, если модель их переиспользовала.

#### Scenario: Маскирование ПДн

- **WHEN** реплика содержит ФИО и телефон
- **THEN** во внешний вызов уходит текст с замаскированными сущностями; логи вызова не содержат исходных ПДн

### Requirement: Антизависимый контур

Агент SHALL распознавать состояние «долгий диалог/высокая дневная нагрузка» по собственной истории диалогов (длительность текущего диалога и суммарное время за сутки; пороги — в конфигурации): при превышении агент MUST мягко подводить к завершению и рекомендации живого контакта вместо удержания в диалоге. Внешний флаг от вызывающей стороны в v1 не требуется. Агент MUST NOT генерировать контент, поощряющий зависимость (обещания «я всегда рядом, только со мной», ревность к живым людям).

#### Scenario: Превышение дневной нагрузки

- **WHEN** суммарное время диалогов пользователя за сутки превысило настроенный порог
- **THEN** ответ мягко подводит к завершению диалога и/или рекомендует живой контакт
