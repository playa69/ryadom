## 2. Клиенты внешних сервисов

- [ ] 2.1 `app/clients/cloudru_llm.py` (design D3): `AsyncOpenAI` с `base_url` Cloud.ru; методы `chat_stream()` (токен-генератор), `classify()` (JSON response_format, дешёвая модель), `embed()`; таймауты, retry с backoff, circuit breaker. Критерий: интеграционный тест с реальным ключом — стрим отдаёт токены, classify возвращает валидный JSON; при недоступном endpoint — ошибка `AGENT_LLM_UNAVAILABLE` за время таймаута.
- [ ] 2.2 `app/clients/salutespeech.py`: ASR-стриминг (частичные/финальные гипотезы) и TTS-стриминг (аудио-чанки), таймауты + circuit breaker по specs/speech-pipeline «Устойчивость внешних вызовов». Критерий: интеграционный тест — кадры PCM16 16 кГц → итоговая расшифровка; текст → кадры PCM16 24 кГц по 200 мс; недоступность провайдера → ошибка за время таймаута.
- [ ] 2.3 `app/clients/redis.py`: подключение через Sentinel, операции для TTS-кэша (get/set с TTL). Критерий: юнит-тест с fakeredis — set/get/TTL работают.
- [ ] 2.4 `app/clients/postgres.py` + миграции alembic (design D6): async-engine SQLAlchemy к собственной БД `agent`, пул с ограничением; схема — диалоги, сообщения (`emo_tags`, эмбеддинг pgvector), сводки, факты памяти. Критерий: подключение к port-forward БД выполняет `SELECT 1`; `alembic upgrade head` применяется на пустую БД и откатывается; политика бэкапов БД согласована с владельцем кластера.

## 3. Сервисы доменной логики

- [ ] 3.1 `app/services/pii_service.py` (design D8): natasha NER (PER/LOC/ORG) + regex (телефоны, email, паспорта) → маскирование в `[PER_1]` с маппингом, обратная подстановка в ответе. Критерий: юнит-тесты specs/agent-core «PII-фильтрация» — ФИО и телефон маскируются, лог вызова не содержит исходных значений, подстановка восстанавливает текст.
- [ ] 3.2 `app/services/safety_service.py` (design D7): ступень 1 — словари/регулярки суицидальных маркеров; ступень 2 — LLM-классификатор (`level`, rationale) через `cloudru_llm.classify()`; эскалация вверх при сомнении; детерминированные шаблоны кризисного вмешательства (деэскалация + горячие линии, константа до появления справочника add-backend-content). Критерий: юнит-тесты specs/agent-core «Кризисный протокол» — маркерная реплика → `red` и шаблон вмешательства без вызова генерации; нейтральная → `green`; recall-набор (≥ 20 эталонных кризисных фраз) классифицируется не ниже `yellow`.
- [ ] 3.3 `app/services/emotion_service.py`: классификация эмоций реплики (теги + валентность + интенсивность) через `classify()`. Критерий: юнит-тест specs/agent-core «Классификация эмоций» — результат содержит теги с интенсивностью из фиксированной таксономии.
- [ ] 3.4 `app/services/memory_service.py` (design D6): retrieval — факты L2 (`memory_facts`), vector-поиск по `messages.embedding` с весом давности, время с последнего диалога из собственной истории; фильтр строго по `user_id` из пути запроса. Критерий: юнит-тесты specs/agent-core «Retrieval памяти» — чужие данные не возвращаются; персонализированный контекст собирается из фактов и прошлых сообщений.
- [ ] 3.5 `app/services/tts_cache_service.py` (design D9): кэш `tts:{voice_id}:{sha256(text)}` в Redis, TTL 7 дней, только фразы из белого списка (ритуалы, приветствия, кризисное вмешательство). Критерий: юнит-тест specs/speech-pipeline «Кэш типовых фраз» — повторная фраза отдаётся без вызова SaluteSpeech (spy на клиенте).
- [ ] 3.6 `app/services/dialog_service.py` (design D6, specs/agent-api «Начало и возобновление диалога», «Завершение диалога»): создание/возобновление открытого диалога (идемпотентно, не больше одного на пользователя), приветствие и `sinceLastDialogHours`, сохранение сообщений с идемпотентностью по клиентскому `id` (`ack` с тем же `messageId`), журнал с курсором, завершение со сводкой (`title`, `themes`, `tensionBefore`, `tensionAfter`), проверка принадлежности пары (`userId`, `dialogId`). Критерий: юнит-тесты — второй `POST dialogs` возвращает тот же диалог с `resumed: true`; повтор `user_message` с тем же `id` не создаёт второго сообщения; чужой `dialogId` → «не найден».

## 5. Внутренний API

- [ ] 5.1 `app/api/dialogs.py` — REST (specs/agent-api «Начало и возобновление диалога», «Журнал и история диалогов», «Завершение диалога», «Принадлежность диалога»): `POST /v1/users/{userId}/dialogs`, `GET …/dialogs`, `GET …/dialogs/{dialogId}`, `POST …/dialogs/{dialogId}/end`; валидация, единый формат ошибок. Критерий: интеграционные тесты — идемпотентный `POST` (`resumed: true`), страница журнала с курсором, история с `messages`, повторный `end` возвращает ту же сводку, чужой `dialogId` → `404`.
- [ ] 5.2 `app/api/dialog_ws.py` — WebSocket `GET …/dialogs/{dialogId}/ws`, текст (design D2, specs/agent-api «Разговор по WebSocket»): рукопожатие с проверкой пары (`404`), кадр `ready` первым, `user_message` → `ack` (после сохранения) → `assistant_start/delta/end`, очередь реплик, идемпотентность по `id`, `end` → `ended` и закрытие кодом `1000`. Критерий: интеграционный тест WS — повтор `user_message` с тем же `id` даёт тот же `messageId` и один ответ; `assistant_end.text` равен склейке дельт; рукопожатие для чужого диалога отклоняется.
- [ ] 5.3 Голос в сокете диалога (specs/agent-api «Голос — формат и ввод», «Голос — озвучка ответов», «Приветствие»; specs/speech-pipeline): двоичные кадры `[вид][номер uint32 BE][PCM16]`, вход `0x01` (16 кГц, 100 мс), выход `0x02` (24 кГц, 200 мс); `audio_start`/`audio_end`, `transcript` (partial ≤ 5/с, final с `messageId`, тишина без `messageId`); озвучка по предложениям с `tts_start` не позже 0,9 с после `assistant_end`; `tts_cancel`; приветствие под `messageId` `"greeting"` один раз на каждый `POST …/dialogs`. Критерий: интеграционный тест WS — кадры `0x01` + `audio_end` → один `transcript { final: true, messageId }` и ответ; `tts_cancel` останавливает кадры сразу; повторное подключение не озвучивает приветствие снова.
- [ ] 5.4 Авторизация внутренним токеном на `/v1/**` и рукопожатии WebSocket (dependency, shared secret из конфига) + таймаут реплики 60 сек с кадром `error` `AGENT_TIMEOUT` + отмена вызовов ASR/TTS при разрыве соединения за 5 сек. Критерий: тесты specs/agent-api «Внутренняя авторизация» и «Таймауты и отмена» — `401` без токена (REST и сокет); зависший мок → `AGENT_TIMEOUT`; разрыв сокета отменяет мок синтеза.
- [ ] 5.5 Деградации и ошибки (specs/speech-pipeline «Деградация в текстовый режим», specs/agent-api «Формат ошибок»): отказ ASR/TTS → `error VOICE_UNAVAILABLE` либо отсутствие `tts_start`, диалог продолжается текстом; отказ LLM → `error AGENT_LLM_UNAVAILABLE`. Критерий: тесты — отказ TTS → текстовый ответ без озвучки; отказ LLM посреди ответа → кадр `error` с кодом `AGENT_LLM_UNAVAILABLE`.
- [ ] 5.6 `DELETE /v1/users/{userId}` (specs/agent-api «Стирание пользователя»): синхронное и идемпотентное удаление диалогов, сообщений, сводок и памяти пользователя до ответа `204`. Критерий: тест — после `204` в БД нет строк пользователя; повторный вызов безопасен; чужие данные не затронуты.
- [ ] 5.7 Несколько реплик и остановка пода (specs/agent-api «Обрыв и переподключение», «Работа нескольких реплик и остановка пода»; design D11): состояние диалога только в БД и Redis; по `SIGTERM` перестать принимать новые сокеты и реплики, дописать идущие ответы и сохранить, закрыть сокеты кодом `1012`; новое соединение к диалогу с живым сокетом → `409`. Критерий: тест с двумя экземплярами приложения на общей БД — любой обслуживает любой диалог; `SIGTERM` посреди ответа → ответ в истории и закрытие `1012`.
