# Продуктовая аналитика (PostHog)

Проект `Ryadom` в PostHog Cloud EU, id `300786`. Как устроен сбор, что отправляется и чего нет, каталог событий —
[docs/analytics.md](../../../docs/analytics.md), там же — что считается целевым действием и как цифры сверяются с
базами (раздел «Целевое действие, DAU и воронка»). Типы событий и свойств — `app/packages/analytics/src/events.ts`.

## Доступ

```bash
node .agents/skills/analytics/scripts/hogql.mjs "SELECT count() FROM events WHERE timestamp > now() - INTERVAL 1 DAY"
node .agents/skills/analytics/scripts/hogql.mjs -f .agents/skills/analytics/scripts/queries/daily.sql --set days=14
```

Скрипт шлёт HogQL в `POST /api/environments/300786/query/` и печатает таблицу (`--json` — колонки и строки как JSON).
В тексте запроса `{{people}}` заменяется стандартным фильтром людей (ниже), остальные `{{имя}}` берутся из
`--set имя=значение`; `--dry` печатает готовый запрос и ничего не отправляет (ключ не нужен). Нужен личный ключ PostHog
с правом `query:read` в `POSTHOG_PERSONAL_API_KEY`; его выдаёт администратор, в чат и в файлы репозитория он не
попадает. Публичный токен проекта `phc_…` (`POSTHOG_KEY`) для запросов не годится: он только принимает события.

Без ключа, из браузера, где человек вошёл в `eu.posthog.com`: `--dry` раскрывает заготовку, дальше запрос выполняет
`fetch` со страницы проекта (сессия и заголовок `X-CSRFToken` из cookie `posthog_csrftoken`):

```js
window.__q = async (sql) => {
  const token =
    (document.cookie.match(/posthog_csrftoken=([^;]+)/) || [])[1] || "";
  const r = await fetch("/api/environments/300786/query/", {
    method: "POST",
    credentials: "include",
    headers: { "Content-Type": "application/json", "X-CSRFToken": token },
    body: JSON.stringify({ query: { kind: "HogQLQuery", query: sql } }),
  });
  const j = await r.json();
  return j.results ? { columns: j.columns, rows: j.results } : j;
};
```

- Открывай PostHog в **своей** вкладке и перед `fetch` проверяй `location.host.includes('posthog.com')`: чужие
  вкладки человека не трогай.
- Страница `/login` вместо проекта — сессия кончилась (бывает через несколько дней). Попроси человека войти; логин и
  пароль не вводи.
- Веб-интерфейс `app.posthog.com` из части регионов отвечает 403 «not available in your region» — используй
  `eu.posthog.com`.

**Ничего не менять в проекте без прямой просьбы:** дашборды, инсайты, когорты, настройки проекта, люди. Запросы — только
чтение.

## Фильтр людей

Любой подсчёт людей начинается с исключения тестового, командного трафика и событий без человека. В заготовках это
`{{people}}`; в ручном запросе подставь этот текст:

```sql
WHERE person_id NOT IN COHORT 275976                                   -- нагрузочный тест 13.10, 150 аккаунтов
  AND coalesce(properties.app_env, '') NOT IN ('local', 'staging', 'development')
  AND coalesce(properties.traffic_type, 'real') NOT IN ('test', 'internal')
  AND event NOT IN ('safety_signal', 'sos_opened', 'hotline_called', 'password_reset_requested', 'account_deleted')
  AND NOT (event = 'cta_clicked' AND properties.cta = 'hotline')       -- события без человека, см. ниже
```

`traffic_type` ставит сервер по аккаунту (`users.properties.traffic_type`): `test` — устройства с id на `loadtest-`,
`internal` — команда, помеченная вручную (запись в боевую базу, скилл `db`, только по «да»). Аккаунт команды без метки
считается настоящим человеком: исключай его по началу id через `POSTHOG_EXCLUDE_PERSONS=<начало id>,<начало id>`
(скрипт добавит `toString(person_id) NOT LIKE '…%'`); список хранится локально у администратора, в репозиторий он не
попадает. Аккаунты новых нагрузочных прогонов нужно дописывать в когорту 275976 (запрос — в docs/analytics.md,
«Дашборды и тестовые данные») — это изменение проекта, только по просьбе.

**События без человека** (`safety_signal`, `sos_opened`, `hotline_called`, `password_reset_requested`,
`account_deleted`, `cta_clicked` с `cta = 'hotline'`) уходят со случайным id на каждое событие и временем,
округлённым до часа. `uniq(person_id)` по ним считает **события, а не людей**: без исключения в «посетителях» и
«новых» оказываются лишние «люди». Сколько было нажатий SOS и звонков — сказать можно, скольким людям — нет.

## Заготовки запросов

`scripts/queries/*.sql`, запуск: `node .agents/skills/analytics/scripts/hogql.mjs -f <файл> --set имя=значение`.
`since` — UTC в виде `2026-10-15 17:18:49` (Москва минус три часа).

| Файл                           | Что считает                                                     | Параметры          |
| ------------------------------ | --------------------------------------------------------------- | ------------------ |
| `daily.sql`                    | говорившие, реплики, вызовы, новые аккаунты по дням (Москва)    | `days`             |
| `target-people.sql`            | говорившие и люди с разговором от N реплик в одном диалоге      | `replies`          |
| `spoke-before-dialog-turn.sql` | говорившие до 13.10 вечером, когда `dialog_turn` ещё не было    | —                  |
| `new-people.sql`               | новые говорившие по дням и те из них, кто дошёл до N реплик     | `since`, `replies` |
| `retention.sql`                | вернувшиеся через N часов и знаменатель                         | `hours`            |
| `sources.sql`                  | входные сессии по рефереру и UTM                                | `since`            |
| `entry-pages.sql`              | с какой страницы начинаются сессии (лендинг, веб, Mini App)     | `since`            |
| `platform-funnel.sql`          | новые люди по платформе: открыл → аккаунт → диалог → реплика    | `since`            |
| `telegram-start.sql`           | Mini App по метке ссылки `startapp`: открыл → аккаунт → реплика | `since`            |
| `components.sql`               | вызовы компонентов агента по типу, исходу, кэшу                 | `since`            |
| `screens.sql`                  | какие экраны открывают                                          | `since`            |
| `reply-input.sql`              | реплики голосом и текстом                                       | `since`            |

Остальное — вручную по шпаргалке:

```sql
-- Сказал хоть что-то: dialog_turn появился 13.10 вечером, до него — счётчики в конце диалога
SELECT count(DISTINCT person_id) FROM events
WHERE (event = 'dialog_turn' OR (event IN ('dialog_ended', 'dialog_interrupted') AND toInt(properties.user_messages) > 0))
  AND <фильтр людей>

-- Кризисные сигналы и SOS: события без человека, фильтр людей не нужен; считай события, не людей
SELECT event, properties.level, count() FROM events
WHERE event IN ('safety_signal', 'sos_opened', 'hotline_called') AND timestamp > now() - INTERVAL 7 DAY GROUP BY 1, 2
```

## Определения

Назови в отчёте, какое взято: «человек сказал» и «целевое действие» в проекте и в отчёте для конкурса не совпадают.

- **Целевое действие по проекту** — хотя бы одна реплика (`dialog_turn`), см. docs/analytics.md. **«Разговор от трёх
  реплик»** — три `dialog_turn` с одним `dialog_id`; так считали для конкурса с 15.10.2026 (`target-people.sql`,
  `replies=3`). Реплики разных диалогов не складываются.
- **Активный день, DAU** — день по Москве, в который человек сказал реплику. Число людей за сутки — DAU по целевому
  действию. Последние сутки в выгрузке неполные: так и пиши.
- **Новый** — первая реплика человека позже даты среза (`new-people.sql`); **вернувшийся** — говорил до среза и
  сказал реплику после. Накопительный итог бери из `target-people.sql` плюс `spoke-before-dialog-turn.sql`, а не
  складывай «было + новые»: заговоривший раньше и ставший целевым позже в «новых» не виден.
- **Удержание N ч** — последняя реплика позже первой не меньше чем на N часов; доля от тех, чья первая реплика была
  больше N часов назад (`retention.sql`, сам знаменатель в ответе тоже называй: «6 из 28»).
- **Обращения на DAU** — `component_called` на активного человека за сутки; фразы из кэша (`cached = true`) настоящими
  вызовами не считаются, назови, с кэшем число или без. По примеру из Положения конкурса (прил. 2 п. 2.2) системный
  промпт над моделью тоже считается вызовом: +1 на каждый ход `live`, в журнале события для него нет. Для конкурса
  15.10 считали так; в отчёте называй оба числа — по журналу и с навыком.
- **Посетитель — не человек.** В Telegram Mini App и на лендинге события до входа анонимны (id устройства, без
  профиля): это устройства, а не люди. Человеком становится тот, у кого есть аккаунт.

## Как читать источники

- **UTM и реферер** есть только у клиентских событий (`$pageview`, `app_opened`). У серверных (`account_created`,
  `dialog_turn`…) полей `$session_entry_*` нет: источник по ним не определить, берись за `sources.sql`.
- `$direct` — реферера нет: набрал адрес, пришёл из мессенджера или открыл Telegram Mini App. Свой домен
  `xn----htbtgjker8b3a2c.xn--p1ai` (слышу-рядом.рф) — переход лендинг → приложение, не внешний источник.
- Telegram Mini App: вход на `/pwa/` и `app_platform = telegram`, реферер всегда `$direct`. Источник задаёт метка в
  ссылке на бота, `https://t.me/slyshu_ryadom_bot?startapp=<метка>`: клиент кладёт её в `start_param` события
  `app_opened` (`telegram-start.sql`). Поле есть только у запусков из образа PWA, который это пишет; ссылка без
  метки, кнопка меню бота и запуски до этого образа дают пустое значение. Соглашение о метках — в docs/analytics.md.
- UTM остаётся только короткой меткой из букв, цифр и `_.-`; клик-идентификаторы рекламы (`gclid`, `yclid`…) при
  очистке удаляются.

## Сверка с базой

PostHog сверяется с базами (скилл `db`): `dialog_id` событий = `dialogs.id` в базе `agent`, `person_id` = id аккаунта
(`users.id` в базе `app`). Для пересечения выгрузи оба списка в файлы вне репозитория и сопоставь скриптом; люди,
которые говорили до 10.10.2026, есть в базе, но не в PostHog (аналитики ещё не было). Расход токенов и стоимость
PostHog не хранит: они в Langfuse и Prometheus (скилл `logs`).

## Отчёт

В ответе всегда: период и на какой момент выгружено, какой фильтр и какое определение целевого действия, что не сверено
с базами и Langfuse, какие сутки неполные. Для «откуда» и «чем пользуются» давай цифры людей и сессий отдельно от
событий.

## Грабли

- **100 строк по умолчанию.** HogQL молча режет ответ, если в запросе нет `LIMIT`; скрипт предупреждает. Список
  событий, сгруппированный с `LIMIT 40`, тоже обрезает редкие события: ставь `LIMIT` с запасом.
- **Время** в `timestamp` — UTC: для суток по Москве `toTimeZone(timestamp, 'Europe/Moscow')`.
- **Типы.** `greatest()` и сравнения между `Int64` и `UInt64` падают: приводи явно или считай в скрипте.
- **Пустое агрегирование.** `minIf` и `maxIf` без подходящих строк дают `1970-01-01 00:00:00`, а не `NULL`;
  `argMinIf` — `NULL`. Условие «позже даты» это отсекает, а «раньше даты» — нет.
- **Псевдоним с именем столбца** внутри агрегата (`min(first_turn) AS first_turn`) может сломать запрос или исказить
  результат: называй по-разному.
- **События без человека** (см. «Фильтр людей») — с людьми не сопоставляются и в «людях» не считаются.
- **`app_version`** — тег образа (`--build-arg RELEASE`); `0.1.0` значит, что образ собран без него.
- **Свойства людей и событий не выгружай целиком:** в отчёты и задачи — только агрегаты. Готовые карточки — дашборды
  «Рядом — продукт» (`https://eu.posthog.com/project/300786/dashboard/1012431`) и «Рядом — воронка и удержание»
  (`…/dashboard/1020753`).
