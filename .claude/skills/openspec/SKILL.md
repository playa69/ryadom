# OpenSpec

OpenSpec в `openspec/` описывает, что делает продукт: поведение, которое видит человек, и контракты между клиентами,
API и агентом. Как устроен код — в `design.md` и `tasks.md`, не в спеках.

## Что где лежит

- `openspec/specs/<capability>/spec.md` — как продукт работает сейчас, по папке на capability. Сюда пишет только
  архивация change'а; руками не правят.
- `openspec/changes/<change>/` — изменение в работе: `proposal.md` (зачем и что меняется), `design.md` (решения и
  открытые вопросы; для мелких изменений можно без него), `specs/<capability>/spec.md` (дельта), `tasks.md` (шаги),
  `mockups/` (для интерфейса, до кода).
- `openspec/changes/archive/<ГГГГ-ММ-ДД>-<change>/` — выкаченные изменения: история того, почему всё устроено так.
- `openspec/config.yaml` — контекст проекта и правила артефактов; CLI отдаёт их любому агенту.

## Сейчас источник правды — код

Ни один change ещё не архивирован, `openspec/specs/` нет, а старые change'и разошлись с кодом. Пока базу не сняли с
кода и не архивировали:

- Верь коду в `main`. Спека противоречит коду — прав код; расхождение назови в отчёте и PR.
- Не верь `- [x]` в `tasks.md`: проверь, что код есть в `main`.
- Как требования не используй `add-agent-service` и `add-app-client-specs` (устарели, их заменит база), а также
  всё про удалённый `backend/`.
- В новом change пиши ADDED-требования на то поведение, которое change вводит или меняет, в capability по домену
  продукта. MODIFIED и REMOVED на требования из папки другого change'а не пиши.
- Когда база появится, открытые change'и перебазируются: ADDED-требование, чьё имя уже есть в `openspec/specs`,
  становится MODIFIED.

## Когда нужен change

- Change нужен, когда меняется поведение, которое видит человек или клиент: новая функция, изменённое или убранное
  поведение, изменённый контракт клиент ↔ API ↔ агент. Багфикс, который возвращает описанное поведение, рефакторинг и
  чистка конфигов обходятся без него.
- Одна задача — один change — одна ветка. Имя — глагольная фраза в kebab-case (`add-mood-diary`,
  `restrict-memory-health`).
- Первая строка `proposal.md` — `Задача: PROTEUS-NNN`, если задача есть. Задача ссылается на папку change'а.
- Новая функция или изменение поведения: сначала proposal, дельта, tasks и для интерфейса макеты; покажи их человеку
  и дождись «да», потом код в той же ветке.

Править текущий change или заводить новый:

- Цель та же, уточнилось исполнение (сузили объём, дизайн не сработал, владелец поправил), change ещё не в архиве —
  правь текущий.
- Новая цель или текущий change уже выкачен и архивирован — новый change.
- Архивированный change и `openspec/specs` руками не правят.

## CLI

В зависимостях репозитория CLI пока нет: запускай версию, которой сгенерированы файлы, из корня репозитория.

```bash
npx -y @fission-ai/openspec@1.9.0 <команда>
```

| Команда | Что делает |
|---|---|
| `list`, `list --specs` | change'и в работе, capability |
| `show <имя> --json --no-interactive` | один change или спека |
| `new change <имя>` | заготовка change'а с `.openspec.yaml` |
| `status --change <имя>` | какие артефакты готовы |
| `instructions <артефакт> --change <имя>` | шаблон, указания схемы, контекст проекта и наши правила для `proposal`, `specs`, `design`, `tasks` |
| `instructions apply --change <имя>` | что прочитать и сколько задач сделано — для реализации |
| `validate <имя> --strict`, `validate --all --strict` | проверка формата |
| `archive <имя> --yes` | влить дельты в `openspec/specs` и перенести change в `archive/` |

Агент на вопросы CLI не отвечает: имена всегда явно, плюс `--yes` или `--no-interactive`. `openspec init` и
`openspec update` не запускай: они раскладывают в `.agents/skills/` по скиллу на каждую операцию, а в репозитории
вместо них этот один скилл.

## Обдумать

Размышление до proposal: читай код в `main`, открытые change'и (`list`, `show`) и `docs/spec.md`, задавай вопросы,
сравнивай варианты. Ни файлов, ни кода не пиши. Когда идея сложилась — предложи завести change.

## Предложить

1. Выясни, что должно измениться. Спрашивай, если ответ влияет на объём, видимое поведение, совместимость или
   приёмку; мелкие допущения запиши в proposal.
2. Проверь пересечения: `list` и `git grep -n "Requirement: <имя>" openspec/`. Change с таким именем уже есть —
   спроси, продолжать ли его.
3. `new change <имя>`.
4. Для `proposal`, `specs`, `design`, `tasks` по порядку: `instructions <артефакт> --change <имя>` и файл, который он
   называет, — по его шаблону и правилам. Блоки `<project_context>` и `<rules>` — ограничения для тебя, в файл их не
   копируй. Перед следующим артефактом перечитай уже написанные с диска.
5. `status --change <имя>` показывает все артефакты готовыми; `validate <имя> --strict` зелёный.
6. Стоп. Покажи артефакты человеку и до кода дождись явного «да»: просьба предложить — не просьба реализовать.

## Реализовать

1. `instructions apply --change <имя>`; прочитай proposal, design, дельты и tasks, которые он перечисляет.
2. Задача за задачей: код и тесты, затем `- [ ]` → `- [x]` в том же коммите, что и код задачи. Коммит или PR только
   со спекой галочек не ставит.
3. Галочку — только за полностью сделанное поведение. Остановись и спроси, если задача неясна, дизайн не работает
   (сначала поправь change), работа выходит за рамки спеки или хочется сузить или отложить описанное поведение.

## Поправить change

- Правятся только артефакты планирования, не код. После правки сверь с ней все остальные артефакты в любую сторону
  (правка tasks может потребовать правки proposal) и убери противоречия, пробелы и повторы.
- Правка, которая меняет поведение или объём, требует «да» человека, как новый proposal.
- Change уже реализован — после правки перенеси разницу в код (раздел «Реализовать»).
- Изменилась сама цель — заводи новый change.

## Дельта

Текст по-русски, ключевые слова по-английски (SHALL, MUST, WHEN, THEN), как в существующих change'ах:

```markdown
## ADDED Requirements

### Requirement: Запоминание по просьбе
Агент SHALL сохранять заметку, только когда человек попросил запомнить.
Поверхности: agent · api · web · pwa

#### Scenario: Человек попросил запомнить
- **WHEN** человек говорит «запомни, что у меня кот Барсик»
- **THEN** на экране «Память» появляется заметка «Живёт с котом Барсиком»

#### Scenario: (PWA) Заметка видна без перезагрузки
- **WHEN** …
- **THEN** …
```

- **ADDED** — новое требование.
- **MODIFIED** — скопируй требование из `openspec/specs` целиком и правь: текст и все сценарии, которые остаются. Что
  не перенёс — пропадёт при архивации. Если `validate` не пропускает MODIFIED без одного из сценариев — REMOVED и
  ADDED под новым именем.
- **REMOVED** — имя требования и строки `**Reason**:` и `**Migration**:`.
- **RENAMED** — строки `FROM:` и `TO:`.
- **Имя** `### Requirement:` — ключ для MODIFIED, REMOVED и RENAMED: не меняй его без нужды.
- **Форма** — одно предложение с SHALL или MUST и хотя бы один `#### Scenario:` (четыре `#`) с пунктами **WHEN** и
  **THEN**.
- **Поверхности** — строка `Поверхности:` у каждого требования, только то, что оно затрагивает: agent, api, web, pwa,
  android, ios, tg, admin, landing. Сценарий одной поверхности начинается с неё в скобках: `(PWA)`, `(Android)`.
- **Capability** — по домену продукта (`memory-notes`, `dialog`, `account-deletion`), не по сервису. Прежде чем
  заводить новую, посмотри `openspec/specs` и открытые change'и.
- **Перед MODIFIED** — `git grep -n "Requirement: <имя>" openspec/`. Если то же требование меняет другой открытый
  change, напиши об этом в обеих задачах; кто архивирует вторым, переносит свой блок на обновлённую спеку.
- **Вес** — как можно легче, лишь бы изменение можно было проверить. Без путей к файлам, имён классов и библиотек в
  требованиях.
- **docs/spec.md** держит требования продукта (`REQ-…`): ссылайся на их номера в proposal, сценарии туда не копируй.

## tasks.md

- Разделы по порядку, ненужные пропускай: 0 Решения (вопросы владельцу) → 1 Данные и контракты → 2 Агент → 3 Шлюз
  API → 4 Клиенты по поверхностям → 5 Проверка → 6 Выкат → 7 Архив.
- В каждой задаче — реальные пути и строка `Приёмка:`.
- Раздел «Проверка» — по каждому сценарию: файл unit- или integration-теста; файл e2e и проект (desktop, mobile);
  скриншоты; ручные проверки (Android, iOS, Telegram); проверки после выката (`k8s/postdeploy`).
- В тесте — комментарий с change'ем и требованием: `` `openspec/changes/<change>`, «<требование>» ``.
- Скриншоты визуальной фичи — скилл `screenshots`: снимок на каждый шаг сценария, 390 и 1280, без видео, данные
  только синтетические.

## Архивировать

Когда код в `main` и выкачен; если фича за флагом, требование это говорит.

1. Все задачи `[x]` или помечены `→ <другой change>` или `снято` с причиной.
2. Открытые вопросы в `design.md` закрыты.
3. `validate <change> --strict` зелёный.
4. `archive <change> --yes` вливает дельты в `openspec/specs` и переносит папку в `archive/`. Проверь
   `git diff openspec/specs`: MODIFIED заменяет требование целиком, ничего нужного пропасть не должно. Затем
   `validate --specs --strict`.
5. Коммит — в PR выката или сразу после выката. Задача после этого закрывается.

В `openspec/specs` дельты попадают только через архивацию: заранее руками их туда не вливай. Брошенный change
удаляется, а не архивируется: архив значит «выкачено».

Связанные скиллы: `screenshots` (снимки шагов), `e2e` (тесты в разделе «Проверка»), `commit` (галочки и PR).
